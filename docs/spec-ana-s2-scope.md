## 1. Цель и пользовательская проблема

У аналитики продукта **два пользователя**:

1. **Владелец** — хочет видеть, жив ли продукт и как сработал релиз. Сейчас есть
   голые счётчики; трендов удержания нет (из текущих агрегатов честно не считается —
   §2а), алертов нет, воронка онбординга не измеряется вовсе.
2. **Пользователь** — хочет чувствовать прогресс и возвращаться. Приложение уже
   хорошо показывает «что было», но: нет сравнения «я сейчас vs я в прошлом
   месяце», нет динамики объёма по неделям, тренд упражнения — одно число без
   графика. И главное: пользователь, который **не открыл** приложение, ничего не
   видит вообще — бот молчит. Сводка недели в чате — единственный канал, который
   доходит до него без его действия.

## 2. Треки развития

### (а) Дашборд владельца — добавить в Grafana (код НЕ нужен, только конфиг панелей)

Панели поверх существующего `weeks`-массива (root_selector `weeks`):

|---|---|---|---|
| Открытия по неделям (`maInit`) | уже в инструкции metrics.md | — | сделано |
| Завершённые тренировки / неделю | `weeks.workoutsCompleted` | S | просто ещё панель |

Решение — трек (г1): счётчики `maInitNew`/`maInitRepeat`/`maInitReturn` → тогда панель и «удержание по неделям» (повторные ÷ все) считаются конфигом |

**Алерты (падение init?) — сейчас НЕ включать.** Блокер: данные попадают в gist
только при ручном запуске `ana-to-gist.mjs`; алерт будет срабатывать по устаревшим
данным (ложные тревоги) или молчать. Предусловие — автоматизация выгрузки
(GitHub Action по расписанию или cron на VPS — отдельный `tech`-тикет, НЕ в этом
скоупе). До тех пор — еженедельный ручной осмотр дашборда перед обзором спринта.

**Ценность:** M (видимость трендов) · **Стоимость:** ~0 (панели) + S (г1 для удержания)
· **Privacy:** без изменений.

### (б) Пользовательская аналитика в приложении — что ДОБАВИТЬ осмысленно

Проверка на дубли (§0): сравнения периодов нет; графика объёма нет; тренд упражнения
— только последнее число. Кандидаты:

| # | Идея | Что на экране | Дублирует? | Оценка |
|---|---|---|---|---|
| б1 | **«Этот месяц vs прошлый»** | карточка: тренировки / тоннаж / ккал / время, у каждой дельта ▲▼ (компоненты `.dl-up/.dl-down` уже есть) | нет — сейчас есть только счётчик «в этом месяце» без базы сравнения | S |
| б2 | **Объём по неделям** | столбиковая диаграмма тоннажа за 8–12 недель (SVG-бары, без библиотек) | нет | M |
| б3 | **Прогресс упражнения (90 дней)** | тап по строке в «Трендах» → разворот: спарклайн макс. веса по тренировкам (`maxWeightSeries` уже считается!) + Δ e1RM | нет — данные есть, показывается одно число | M |
| б4 | Ккал по неделям | как б2, но ккал | частично б1; низшая ценность, зависит от профиля | отсечь в б1 строкой |

Оценки S/M — по шкале объёма работ для coder (не SP эпика). **Рекомендация:** когда
дойдёт очередь — б3 (самая «тренировочная» ценность) + б1 (самая дешёвая), б2 следом.
Требует отдельной мини-спеки с макетом до кода.

**Ценность:** M–H для пользователя · **Стоимость:** S–M · **Privacy:** данных не
добавляет (всё считается локально из своих данных, на сервер не уходит).

### (в) Еженедельная сводка ботом — детальная проработка [главный кандидат]

**Суть:** раз в неделю бот сам пишет в чат снимок прошедшей недели по ДАННЫМ САМОГО
пользователя. Это его данные в его чате — легитимно (см. §3), риск ПДн отсутствует:
ничего не уходит на сервер аналитики, владельцу не пересылается.

#### Механика (для coder, оценочно M)

- Триггер: еженедельный job в `Main` (проверка раз в минуту в цикле или
  `ScheduledExecutorService`). Отправка — **понедельник 09:00 по серверным часам**
  (вопрос В3 владельцу: день/время). Сводка за прошедшую ISO-неделю (Пн–Вс).
- Список адресатов: файлы `data/chat_<id>.json` — как у `/announce`, пауза 50 мс.
- Состояние: `data/digest-state.json` вида `{"lastWeek":"2026-W46"}` — защита от
  повторной отправки после рестарта контейнера. Файл глобальный, без ПДн.
- Отключение (вкл. по умолчанию у активных): флаг в `GymData` пользователя —
  **новое опциональное поле** (обратная совместимость: старые файлы без поля =
  сводка включена; эталон — `GymContractTest`). Управление: кнопка под сводкой +
  команда `/digest` (§Тексты).
- Пропуск отправки: нет файла · флаг выключен · **0 завершённых тренировок за
  неделю — молчим** (рекомендация; вопрос В4). Незавершённые не считаются
  (консистентно с `/stats`).
- Курсор недели: если сервер молчал 2+ недели — шлём сводку только за последнюю
  (навёрстывать всю историю — шум).

#### Расчёт метрик сводки (всё уже есть в коде, дублировать не надо)

| Метрика | Как | Референс |
|---|---|---|
| Тренировки | число `finished` с датой в ISO-неделе | `countFinished` |
| Время в зале | Σ `durationMin` | `BotLogic.durationMin` |
| Тоннаж | Σ `avgNum(w) × sets × repsAvg(r)` | формула `workoutVolume`, `web/app.js:221–226`; в боте понадобятся Java-эквиваленты парсеров `avgNum`/`repsAvg` (логика уже есть в `Records` для живых рекордов) |
| Ккал | Σ `calcWorkoutKcal(profile, w)`; нет профиля — строка опускается | формула MET в `BotLogic` |
| Рекорды недели 🏆 | упражнения, у которых max e1RM блока на неделе выше, чем максимум ДО недели («▲ +X кг к 1ПМ»); упражнения без веса — по объёму повторений (как живые рекорды) | `Records.e1rm` |
| Дельта «к прошлой» | те же метрики за предыдущую неделю; прошлой нет — без дельты | — |

#### Тексты сообщений (HTML parse_mode, жирный — как в остальных сообщениях бота)

**Сводка недели:**

```
📊 <b>Итоги недели</b> · 9–15 ноября

🏋️ Тренировки: <b>4</b> · в зале 3 ч 40 мин
⚖️ Тоннаж: <b>6,2 т</b> · ▲ +0,8 т к прошлой
🔥 Ккал: <b>≈ 2 400</b>

🏆 Рекорды недели:
• Жим лёжа — 1ПМ ≈ 82 кг (▲ +2)
• Приседания — 100 кг × 5 — новый максимум

Хорошая неделя. Так держать 💪
```

Правила сборки: секции без данных (ккал без профиля, тоннаж без весов, рекордов
нет) — строка/секция целиком опускается; заголовок всегда; финальная строка
мотивации — 2–3 варианта по числу тренировок (0 тренировок не отправляем вовсе).

С populated-данными меньше порога — рекорды: если за неделю ни одного нового
рекорда, секция 🏆 опускается (не писать «рекордов нет» — демотивирует).

**Клавиатура сводки:**

| Ряд | Кнопка | Тип | Действие |
|---|---|---|---|
| 1 | 📱 Открыть приложение | URL (`appLink`/`webAppUrl`) | открывает Mini App |
| 2 | 🔕 Не присылать сводки | callback `digest:off` | выключает, см. ниже |

**Ответ на `digest:off` (новое сообщение, сводка остаётся в чате):**

```
Хорошо, итоги недели больше не приходят 👌
Вернуть: /digest — покажу последнюю сводку и включу отправку.
```

**Команда `/digest` (новая; также ручной просмотр в любой момент):**

```
За прошлую неделю (9–15 ноября): 3 тренировки, тоннаж 5,1 т, ккал ≈ 1 800.
Сводки недели: 🔔 включены.
```
+ клавиатура: `[🔕 Выключить сводки]` (если включены) / `[🔔 Включить сводки]`
(если выключены) + `[📱 Открыть приложение]`. Если пользователь в чате впервые —
штатный ответ «Нет данных для статистики…» как у `/stats`.
Добавить в `/help` и в описание команды в `TelegramApi` (`cmds`).

**Счётчики к whitelist `Stats.KEYS` (г4):** `digestSent` (отправлено сводок),
`digestOff` (тапов «Не присылать») — видим охват и процент отключок; в дашборд
панель по желанию. Расширение whitelist — по таблице §3, ПДн нет.

#### Состояния и edge cases

| # | Кейс | Поведение |
|---|---|---|
| E1 | 0 завершённых тренировок за неделю | молчим (вопрос В4 — могло бы быть «вернись», но это спам-риск) |
| E2 | нет профиля (вес не задан) | строка 🔥 Ккал опускается |
| E3 | все упражнения без веса | тоннаж опускается; рекорды считаем по объёму повторений |
| E4 | повторения нечисловые («8-10», «макс», «5+1») | тоннаж через `repsAvg`-эквивалент («8-10»→9, «макс»→10, «5+1»→6) — ровно как в приложении, расхождений нет |
| E5 | рестарт сервера в понедельник | `digest-state.json` не даёт отправить дважды; недосыл — только если упало до перезаписи состояния (неделю пропустим, не критично) |
| E6 | часовой пояс сервера (Docker, вероятно UTC) | 09:00 UTC = 12:00 МСК; либо зафиксировать и принять, либо задать env `GYM_DIGEST_TIME`; вопрос В3 |
| E7 | бот заблокирован/чат удалён | ошибка sendMessage глотается, счётчик `digestSent` не растёт; через неделю попытка повторится |

| E9 | активная незавершённая тренировка | не считается (только finished), как в `/stats` |
| E10 | редактирование/удаление тренировок после отправки | сводка — снимок на момент отправки, не пересылается |

удержание и возврат в зал/приложение · **Стоимость:** M (job + расчёты + opt-out +

### (г) Прочие идеи

#### г1. Сегментация init: новые / повторные / вернувшиеся

При `/api/init` классифицировать событие БЕЗ чтения ПДн: файл `data/chat_<id>.json`
отсутствует → `maInitNew`; есть, а последняя активность (mtime файла / предыдущий
init) старше 7 дней → `maInitReturn`; иначе → `maInitRepeat`. Три счётчика в тот же
`weeks`. Даёт дашборду: удержание («повторные ÷ все»), отвал («вернувшиеся» как
 индикатор). **Стоимость:** S · **Privacy:** ок — счётчики, факт существования
файла и его mtime не содержат данных пользователя.

#### г2. События онбординга: `onboardingStarted` / `onboardingCompleted` / `onboardingTutorialSkipped`

Онбординг живёт в `localStorage` (спека [ONB] §7: флаги в `GymData`/на сервере
отсечены) — сервер про него не знает. Механика доставки события (решать coder):
опциональное служебное поле в payload `/api/save` или `/api/init`, которое
`WebServer` передаёт в `stats.inc()` и **не** персистит в `GymData` (формат данных
не меняется — принцип [ONB] §7 соблюдён). Whitelist имён событий, дедуп на клиенте
(флаг в `localStorage` — отправить 1 раз за жизнь онбординга).

**Стоимость:** S–M · **Privacy:** ок (только имена событий, без payload) ·
**Связка:** делать пакетом с онбординг-релизом (вот-вот выкатывается), иначе
воронку первых недель не поймаем — данные необратимы.

#### г3. Воронка онбординга в дашборде

Панели «Онбординг: started → completed → skipped» из г2 (root_selector `weeks`).
Конфиг-only, после г2.

#### г4. Счётчики сводки `digestSent` / `digestOff`

Описано в (в). Панель по желанию.

## 3. Privacy-границы (152-ФЗ / GDPR упрощённо)

### 3.1. Правило «только агрегаты»

- **ПДн** = любые сведения, по которым можно выделить конкретного человека, прямо
  или косвенно (GDPR, Recital 26: псевдонимизированные данные — тоже ПДн;
  chat_id/username — ПДн).
- **Счётчик** = «тип события + число». Выделить человека нельзя → не ПДн, сбор не
  требует согласия, как обычные серверные логи без идентификаторов.
- Граница: если значение можно **приписать конкретному пользователю** — это уже не
  счётчик. «init в 12:03 от chat 123» — ПДн; «за неделю было 40 init» — нет.
- Отдельная категория — **данные пользователя в его собственном чате** (сводка
  недели): это не «сбор», а возврат его же данных ему; на сервер аналитики не
  уходит, владельцу не виден. Легитимно без новых согласий.
- Пересылка обратной связи владельцу (имя/username/chat_id) — уже есть и
  юзер-инициирована ([ONB-T8]); в скоуп не входит.

### 3.2. Таблица границ

| ✅ Можно | ❌ Нельзя |
|---|---|
| счётчики-события в `Stats` (whitelist `KEYS`) | по-пользовательные ряды/сессии в `stats.json` |
| недельные агрегаты `weeks` (26 недель, ротация есть) | списки chat_id/дат/username в аналитике |
| факт «файл данных существует», его mtime (г1) | чтение содержимого `chat_*.json` ради аналитики |
| сводка — свои данные в свой чат | выгрузка пользовательских данных к владельцу/в дашборд |
| whitelist новых ключей через эту спеку (г2, г4) | «соберём на всякий случай, разберём потом» |
| хранение только агрегатов, TTL 26 недель | бесконечная история по-пользовательных событий |

### 3.3. Процессуальное

- Новый счётчик = новая строка в таблице §3.2 этой спеки + `Stats.KEYS`;
  без «тихих» инкрементов мимо whitelist (уже соблюдается кодом).
- В мини-апп НЕ добавлять внешние аналитические SDK (Метрика/GA) — внешние
  зависимости + ПДн-риск + против конвенции «без внешних сервисов».
- Политика `web/privacy.html` при добавлении (в)/(г2): дополнить абзацем «итоги
  недели формируются из ваших данных и остаются в вашем чате; отключается кнопкой
  под сводкой» — мелкая правка, в скоуп (в) включить.

## 4. Приоритизация (рекомендация)

| Порядок | Трек | Почему | Когда |
|---|---|---|---|
| 1 | **(в) сводка ботом** | единственный проактивный контакт; удержание; ценность видна пользователю сразу | следующий спринт, после ответов В1–В4 |
| 2 | **(г2) онбординг-события + (г1) init-сегменты** | данные необратимы: онбординг выкатывается сейчас — не поймаем воронку первых недель; оба трека дешёвые (S) | пакетом с ONB-релизом / сразу следом |
| 3 | **(а) панели дашборда** | кода нет вообще — только конфиг Grafana; но осмысленны, когда есть хотя бы пара недель данных и г1/г2 | сразу после деплоя ANA-T2/T3 + подключения datasource владельцем |
| 4 | **(б1–б3) аналитика в приложении** | ценность высокая, но требует мини-спеки с макетом; приложение и так сильное в статах | после (в); сначала б3+б1 |
| 5 | **алерты** | блокер — ручная выгрузка gist; сначала `tech`-тикет на автоматизацию (GitHub Action/cron) | после автоматизации пайплайна |
| — | (б4) ккал-график, ASCII-графики в боте, A/B, внешние SDK | см. §5 | не делаем |

Резюме: **сводка ботом — следующий шаг** (самая высокая пользовательская ценность
при умеренной стоимости), онбординг-события — дешёвый «поезд-вместе», дашборд —
бесплатный конфиг поверх, пользовательская аналитика приложения — отдельная
дизайн-итерация позже.

## 5. Что НЕ делаем и почему

| Отсечено | Почему |
|---|---|
| По-пользовательные ряды событий, «живые» сессии, список активных чатов в аналитике | Privacy: это уже ПДн (§3); ценность для продукта из 1–2 десятков пользователей не окупает риск |
| Алерты Grafana сейчас | Данные в gist попадают вручную — алерт по устаревшим данным = ложные тревоги; предусловие — автоматизация выгрузки (отдельный tech-тикет) |
| Внешние аналитические SDK в Mini App (Я.Метрика, GA, PostHog…) | Внешние зависимости и передача данных третьим лицам — против конвенции проекта и §3 |
| Трекинг каждого тапа/команды бота | Шум в данных, рост whitelist, риск случайно собрать ПДн; только ключевые события |
| ASCII-графики прогресса в чате бота | Приложение уже рисует статы лучше; чат — канал снимка-сводки, не визуализации |
| Полноценная «аналитика» ккал/тоннажа отдельными бот-командами | Дублирует `/stats` бота и приложение; сводка недели закрывает потребность «что у меня было» |
| A/B-фреймворк, фича-флаги экспериментов | Нет масштаба: измерения на всей базе честнее при N≈десятки |
| Хранение содержимого обратной связи в аналитике | [ONB-T8] уже решено: только счётчик `feedbackSent` |
| Секция «Цель недели» в сводке сейчас | Фичи целей ещё нет ([GOA-I1] — направление на доске); заложено как будущее расширение текста сводки, макет честно её не показывает |
| Навёрстывание пропущенных недель сводки | Шум; за прошлую неделю — одну сводку (E-серия §2в) |

## 6. Вопросы владельцу

1. **Делаем еженедельную сводку ботом (трек «в»)?** Рекомендую да — это главный
   проактивный контакт с пользователем и лучший кандидат следующего спринта.
2. **День и время отправки?** Рекомендация: понедельник 09:00 (итоги завершённой
   недели, настрой на новую). Альтернатива — воскресенье вечер. Часы серверные
   (на VPS, вероятно UTC → 12:00 МСК) — ок или задать пояс?
3. **Пустая неделя (0 тренировок):** молчим (моя рекомендация — сводка не должна
   превращаться в напоминатель) или короткое «на этой неделе не тренился»?
4. **Отключаемость:** кнопка «🔕 Не присылать сводки» под каждой сводкой + возврат
   командой `/digest` — достаточно? Включена по умолчанию у всех, у кого были
   тренировки за неделю — ок?
5. **Состав сводки:** тренировки/время/тоннаж/ккал/рекорды с дельтой к прошлой
   неделе — что приоритетно, что убрать? (Ккал требует профиля — без него строка
   исчезает.)
6. **Privacy-ок?** Сводка — данные пользователя в его же чате, на сервер аналитики
   ничего не уходит (только счётчики `digestSent`/`digestOff`). Границы §3 —
   согласны?
7. **Онбординг-события (г2) + init-сегменты (г1)** добавить мелким тикетом в пакет
   с онбординг-релизом? Данных воронки после выката онбординга не будет, если не
   померить сразу.
8. **Алерты дашборда** отложить до автоматизации выгрузки gist (отдельный
   `tech`-тикет на GitHub Action/cron)? Сейчас они будут лгать на ручных данных.
