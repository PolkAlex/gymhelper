# AGENTS.md — правила проекта MyHelper (GymHelper)

Telegram-бот дневника тренировок. Backend: чистая **Java 17 без внешних зависимостей** (`src/gym/`).
Frontend: Telegram Mini App — ванильный JS/HTML/CSS (`web/`), без сборки и npm-пакетов.
Тесты: Playwright e2e + контрактный тест на Java. Подробности — `README.md`.
Заметки владельца — `TODO.md` (проверять в начале любой задачи).

## Структура

```
src/gym/*.java             — бот (Main, BotLogic, TelegramApi, Json, GymData, Storage, ...)
src/gym/web/WebServer.java — HTTP-сервер Mini App (порт 8080)
web/                       — фронтенд Mini App (app.js, catalog.js, style.css, index.html)
tests/                     — e2e.spec.js (Playwright), GymContractTest.java, check.js, server-test.js
.github/                   — CI-воркфлоу, шаблоны issue/PR
docs/                      — спецификации и макеты дизайнера, карта покрытия тестами
data/                      — данные пользователей (JSON на чат) — НЕ коммитить
build.gradle, gradlew      — сборка Gradle (код остаётся чистой Java без зависимостей)
Dockerfile, docker-compose.yml — контейнер для VPS (deploys вручную, systemd ещё жив)
```

Порядок: Inbox → Backlog → Todo → (In Design) → In Dev → Code Review → In Test → Ready To Deploy → Done

красный → обратно In Dev.

**Статусы по типам тикетов** (правила движения):
- **Idea**: Inbox (сырая) → Backlog (проработана/оформлена) → при взятии в работу потомки
  едут по конвейеру; Idea не покидает Backlog, пока потомки не Done
- **Epic**: Backlog → Todo → In Dev → Done (статус = состояние детей; Design/Test-статусы не используются)
- **Story**: Backlog → Todo → In Dev → Done (аналогично — состояние её Task'ов)
- **Task/Bug**: полный конвейер (Inbox не используется — это только для Idea)

### Технические грабли (gh + PowerShell) — НЕ НАСТУПАТЬ

1. **Инлайн-кавычки в длинных командах**: bash-слой съедает `"` внутри PowerShell-строк
   → GraphQL-мутации НЕ собирать инлайном-конкатенацией. Пиши mutation в JSON-файл
   (Write tool, с реальными значениями сразу) и запускай `gh api graphql --input файл`.
2. **PS 5.1 кодировки**: `.ps1`/файлы с кириллицей — только UTF-8 **С BOM** (WriteAllText
   с UTF8Encoding($true)); Set-Content/Get-Content без `-Encoding` перекодируют UTF-8
   в ANSI (mojibake). Продуктовые файлы (web/, src/) править только Write/Edit tool,
   после правки — Read-проверка кириллицы.
3. **Плейсхолдеры-замены**: не гоняй цепочки Replace поверх изменённых файлов — сначала
   получи все значения (выведи/прочитай), затем ОДИН Write файла с готовым содержимым,
   перед запуском — Read-проверка.
4. **`$pid` и прочие автоматические переменные** — readonly, не использовать как имена.
5. **`--jq` надёжнее инлайна** для извлечения значений из gh api вывода; лимитированные
   поля: `gh api ... --jq '.data.r.iNN.id'` — работает стабильно.
6. **gh project item-delete** требует: `gh project item-delete 1 --owner PolkAlex --id <ITEM_ID>`.

### Коды тикетов в заголовках

GitHub не поддерживает Jira-нумерацию (номера issue сквозные и неизменяемы), поэтому семья
обозначается кодом в заголовке: `[MON-E1] Монетизация: ...`. Формат: `[ABC-XN] Название`,
где `ABC` — код направления (таблица выше), `X` — буква типа тикета (`I`=Idea, `E`=Epic,
`S`=Story, `T`=Task, `B`=Bug), `N` — порядковый номер тикета **этого типа** внутри
направления. Примеры: `[DSN-I1]` — первая Idea направления Дизайн, `[MON-E1]` — первый
Epic направления Монетизация, `[MON-T3]` — третий Task. Код и номер ставит lead при
создании тикета; при смене направления заголовок обновляется. Новому направлению
присваивается новый 3-буквенный код.

Idea — постоянный контейнер: тикет навсегда остаётся Тип=Idea и не «вызревает». При взятии
в работу под ней заводятся потомки (Epic/Story/Task) как sub-issues. Связь потомка с
родителем — поле Parent issue (нативный GitHub), на доске виден Sub-issues progress.
По конвейеру едут только потомки; Idea-тикет живёт в Backlog, пока все её потомки не
дойдут до Done, после чего закрывается.

### Процесс работы (договорённости)

1. Когда владелец говорит «идея»: lead продумывает идею; при необходимости задаёт владельцу
   уточняющие вопросы и/или привлекает агента design для проработки (design тоже может
   задавать вопросы владельцу). По итогам обсуждения заводится issue + item на доске
   (Тип=Idea, статус Backlog). Код по идее не пишется до взятия в работу.
2. Когда идею берут в работу: Idea-тикет остаётся собой (Тип=Idea). Lead уточняет детали
   и заводит под неё потомков (Epic/Story/Task) как sub-issues; потомки идут в Todo и далее
   по конвейеру.
3. Тикет с меткой `need_design` идёт через In Design (даже Bug — бывают баги по дизайну);
   остальные — сразу In Dev.
4. Статусы на доске двигает lead в момент передачи работы следующему агенту.
5. Блокер ревью/тестов возвращает задачу в In Dev.
6. Релиз = Milestone. Релиз проводим, когда ВСЕ тикеты milestone в статусе Ready To Deploy.
7. Деплой на прод делает владелец вручную; после его подтверждения lead переводит тикеты
   в Done и закрывает issues (`gh issue close N --comment "что сделано"`).
   ⚠️ ЖЕЛЕЗНОЕ ПРАВИЛО: без явной отмашки владельца («тест пройден / едем») на прод НЕ
   едем — ни lead, ни агентам, ни скриптами. Нарушение — критический инцидент.
   Автоматического деплоя в проекте нет и появляться не должно.
8. Владелец может лично тестировать тикет на этапе In Test: lead передаёт ему инструкцию
   по проверке; тикет ждёт его отмашки («тест пройден») перед переходом в Ready To Deploy.
9. Счётчик багов владельца: lead считает баги, которые владелец находит в работе агентов
   и приносит в чат. При достижении 3 багов владелец проводит полную перепроверку
   недавней работы, после чего счётчик сбрасывается. Текущее значение: **0/3** (обновляет lead).
10. Статусы родителей синхронно с детьми: когда ВСЕ дети (Task'ы Story / Story'и Epic)
   в одном статусе — родитель переводится lead'ом в тот же статус; если хоть один ребёнок
   в предыдущем статусе — родитель остаётся в своём текущем. Lead проверяет это при
   каждом движении тикета.
11. Вместимость: за один релиз/спринт — ОДИН эпик или ДВА мелких тикета. Больше не брать:
   тяжёлый релиз Релизов 1.6+1.7 (два эпика параллельно) дал много багов по обоим — учимся.
12. **Todo = только то, что взято в текущий спринт.** Всё остальное живёт в Backlog
   (двигать в Todo без включения в спринт нельзя). В конце спринта незавершённое
   возвращается в Backlog.
13. **Тайминги перед стартом**: перед каждой итерацией/задачей lead сообщает владельцу
   оценку времени (сколько занимает работа агентов и когда понадобится владелец) —
   владелец решает, когда давать старт (может быть не за компьютером).
14. **Спринт проставляется на все тикеты семьи** — включая Epic и Idea-контейнер,
    а не только исполнительные Story/Task (GitHub не наследует итерацию от детей).
15. **Спринт закрывается строго по дате** (правило владельца, 06.11.2026): длится ровно
    14 дней и НЕ закрывается раньше — даже если все его тикеты уже Done; досрочное
    закрытие или продление — только явное решение владельца. «Все тикеты Done» = спринт
    выполнен по содержанию, но окно спринта продолжает действовать: тикеты, взятые
    в работу до даты закрытия, получают текущий спринт (см. п.14 и правило
    обязательного поля «Спринт»). Релизы (Milestone, п.6) — отдельная механика,
    к закрытию спринта не привязаны.

## Конвенции

- Java 17, **никаких внешних зависимостей в коде** (Gradle — только инструмент сборки,
  никаких Maven-зависимостей в build.gradle)
- `web/` — ванильный JS/CSS/HTML: без фреймворков, сборщиков и новых npm-пакетов
- Формат данных `data/*.json` (класс `GymData`) — **обратная совместимость обязательна**:
  старые файлы без новых полей должны читаться (эталон — `GymContractTest`)
- Все тексты интерфейса — на русском
- Стиль кода — как в соседних файлах; минимальные диффы, рефакторинг без просьбы не делать
