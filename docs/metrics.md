# Метрики качества — определения и порядок сводок

Правило владельца от 07.11.2026 (AGENTS.md п.17). Единственный источник данных —
журнал переходов `docs/metrics-log.md`: GitHub Projects не хранит историю изменений
статусов item'ов, поэтому lead обязан записывать каждый переход тикета по статусам
(дата, тикет, из → в) в журнал в момент перевода.

Точность — календарные дни (время не фиксируется), поэтому все метрики времени
считаются в днях с точностью ±1.

## Метрики

### 1. Throughput (пропускная способность)
Число тикетов, достигших **Done**, за период. Считаем по типам-исполнителям
(Task, Bug) и отдельно по Story/Epic. Идея-контейнеры не считаются (они закрываются
один раз за всю жизнь семьи).

Сводки: за спринт, месяц, квартал, год.

### 2. Velocity (скорость команды)
Сумма **Story Points эпиков**, достигших Done за спринт. SP есть только у эпиков
(Story/Task не оцениваются) — velocity считается по спринтам (и их суммами за
месяц/квартал/год). Эпик, не доведённый до Done, не засчитывается, даже если его
задачи в RtD (полу-очки не даём).

### 3. Returns (возвраты)
Число переходов `Code Review → In Dev`, `In Test → In Dev` и `Ready To Deploy → In Dev`
(проверка вернула тикет в работу). По каждому возврату в журнале должна быть причина
(блокер ревью / красный тест / дефект на ручной проверке).

Производная метрика:
- **First-Pass CR Rate** — доля тикетов-исполнителей (Task/Bug), прошедших Code Review
  без единого возврата, от всех прошедших Code Review за период. Цель — к 100%.

### 4. Cycle Time (CT)
Календарные дни от **первого входа тикета в In Dev** до **входа в Ready To Deploy**.
Включает весь конвейер после начала кода (Code Review, In Test); работа до In Dev
(In Design) в CT не входит — она считается отдельно, если понадобится.

Считается по тикетам-исполнителям (Task/Bug). Агрегация — по сложности:

| SP эпика | Категория |
|---|---|
| 1–2 | S (малый) |
| 3 | M (средний) |
| 5 | L (крупный) |
| 8+ | XL |

Для каждой категории за период: медиана и среднее CT. Отчёт: «CT(M) за спринт N =
медиана 2 дн, среднее 2.3 дн (2 тикета)».

### 5. Escaped Defects (утечка дефектов)
Баги, найденные **после** перехода тикета в Ready To Deploy/Done: владельцем на ручной
проверке после отмашки, или пользователями на проде. Учитываются тикеты типа Bug с
указанием, дефект какой фичи это следствие. Сводки за месяц/квартал/год. Связан со
счётчиком багов владельца (AGENTS.md п.9: 3 бага → полная перепроверка).

### 6. WIP (незавершённая работа)
Снимок на конец спринта: сколько тикетов находятся в In Dev / Code Review / In Test.
Против перегруза (урок Релизов 1.6+1.7: два эпика параллельно → баги в обоих).
Цель — WIP, соответствующий заявленной вместимости спринта.

## Порядок сводок

| Период | Когда | Что |
|---|---|---|
| Спринт | в течение 2 дней после истечения 14 дней окна | Throughput, Velocity, Returns, CT по категориям, WIP-снимок |
| Месяц | первые 3 дня следующего месяца | те же за календарный месяц |
| Квартал | первые 5 дней квартала | те же за квартал |
| Год | первые 7 дней января | те же за год + динамика по спринтам |

Сводки дописываются в `docs/metrics-log.md` отдельными разделами; в конце строки
«Сводка» всегда ссылка на период (например, «Сводка S1 (04.11–18.11.2026)»).

## Дашборд (Grafana Cloud, бесплатный tier) — правило владельца от 07.11.2026

Схема данных:

```
docs/metrics-log.md  →  tools/metrics-to-json.mjs  →  metrics.json  →  secret gist  →  Grafana Cloud (Infinity)  →  дашборд
   (ручной журнал)        (node, без зависимостей)      (JSON)        (публичный raw-URL)      (читает URL)          (графики)
```

Компоненты:
- **Генератор**: `tools/metrics-to-json.mjs` — парсит из журнала «Реестр тикетов», «Журнал
  переходов», «WIP-снимки», «Escaped defects» и заголовки спринтов; сам считает velocity,
  throughput, возвраты, CT по категориям SP.
- **Хранилище**: secret gist `4de075a074c4e6fcf1dfce3b43361e5c` (без секретов — только
  метрики; удалить можно в любой момент). Raw-URL читается анонимно.
- **Дашборд**: `docs/grafana-dashboard.json` (импорт в Grafana; uid `gymhelper-metrics`,
  8 панелей: Velocity, Throughput, Escaped, возвраты, WIP, CT по SP, реестр, журнал).

Обновление данных (после каждого изменения журнала):

```powershell
node tools/metrics-to-json.mjs
& "C:\Program Files\GitHub CLI\gh.exe" gist edit 4de075a074c4e6fcf1dfce3b43361e5c --filename metrics.json "$env:TEMP\opencode\metrics.json"
```

Первичная настройка Grafana Cloud (владелец, ~5 минут):
1. Регистрация на grafana.com → **Grafana Cloud Free** (3 юзера, без карты).
2. В стеке: Connections → Data sources → Add → **Infinity** (есть в каталоге Cloud) → Save.
3. Dashboards → Import → загрузить `docs/grafana-dashboard.json` → на шаге импорта
   выбрать Infinity в качестве datasource → Import.
4. Готово: дашборд «GymHelper — метрики качества» читает gist, автообновление 5 мин.
   Если панель пуста — открыть панель, проверить datasource и root_selector.

## ANA-дашборд — продуктовые агрегаты /stats [ANA-T2]

Отдельный gist для продуктовых счётчиков ([ANA-T1] `/stats`: maInit/maSave, workouts*,
templates*, feedbackSent — только агрегаты, без ПДн). Схема:

```
data/stats.json (или GET /stats?token=)  →  tools/ana-to-gist.mjs  →  ana-stats.json  →  secret gist  →  Grafana Cloud (Infinity)
   (env GYM_STATS_URL + GYM_ADMIN_TOKEN        (node 18+, без зависимостей; (компактный      (raw-URL         (подключает
    или локальный файл)                         выгрузка ниже)               JSON)            анонимно)         владелец, веб-UI)
```

Формат ana-stats.json: `{generatedAt, source, totals: {7 счётчиков}, weeks: [{week: "2026-W46",
maInit, …}]}` — weeks массив по возрастанию ISO-недели.

Требуется Node 18+ ([ANA-T3]: глобальный fetch и AbortSignal.timeout — полифиллов нет).

Выгрузка (локально, после каждого «посмотреть цифры» / перед обзором спринта):

```powershell
# источник: заданы env GYM_STATS_URL+GYM_ADMIN_TOKEN → /stats с прода;
# иначе локальный файл (env GYM_STATS_FILE или 1-й аргумент — путь, по умолчанию data/stats.json)
node tools/ana-to-gist.mjs
& "C:\Program Files\GitHub CLI\gh.exe" gist edit <GIST_ID> --filename ana-stats.json "$env:TEMP\opencode\ana-stats.json"
```

**GIST_ID: <вписать после создания>**, raw-URL: `https://gist.githubusercontent.com/PolkAlex/<GIST_ID>/raw/ana-stats.json`

Одноразовое создание (владелец; скрипт гист сам не создаёт и токены не печатает):
1. `node tools/ana-to-gist.mjs` → `%TEMP%\opencode\ana-stats.json`
2. `gh gist create --secret --desc "GymHelper ANA stats (Grafana Infinity)" "$env:TEMP\opencode\ana-stats.json"`
3. Полученный gist id вписать в этот раздел (GIST_ID выше).

Настройка Infinity datasource (владелец, веб; отдельный datasource или тот же — URL другой):
- Type: **JSON**; URL: raw-URL из этого раздела; Format: JSON.
- root_selector: для totals-панелей — `totals`; для недельных — `weeks` (подбирается по
  структуре: totals — плоский объект из 7 счётчиков, weeks — массив объектов с полем `week`).

Пример панели «Открытия Mini App по неделям»: визуализация **timeseries**, datasource —
Infinity (URL выше), root_selector `weeks`, X = `week`, Y = `maInit` (аналогично maSave,
workoutsCreated/Completed — по одной панели на счётчик).

## Ограничения

- История до 06.11.2026 не восстановима (доска не хранит переходы) — метрики считаются
  с Спринта 1 (старт 04.11.2026).
- Ручной журнал = человеческий фактор: lead должен писать строку в момент перевода.
  Если переходы batch (несколько тикетов сразу) — допустима одна строка со списком тикетов.
