## 1. Цель и проблема

Желание владельца: **«ккал считается упрощённо и не учитывает, КАК пользователь
поднимает/тянет вес»**. Сейчас калории зависят только от тоннажа в минуту на уровне
всей тренировки: присед со штангой и махи гантелями дают одинаковый MET, если кг/мин
совпали. Пользователь не видит, откуда взялось число, и не может ему доверять.

**Ключевой факт (упрощает задачу):** в каталоге [EXR-T3] у каждой из 243 записей уже
есть поле `met:` (`web/catalog.js`: жим лёжа 3.5, присед 6.0, становая 5.0, скакалка 8.0,
растяжка 2.3–2.5, кардио-разминка 3.0) — оно даже показывается бейджем «MET 3.5» в
Технике (`web/app.js:2116`), но **калькулятором не используется**. Фундамент готов:
фича — это «подключить существующие данные к формуле + показать их пользователю».

**Решение в одном абзаце:** расчёт переходит с тренировочного уровня на **уровень
упражнения**: `ккал_упр = MET_упр × 3.5 × вес ÷ 200 × минуты_упр`, где MET берётся из
каталога (для «Своих» — по выбранному типу, по умолчанию умеренный 3.3), минуты — из
реальных окон упражнения (`st`/`en`, есть в обеих моделях данных). Итог = сумма по
упражнениям. Прозрачность: экран «Как считаются калории» (из FAQ) с формулой, входами и
разбором последней тренировки; разбор по упражнениям в карточке (вместо текстового
черновика «(в разработке)»).

## 2. Текущая формула (зафиксировано из кода)

### 2.1. Mini App — `calcWorkoutKcal` (`web/app.js:422–451`)

```
объём_тр = Σ по упражнениям Σ по сетам (средний_вес × подходы × средние_повторы)
мин_тр   = min(длительность, 240)
кг/мин   = объём_тр / max(мин_тр, 1)
MET_тр   = кг/мин < 120 → 3.5; 120…300 → 5.0; > 300 → 6.0   // одна на всю тренировку
ккал_тр  = round(MET_тр × 3.5 × вес_кг ÷ 200 × мин_тр)
разбор   = доля упражнения в объёме × ккал_тр   // делёжка одного числа, не расчёт
```

### 2.2. Бот — `calcKcal` (`src/gym/BotLogic.java:2422–2431`)

Та же формула: `calcMin = min(мин, KCAL_MAX_MIN=240)` (константа — `BotLogic.java:31`),
`vol = workoutVolume(w)` (строки 2440–2448, вес сетов — максимальный из диапазона),
пороги кг/мин 120/300 → MET 3.5/5.0/6.0, `round(MET × 3.5 × вес ÷ 200 × calcMin)`.
Экран «🔥 Расчёт калорий» (`BotLogic.java:2175–2215`) показывает: длительность (с
пометкой про кэп 240), объём ≈ кг и кг/мин, интенсивность (низкая/средняя/высокая),
MET, вес из профиля, текст формулы, итог. Нет длительности или веса → предупреждение.

### 2.3. Что модель не учитывает (суть претензии владельца)

| Не учитывается | Следствие |
|---|---|
| Тип/механика упражнения | Присед (реально ~6 MET) и изоляция (~3 MET) могут дать одинаковый MET: всё решает кг/мин |
| Упражнения без веса | Тело-упражнения и кардио почти не добавляют объёма → тонут в общем кг/мин и занижают MET всей тренировки |
| Паузы внутри минут | Считается всё окно тренировки: долгий отдых раздувает минуты, кг/мин падает → MET занижен (и наоборот) |
| Поля `met` каталога | 243 значения уже в проде — простаивают |
| Понятность | «(в разработке)» в развороте ккал карточки (`web/app.js:1676`); разбор — пропорциональный делёж одного числа, а не расчёт по упражнению |

Попутное расхождение (не чиним этой спекой, фиксируем): объём в JS использует
средний вес диапазона (`avgNum`), в Java — максимальный (`maxWeight`): тренировка с
вводом «50-60» даст разные кг/мин в приложении и боте. Новая формула от объёма
не зависит — расхождение уходит само.

### 2.4. Важное следствие: ккал нигде не хранится

Оба расчётчика вызываются на лету при рендере (пилюли карточек `app.js:1396,1633`,
разбор `app.js:1841`, прогресс `app.js:1865`, бот `BotLogic.java:2210,2238`). В
`data/*.json` ккал не пишутся. Значит **смена формулы автоматически «пересчитывает»
всю историю** — миграция данных не нужна и хранить нечего (см. §8 и вопрос 1).

## 3. Новая формула: MET по упражнению

### 3.1. Вид

```
ккал_упр = MET_упр × 3.5 × вес_кг ÷ 200 × мин_упр        (для каждого упражнения с сетами)
ккал_тр  = Σ ккал_упр
```

Форма — та же, что сегодня (и как в README §Калории): меняется источник MET и
единица времени (упражнение вместо тренировки). `3.5 × кг ÷ 200` — перевод MET в
ккал/мин (стандарт ACSM/Compendium), для веса 78 кг это 4.78 ккал/мин на 3.5 MET.

### 3.2. Источник MET — приоритеты

1. **Каталог** (`met` записи) — источник истины для 243 упражнений. Уже есть, показан
   пользователю в Технике — данные и интерфейс уже согласованы.
2. **Тип «Своего»** — пресет MET по выбранному типу (§5).
3. **Дефолт** — 3.3 MET («умеренная изоляция») для «Своих» без типа.

### 3.3. Минуты упражнения

Источник: реальные окна `ExerciseEntry.startedAt/endedAt` (`st`/`en`) — парсятся и в
Java (`GymData.java:119–120,232–233`), и в JS (`exMinutes`, `app.js:401–406`).
Порядок: `мин_упр = en − st` (минимум 1 мин), `en` незакрытого активного упражнения =
«сейчас» (как сегодня для тренировки). Fallback при кривых данных (нет `st`, `en ≤ st`,
окно вне окна тренировки из-за ручных правок времени) — распределение по долям
подходов, как в текущем разборе (`app.js:445`): детерминированно и одинаково на обоих
клиентах. Если сумма минут упражнений превысила длительность тренировки (правки рукам)
— пропорционально ужать до длительности. Кэп 240 мин сохраняется на уровне тренировки
(применяется к сумме до масштабирования).

Паузы между упражнениями больше не «съедают» ккал — минуты принадлежат упражнениям.
Для тела-упражнений и кардио (объём ≈ 0) ккал впервые считаются нормально.

### 3.4. Компаунд vs изоляция: классификация по тегам

Калькулятору различие **не нужно** — у него есть готовый `met` записи. Классификация
нужна человеку: выбор типа «Своего» (§5), таблица на экране прозрачности (§7),
валидация каталога. Предлагаемая схема (без нового флага в данных):

| Тип | Признак по тегам | Примеры каталога | MET диапазон |
|---|---|---|---|
| **Компаунд · низ** | `m:legs` или `m:glutes` (+ `m:` вторая группа или штанга/тренажёр) | присед 6.0, становая 5.0, румынская 5.0, жим ногами 5.0, гакк 5.0, выпады 4.3 | 4.3–6.0 |
| **Компаунд · верх** | ≥2 разных `m:` либо жим/тяга свободным весом | жим лёжа/в наклоне 3.5, тяги 3.5, ОНП 4.3, подтягивания/брусья/отжимания 3.8 | 3.5–4.3 |
| **Изоляция** | ровно одна `m:` и блочный/гантельный инвентарь | махи 3.3, сгибания/разгибания 3.3, кроссовер 3.3, гиперэкстензия 3.0 | 3.0–3.3 |
| **Пресс и кор** | `m:core` | планка 3.3, скручивания/вис/ролик 3.8 | 3.3–3.8 |
| **Кардио** | `cat:cardio` | вел/эллипс 5.0, дорожка 7.0, скакалка/берпи 8.0 | 5.0–8.0 |
| **Растяжка** | `cat:stretch` / `cat:stretching` / `cat:cooldown` | 2.3–2.5 | 2.3–2.5 |
| **Разминка/заминка** | `cat:warmup` | кардио-разминка 3.0, присед без веса 3.8 (гибрид) | 2.5–3.8 |

Правило `≥2 разных m: → компаунд` неточно (жим лёжа — компаунд с одним `m:chest`),
поэтому таблица выше — **справочник для людей и валидации**, не runtime-логика.
Явный флаг `cp:1` в каталоге **не заводим**: поле `met` уже несёт итоговое значение,
а тип нужен только как подпись в UI и пресет для «Своих». Если при ревизии каталога
понадобится машинная проверка «met соответствует типу» — это `tests/check.js`
(контракт диапазонов из таблицы), без изменения формата записей.

### 3.5. Ревизия чисел каталога

Текущие значения в целом совпадают с Compendium of Physical Activities (открытый
справочник): силовая умеренная ~3.5, тяжёлые базы 5.0–6.0, растяжка 2.3–2.5.
Отклонения к пересмотру в MVP: **скакалка** 8.0 (справочник даёт 10–12 — оставляем
8.0 как консервативную оценку среднего темпа, пометить в коде), **берпи** 8.0 ок,
**дорожка** 7.0 (справочник 8.0–9.8 для бега 8–10 км/ч; 7.0 ≈ быстрая ходьба/лёгкий
бег — ок для названия «Беговая дорожка» без темпа). Ревизия — точечные правки
значений `met`, контракт-тест диапазонами (§3.4) не даёт уехать.

## 4. Сценарии использования

### Сценарий A — «Откуда это число?» (главный)
1. Пользователь завершил тренировку; на карточке пилюля «🔥 255 ккал».
2. Разворачивает «🔥 Ккал по упражнениям» → видит строки: упражнение, MET, минуты, ккал, итог.
3. Хочет понять механику → «Почему так?» (ссылка в развороте) → экран «Как считаются калории»:
   формула, три входа, таблица MET, разбор последней тренировки на его данных.
4. Либо из «Помощи»: FAQ «Как считаются калории?» → ответ + кнопка «Показать на моих данных».

### Сценарий B — добавил «Своё» упражнение
1. «➕ Добавить упражнение» → «✍️ Своё упражнение» → название.
2. Новый шаг: чипы типа (Компаунд / Изоляция / Кардио / Растяжка / Разминка).
3. Подсказка под чипами: «Посчитаем как 5.0 MET» — меняется при выборе.
4. «➕ Добавить» → упражнение в тренировке, ккал считается по выбранному типу.

### Сценарий C — «Свои», добавленные раньше (без типа)
1. В тренировке старое «Своё» → ккал по дефолту 3.3 MET.
2. В списке «Своё» у записи появляется подпись «3.3 MET · умеренное» — тап → смена типа (§5.4).

### Сценарий D — нет профиля
1. Пилюли ккал нет (как сегодня), разворот ккал показывает подсказку.
2. На экране прозрачности — «Задайте вес в Профиле» + кнопка перехода; формула и таблица видны.

### Сценарий E — бот
1. «🔥 Расчёт калорий» → тот же разбор списком (MET по упражнениям) вместо кг/мин-интенсивности.
2. «📈 Прогресс» → сравнение ккал по новой формуле; числа прошлых тренировок могли измениться (§8).

## 5. Кастомные («Свои») упражнения

Сегодня «Свои» — список имён в localStorage `gymCustomEx` (`web/app.js:2906–2914`),
без тегов и типа; TODO на выбор категории уже стоит (`app.js:1968–1970`). В этой
фиче — минимальное расширение **только для ккал**: тип → MET. Полноценные
теги/фильтры для «Своих» — НЕ здесь (§10).

### 5.1. Выбор типа при добавлении

В модалку «✍️ Своё упражнение» под полем названия добавляется ряд чипов:
`Компаунд · Изоляция · Кардио · Растяжка · Разминка` (мультивыбор не нужен — MET один).
По умолчанию выбрана «Изоляция» — самый частый случай «того, чего нет в базе».

### 5.2. Пресеты MET по типу (фиксированные, без под-выбора)

| Чип | MET | Текст подсказки |
|---|---|---|
| Компаунд | 5.0 | «базовые движения: присед, тяга, жим стоя» |
| Изоляция | 3.3 | «сведение/сгибание/разгибание, махи» |
| Кардио | 6.0 | «ходьба, бег, велотренажёр, скакалка» |
| Растяжка | 2.5 | «стретчинг, заминка» |
| Разминка | 3.0 | «лёгкая работа до тренировки» |

Под-выбор конкретного MET внутри типа (например, вел 5.0 vs скакалка 8.0) отсечён:
для «Своего» пользователь выбирает характер движения, точность и так ±20%.

### 5.3. Хранение типа

Рекомендация: **`GymData.customEx: [{n, met}]`** (синхронизируется между устройствами,
ккал сходится на телефоне и в боте; `n` — имя). Обратная совместимость обязательна:
файлы без поля → «Своих»-метаданных нет, все дефолт 3.3 (`GymContractTest` + новый
кейс). Вариант «расширить localStorage» отсечён: тип не переедет на другое устройство,
а ккал-числа разъедутся. localStorage-список имён остаётся как есть (не дублируем).

> Если владелец не хочет трогать контракт данных в этой фиче — fallback: тип в
> localStorage `{n, ty}` (быстрее, но устройства расходятся). Вопрос 6.

### 5.4. Существующие «Свои» без типа

Ничего не спрашиваем принудительно: расчёт по дефолту 3.3. Мягкий вход к заданию
типа — подпись «3.3 MET · умеренное» у записи в списке «Своё» и в развороте ккал
(строки «Своих» помечены «тип не задан»); тап по подписи → тот же выбор типа.
Разовых всплывашек/туров не делаем.

### 5.5. Бот и «Свои»

Бот не умеет создавать «Свои» (это фича Mini App), но читает `customEx` из GymData —
ккал «Своих» в боте считается по сохранённому типу; без метаданных — дефолт 3.3.

## 6. Прозрачность — экран «Как считаются калории»

### 6.1. Входные точки

1. FAQ «Как считаются калории?» — в конце ответа кнопка «Показать на моих данных».
2. Разворот «🔥 Ккал по упражнениям» в карточке — строка-ссылка «Почему так?».
Экран — раздел внутри «Помощи» (без нового таба; назад → туда, откуда пришли).

### 6.2. Состав экрана (сверху вниз)

1. **Формула** — крупно: `ккал = MET × 3.5 × вес ÷ 200 × минуты`.
2. **Три входа** — чипы/строки: «Вес — 78 кг, из Профиля» · «MET — по типу упражнения» ·
   «Минуты — время каждого упражнения». Клик по «весу» → Профиль.
3. **«На Ваших данных»** — разбор последней завершённой тренировки (те же строки, что
   в развороте карточки) + ссылка «Открыть тренировку».
4. **Таблица MET** — 7 строк из §3.4 (тип, примеры, диапазон) — «почему присед жжёт
   больше, чем махи».
5. **Дисклеймер** — «≈ оценка: реальный расход зависит от темпа, пауз и техники.
   Точность ±20%. Для дневника и сравнения тренировок — достаточно».

### 6.3. Состояния

| Состояние | Что видит пользователь |
|---|---|
| Норма (профиль + тренировки) | Полный экран с примером на последней тренировке |
| Нет профиля | Формула и таблица видны; блок примера → «Задайте вес в Профиле — он нужен для расчёта» + кнопка «Перейти в Профиль» |
| Нет завершённых тренировок | Вместо разбора — пример на «типовой» тренировке с пометкой «пример, не Ваши данные» (вес — из профиля или 75 кг) |
| Загрузка / ошибка | Расчёт локальный и мгновенный — состояний нет; пустые данные покрыты выше |

### 6.4. FAQ-ответ (новый текст, `FAQ_ITEMS[3]`)

> **Как считаются калории?**
> ккал = MET × 3.5 × Ваш вес ÷ 200 × минуты. MET — интенсивность типа упражнения:
> присед 6.0, жим лёжа 3.5, растяжка 2.5. Вес берётся из Профиля, минуты — из времени
> каждого упражнения. Разбор Вашей тренировки — кнопка ниже.

## 7. Breakdown в карточке тренировки

Вместо текстового `<details>🔥 Ккал по упражнениям (в разработке)</details>`
(`app.js:1676`) и `kcalBreakdown`-строки (`app.js:1838–1854`):

- Summary: `🔥 255 ккал · по упражнениям` (без «в разработке»).
- Строки: имя + бейдж `6.0 MET` + `15 мин` → справа `≈ 123 ккал`; «Свои» без типа —
  бейдж `3.3 MET?` и подпись «тип не задан» (тап → задать тип).
- Итог: `🔥 Итого ≈ 255 ккал` + ссылка «Почему так?» → экран §6.
- Пилюля карточки и «📈 Прогресс» не меняются (числа пересчитаются сами).

Макет: `docs/mockups/fit-calories.html`, экраны A/E.

## 8. Пересмотр чисел: старые тренировки

**Рекомендация: пересчитывать всё, хранить снимки не нужно.**

- Ккал — производное отображение, не данные пользователя (§2.4): в JSON их нет,
  пересчёт происходит сам при рендере — «миграция» бесплатна и неизбежна.
- История чисел не является обещанием продукта: нигде не показывается «ккал на момент
  завершения»; «📈 Прогресс» сравнивает соседние тренировки — обе считаются одной
  формулой, сравнение остаётся честным.
- Хранение снимка ккал при завершении (стабильная история) — против: новая колонка в
  JSON + контракт, двойной источник истины (снимок или свежий расчёт?), старые файлы
  всё равно считаются на лету → выигрыша нет.

Побочный эффект: числа в истории могут измениться (пример: тренировка из макета —
было ≈310 по кг/мин-модели, станет ≈255 по минутам упражнений). Это и есть цель
фичи — честнее; отмечаем в «Что нового» релиза (вопрос 1 — подтверждение владельца).

## 9. Бот: тексты и клавиатуры

Голос бота — «ты» (весь `BotLogic`); новые тексты ниже в голосе бота, чтобы не
смешивать обращение в одном экране. (Mini App — «Вы», как принято в `web/`. Если
владелец хочет унификацию «Вы» в боте — отдельная мелкая задача, не эта.)

### 9.1. Экран «🔥 Расчёт калорий» (замена `BotLogic.java:2175–2215`)

```
🔥 Расчёт калорий

⏱ Длительность: 1ч 5м
🏋️ Объём: ≈6 760 кг
Вес: 78 кг (из профиля)
Формула: MET × 3.5 × вес ÷ 200 × минуты

По упражнениям:
• Приседания со штангой — 15 мин, 6.0 MET ≈ 123 ккал
• Жим штанги лёжа — 12 мин, 3.5 MET ≈ 57 ккал
• Тяга верхнего блока — 10 мин, 3.5 MET ≈ 48 ккал
• Растяжка квадрицепса — 8 мин, 2.5 MET ≈ 27 ккал

🔥 Итого: ≈255 ккал
```

Правила: длительность > 240 мин → строка «(в расчёте учтено 240 мин)» как сегодня;
минуты упражнения неизвестны → строка без минут (только MET и ккал по фолбэку
долей подходов); «Своё» без типа → MET 3.3 с пометкой «(умеренное)»; нет профиля →
текущий warning-блок с кнопкой «⚙️ Профиль» сохраняется; нет длительности → текущий
текст про «⏱ Время» сохраняется.

### 9.2. Клавиатуры (без изменений)

| Экран | Кнопки |
|---|---|
| «🔥 Расчёт калорий», есть профиль | `↩️ Назад` → `scr_<id>` |
| Нет профиля | `⚙️ Профиль` → `pr`; `↩️ Назад` → `scr_<id>` |
| Нет времени начала | `↩️ Назад` → `scr_<id>` (текст просит «⏱ Время») |

### 9.3. «📈 Прогресс» и тексты завершения

`🔥 Ккал: 255 → 310 (+55)` — формула та же, формат строк не меняется
(`BotLogic.java:2238–2245`). Разбор по упражнениям в прогрессе бота не добавляем —
он есть по кнопке «🔥 Расчёт калорий».

### 9.4. Паритет формул Java ↔ JS (требование к кодеру)

Java не имеет каталога. Предлагается сгенерированный класс `src/gym/ExMet.java`
(компактная карта id → MET из `web/catalog.js`; генератор — скрипт/шаг сборки),
+ контракт в `tests/check.js`: значения в Java-карте = значениям каталога 1-в-1.
Без паритета числа бота и приложения разойдутся — неприемлемо для одной записи
дневника. Альтернатива «бот считает по-старому» отсечена (§10).

## 10. Что НЕ делаем и почему

| Не делаем | Почему |
|---|---|
| Пульсометры, HR-формулы, интеграции с часами | Внешние зависимости и датчики — против стека (ванильный JS, Java без библиотек); MET-оценка закрывает дневник |

| Пользовательская правка MET-таблицы | Overengineering; ±20% дисклеймер честнее настроек |

## 11. Вопросы владельцу

1. **Пересчёт истории.** Ккал нигде не хранятся — новая формула автоматически меняет
   числа за все прошлые тренировки (пример §8: 310 → 255). Подтверждаешь? (Хранение
   снимков на момент завершения спекой отсечено, но решение за тобой.)
2. **MET каталога — источник истины.** У всех 243 записей поле `met` уже есть и
   показано в Технике; берём его в расчёт + точечная ревизия по Compendium (скакалка
   оставляем 8.0 против справочных 10–12 — консервативно). Ок?
3. **Тип «Своего» — обязателен?** Предлагаю необязательный шаг: дефолт «Изоляция»
   (3.3 MET) прямо выбран в модалке, подсказка показывает MET. Или сделать выбор
   обязательным (без дефолта, пока не выбрано — кнопка «Добавить» неактивна)?
4. **Старые «Свои» без типа.** Просто дефолт 3.3 + мягкая подпись «тип не задан»
   (§5.4)? Или нужна разовая подсказка-баннер «задайте тип своим упражнениям»?
5. **Хранение типа.** В GymData (синхронизация бот/устройства, апдейт контракта
   `GymContractTest`) или в localStorage (быстрее, но числа разъедутся между
   устройствами)? Рекомендация — GymData.
6. **Экран прозрачности для всех.** Формула и таблица MET открываются из FAQ и
   карточки без скрытий; дисклеймер ±20% размещён на экране. Достаточно, или
   показать формулу ещё и в самой пилюле/развороте карточки?
7. **Связь с [GOA-I1] (цели).** Заводить ли на экране прозрачности «цель по ккал за
   тренировку/день» (прогресс-строка), или цели ккал — вне этой фичи и этой спеки?
8. **Кэп 240 мин.** Сохраняем верхнюю границу на уровне тренировки (сейчас — на
   всю тренировку)? Альтернатива — кэп 60 мин на упражнение (марафон-подходы редки,
   но ручное время бывает кривым).

## 12. Декомпозиция на релизы

**Релиз A (MVP) — «формула + прозрачность»:**
- новая формула по упражнениям (app + бот, §3, §9.4 паритет);
- авто-пересчёт истории (ничего не мигрируем, §8);
- экран «Как считаются калории» из FAQ (§6) + новый FAQ-ответ;
- «Свои» без типа → дефолт 3.3 (без UI выбора);
- бот «🔥 Расчёт калорий» — разбор списком (§9.1);
- «Что нового» 1.3x: «Калории: расчёт по типу упражнения + разбор».

**Релиз B — «разбор и свои»:**
- breakdown в карточке (§7): строки с MET/минутами, «Почему так?», убрать
  «(в разработке)»;
- выбор типа при добавлении «Своего» + задание типа существующим (§5);
- `customEx` в GymData (если вопрос 5 — да) + контракт-кейс;
- ревизия MET каталога по Compendium + диапазонный контракт в `tests/check.js` (§3.5).

Порядок A → B выбран так, чтобы числа поменялись один раз и сразу с объяснением
(экран прозрачности едет вместе с формулой); breakdown и «Свои» — надстройки без
изменения чисел.
