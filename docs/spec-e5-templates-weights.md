## 1. Цель и проблема

Желание владельца: **шаблоны и «Повторить прошлую» должны нести не только упражнения, но и
веса с подходами**. Сейчас:

- `TemplateExercise` хранит план `w/s/r`, но при старте из шаблона записи создаются **пустыми**
  — план виден только в превью карточки (и то не везде: карточка в модалке старта MA план не
  показывает, в боте — тем более);
- «Повторить прошлую» копирует только имена упражнений — фактические веса теряются, юзер
  начинает «с нуля», хотя вся суть повтора — «делаю то же, что в прошлый раз»;
- подсказки прошлых весов (UX-I1 в MA, `sugWeights`/`sugPop`/`sugReps` в боте) помогают
  частично, но не связаны с намерением «сегодня по шаблону».

**Проблема пользователя:** стартовал из шаблона «Спина и бицепс» — и всё равно вручную
вспоминает и вбивает «60, 3 по 10» для каждого упражнения. Повтор прошлой тренировки — та же
история. Это главная ценность шаблонов у конкурентов (Hevy: routine подставляет веса).

**Решение в одном абзаце:** при старте из шаблона/повтора план последнего блока каждого
упражнения снимается снимком в запись упражнения (`ExerciseEntry`) и предлагается в модалке
ввода **пилюлей-подсказкой «в один тап»** (MA) / **кнопкой мгновенной записи блока** (бот) —
без автозаполнения полей и без копирования фиктивных записей.

## 2. Данные: снимок плана в `ExerciseEntry`

### 2.1. Постановка

План должен быть доступен в момент ввода подхода — минуты, часы и дни после старта
(перезапуск бота, перезагрузка MA, офлайн). Значит он не может вычисляться на лету из шаблона:

- шаблон могли удалить (гарантия §4.9: «удаление шаблона не трогает идущую тренировку» —
  runtime-lookup из шаблона её бы нарушил);
- «Повторить прошлую» вообще не создаёт шаблона.

**Решение:** при создании тренировки из шаблона/повтора план пишется **в сами записи
упражнений** — обычные данные GymData, со всеми гарантиями персистентности.

### 2.2. Поля `ExerciseEntry` (минимальное расширение)

```java
public final class ExerciseEntry {
    public String name;
    public String startedAt;
    public String endedAt;
    public final List<SetEntry> sets = new ArrayList<>();
    /* [UX-E5] план-подсказка из шаблона/повтора; ps == 0 → плана нет (старые данные) */
    public String planW = "";
    public int planS = 0;
    public String planR = "";
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `planW` | String | план веса («60», «75-175»); `""` = подход без веса |
| `planS` | int | план подходов; **`0` = плана нет** — дискриминатор «старых» записей |
| `planR` | String | план повторений («10», «8-10»); может быть `""` |

Инвариант «план есть»: `planS >= 1`. При чтении `ps < 1` → весь план сбрасывается
(`planW=""`, `planS=0`, `planR=""`).

### 2.3. JSON и совместимость

Имена ключей — в стиле существующих коротких (`st`/`en`/`w`/`s`/`r`): **`pw` / `ps` / `pr`**.

```json
{ "name": "Тяга верхнего блока", "st": "…", "en": "", "sets": [],
  "pw": "60", "ps": 3, "pr": "10" }
```

- **Чтение** (`fromJson`): ключей нет → поля остаются дефолтными (`planS=0`) — старые файлы
  читаются как раньше, без веток «если план».
- **Запись** (`toJson`): три ключа пишутся **только если `planS >= 1`** — файлы тренировок,
  созданных не из шаблона, остаются **байт-в-байт** прежними (тот же принцип, что у
  `templates`/`del` в §0.2 старой спеки).
- **Round-trip `/api/save`**: отдельных мер не требуется — план едет внутри типизированных
  `ExerciseEntry`, которые Mini App сохраняет целиком (в отличие от `templates`, спец-ветка
  в `WebServer` не нужна).
- `GymContractTest` дополнить: (а) legacy-файл без `pw/ps/pr` читается; (б) тренировка с планом
  переживает round-trip без потерь (вес-диапазон «75-175», `planR` пустой, `planS=0` → ключи
  не пишутся).
- Версионный перекос «новый клиент → старый сервер»: сервер проигнорирует неизвестные ключи —
  план потеряется до деплоя; деплоим атомарно (бот+MA из одного jar/каталога, как всегда).

### 2.4. Кто пишет план

| Среда | Место | Что пишет |
|---|---|---|
| MA | `createFromList(t)` (`web/app.js`) | каждому exercise: `planW=e.w, planS=e.s, planR=e.r` из `TemplateExercise` |
| Бот | `startFromTemplate(...)` (`BotLogic.java`) | то же из `TemplateExercise te` |

«Повторить прошлую» идёт через тот же `createFromList`/`startFromTemplate` с временным
шаблоном (`tplFromWorkout` / `templateFromWorkout`) — значит, план = **фактический последний
блок** упражнения той тренировки. Ничего нового для повтора не придумываем.

Записи, созданные **вручную** (пикер/своё упражнение), план не получают — поведение не меняется.

### 2.5. Схема `TemplateExercise` — НЕ расширяем

Рассматривалось: несколько блоков `w/s/r` в одном упражнении шаблона («60×3×10, потом 65×3×8»).
**Отсекаем** (см. §8): текущий блок «вес+подходы+повторы единым полем» соответствует
семантике этого приложения — один блок записи = «60 кг, 3 подхода по 10», и типичное
упражнение в дневнике имеет 1–2 блока. Схема (`w/s/r` опциональные, толерантное чтение)
допускает будущий апгрейд без ломки совместимости.

### 2.6. Жизненный цикл плана

План **не стирается** после первого залогированного блока — он инертен (3 коротких поля).
Видимость подсказки управляется правилом §3, а не данными. Бонус такого решения: если юзер
удалил первый блок — подсказка **возвращается** (записей снова нет).

## 3. Механика «план-подсказка» — общие правила (обе среды)

1. **План показывается только для нового блока** упражнения, у которого в **этой** тренировке
   ещё нет записей: `isNew && e.sets.length === 0 && e.planS >= 1` (MA) / `!st.editing &&
   entry.sets.isEmpty() && entry.planS >= 1` (бот).
2. **После первого блока** подсказка плана исчезает — дальше работают существующие подсказки:
   «↺ Предыдущий подход» (MA, UX-I1) и `sugWeights`/`sugPop`/`sugReps` (бот). Обоснование:
   план в этой модели описывает **один** блок (последний на момент сохранения); для 2-го и
   дальнейших блоков история внутри тренировки релевантнее плана. Побочно: две пилюли стеком
   — шум, а правило «пока пусто» исключает их одновременный показ (при пустых `sets` пилюля
   UX-I1 всё равно не появляется — конфликта нет by design).
3. **Конфликта с подсказками прошлого веса нет**: они либо не показываются одновременно
   (MA — см. п.2), либо показываются рядом с явным приоритетом плана (бот — кнопка плана
   первым рядом, строка «📋 По плану» первой строкой подсказок).
4. **В редактировании записи** план не участвует (редактируется факт, план не имеет смысла).
5. Подсказка **не автозаполняет** поля — значения попадают в форму только после явного тапа
   (MA) / явного тапа кнопки (бот). Защита от «фантомных» данных: юзер не сохранит блок,
   который не собирался сохранять.

## 4. Mini App

### 4.1. Пилюля плана в модалке записи (`openEntryModalIdx`)

В слоте между полем веса и клавиатурой (где живёт пилюля UX-I1 `.prevpill`) — та же пилюля,
другой смысл:

```
┌ Новая запись ────────────────────────────┐
│ Тяга верхнего блока                       │
│ ┌ Вес, кг (0 — без веса) ───────────────┐ │
│ │ 0                            Очистить │ │
│ └───────────────────────────────────────┘ │
│ (📋 План: 60 кг × 3 × 10 — подставить)    │  ← .prevpill, data-act="planTake"
│ [+0,5][+1][+2][+5][+10][+15][+20][+50]    │
│ [10][20][30][50][60][80][100][200]        │
│ ┌ Подходы ──────────────────────────────┐ │
│ │ 1                                     │ │
│ └───────────────────────────────────────┘ │
│ [1][2][3][4][5][6][7][8]                  │
│ ┌ Повторения (например 12, 8-10) ───────┐ │
│ │                                       │ │
│ └───────────────────────────────────────┘ │
│ [1][2][3][4][5][6][7][8]                  │
│ [10][12][+1][+2][+5][+10]                 │
│ [ ➕ Добавить ]  [ Закрыть ]              │
└──────────────────────────────────────────┘
```

**Условие показа:** `isNew && e.sets.length === 0 && +e.planS >= 1` (правило §3.1). При этом
условии пилюля UX-I1 не показывается никогда (см. §3.2) — в слоте максимум одна пилюля.

**Тексты пилюли:**

| План | Текст |
|---|---|
| `w="60", s=3, r="10"` | `📋 План: 60 кг × 3 × 10 — подставить` |
| `w="", s=3, r="10"` | `📋 План: свой вес × 3 × 10 — подставить` |
| `r=""` (план без повторений) | `📋 План: 60 кг × 3 — вес и подходы` (подставит только вес и подходы) |

Десятичная запятая в весе («62,5»), как в `tplPlan()`.

### 4.2. Действие `planTake`

Тап по пилюле (новый `data-act="planTake"`, аргументы не нужны — берёт `modalCtx`):

1. `mSets.value = e.planS` (если `planS >= 1`);
2. `mWeight.value = e.planW` (если `planW` не пуст; иначе поле не трогаем — остаётся «0»);
3. `mReps.value = e.planR` (если `planR` не пуст).

**Пилюля не исчезает после тапа** — остаётся и работает как «вернуть план»: поправил вес
руками, передумал — тапни пилюлю, план вернётся. После сохранения блока модалка закрывается;
следующее открытие этого упражнения пилюлю уже не покажет (`sets.length === 1`), вместо неё
появится «↺ Предыдущий подход».

**Почему тап-подставить, а не автозаполнение:** автозаполненные поля неотличимы от
введённых пользователем — риск сохранить «60, 3 по 10», не глядя, когда план уже не актуален
(травма, нет блинов 20 кг). Тап — осознанное «сегодня беру план». Пилюля визуально
переиспользует паттерн UX-I1 (янтарная, знакомая механика «тап — подставить»), нового
компонента в дизайн-системе нет.

**Почему не «мгновенно сохранить блок» (как в боте):** форма MA построена вокруг правки
перед сохранением (клавиатуры значений, «Очистить»); кнопка вне формы ломала бы паттерн.
Мгновенная запись — нативный для бота механизм (см. §5.1), у каждой среды свой путь.

### 4.3. Карточка шаблона в модалке старта: строка плана

В `openStartModal()` карточки шаблонов получают **вторую мета-строку** — компактный план
(сейчас `tmeta` показывает только «4 упр. · имена…», план в карточку не рендерится вообще):

```
📋 Спина и бицепс                          [🗑]
4 упр. · тяга блока, подтягивания…
Тяга блока 60×3×10 · Подтягивания 4×8 · Тяга штанги 50×3×10 · +1
```

Формат строки (новая функция `tplPlanLine(t)`):

- участвуют первые **3** упражнения шаблона; элементов больше трёх → хвост `· +N`;
- элемент = `короткое имя + « » + компактный план`;
- короткое имя: длина > 16 символов → первые 15 + `…` (клипается, чтобы план влезал в строку);
- компактный план: `W×S×R` без «кг» (контекст зала однозначен), вес с запятой («62,5×3×10»);
  без веса → `S×R`; `r` пустой → `W×S`;
- строка полностью скрывается, если в шаблоне нет ни одного осмысленного плана
  (теоретический случай рукотворного JSON; шаблоны из продукта всегда план имеют).

Стиль: новая `.tplan` — 11.5px, `--muted`, `tabular-nums`, одна строка с ellipsis
(реализация по образцу существующей `.tmeta`). Вид — макет, экран 1.

Строка **дополняет** `tmeta`, а не заменяет: имена в `tmeta` дают состав, план — целевую
нагрузку. Тап по карточке по-прежнему означает немедленный старт (§4.7 старой спеки) —
предпросмотр планом не усложняется.

### 4.4. Тексты MA, которые меняются

| Где | Было | Стало |
|---|---|---|
| Хинт в модалке «💾 Сохранить как шаблон» (`thint`) | «Шаблон запоминает упражнения и последний план — при старте просто появится список, вводить подходы будешь как обычно.» | «Шаблон запоминает упражнения и план последнего подхода. При старте из шаблона план подставится в форму ввода одним тапом.» |
| Тост при старте из шаблона | «📋 Шаблон применён: 4 упражнения» | без изменений |
| Тост при «Повторить прошлую» | «📋 Шаблон применён: 4 упражнения» (общий `createFromList`) | «🔁 Повтор прошлой тренировки: 4 упражнения» — `createFromList` получает признак повтора (попутный однострочный фикс: сейчас повтор честнее назвать повтором) |

### 4.5. Состояния и edge cases MA

| Случай | Поведение |
|---|---|
| Шаблон/повтор без плана (`planS=0` — старые данные, ручной JSON) | пилюли нет, форма как сейчас; строка плана в карточке скрыта |
| Тренировка НЕ из шаблона | поля `planS=0` → пилюли нет ни у одного упражнения; поведение идентично текущему |
| Упражнение добавлено вручную в тренировку из шаблона | плана у него нет — пилюли нет (подсказка прошлого веса/подхода работает как всегда) |
| Первый блок залогирован, потом удалён | пилюля плана возвращается (правило «пока пусто» — §2.6) |
| Редактирование существующей записи | пилюли нет (§3.4) |
| Мусорный план из рукотворного JSON (`pw="abc"`) | пилюля подставит как есть; существующая валидация `saveEntry` отловит при сохранении. `planS < 1` → план игнорируется целиком при чтении (§2.2) |
| План с пустым весом | пилюля «свой вес × 3 × 10»; тап заполняет подходы и повторения, вес остаётся «0» → блок сохранится как «без веса» |
| Сеть недоступна при старте из шаблона | как сейчас (`createFromList`): тост «Нет связи…», тренировка сохранится при следующей записи; план уже в памяти |

Загрузка/ошибка как отдельные состояния не проектируются: фича не добавляет новых сетевых
вызовов (пилюля читает данные уже загруженного `G`).

## 5. Бот

### 5.1. Вес-шаг: строка «По плану» + кнопка мгновенной записи блока

В `startExercise()` (и повторном входе в упражнение с экрана тренировки) вместе с
`sugWeights`/`sugPop` вычисляется `st.sugPlan` (новое nullable-поле `UserState`,
тип `TemplateExercise` — переиспользуем класс):

```java
st.sugPlan = (e.sets.isEmpty() && e.planS >= 1) ? planOf(e) : null;
```

**Текст промпта веса** (`weightPromptText`), строка плана — первой:

```
Введи вес (кг) или выбери:
📋 По плану: 60 кг, 3 по 10
Прошлый раз: 55кг, 60кг
Популярный: 60кг
```

| План | Строка |
|---|---|
| `w="60", s=3, r="10"` | `📋 По плану: 60 кг, 3 по 10` |
| `w="", s=3, r="10"` | `📋 По плану: без веса, 3 по 10` |
| `r=""` | `📋 По плану: 60 кг × 3` (кнопки мгновенной записи **нет** — блок без повторений невалиден) |

**Кнопка мгновенной записи** — первый ряд клавиатуры веса (до подсказок прошлых весов):

```
[ 📋 60 кг, 3 по 10 ]     ← новый callback "w:plan"
[ 55кг | 60кг ]           ← w:l_0… (как было)
[ 60кг ★ ]                ← w:p (как было)
[ 🚫 Без веса ]           ← w:none
[ ↩️ Назад ]              ← w:back
```

Тап → `confirmEntry(new SetEntry(sugPlan.w, sugPlan.s, sugPlan.r))` **сразу** — блок записан
целиком, дальше обычное «✅ Записано…» + `entryDoneKb()` + автозапуск таймера отдыха
(существующая точка). Это ботовый аналог «взять план в один тап»: в чате нет формы, которую
можно заполнить, — зато есть паттерн мгновенной записи одной строкой («45кг, 4 по 12»),
кнопка плана продолжает именно его.

**Границы:**

- кнопка `w:plan` **только при `!st.editing`** — клавиатура редактирования (`weightEditKb`)
  план-ряд не получает (редактируется одно поле существующего блока, мгновенная перезапись
  всего блока недопустима). Технически: план-ряд добавлять в `weightKb(st, back)` при
  `!st.editing && st.sugPlan != null && !st.sugPlan.r.isEmpty()`;
- `w:plan` при `st.editing` (защита от рассинхрона) — игнорируется с перерисовкой текущего экрана;
- быстрый ввод одной строкой «45кг, 4 по 12» в текстовом вводе веса — **не трогается**;
- кнопки `w:l_*` / `w:p` / `w:none` — не трогаются.

### 5.2. Шапки старта из шаблона / повтора

Упоминание плана в шапке — одна строка, чтобы юзер знал о подсказках до первого тапа:

| Момент | Текст (вместо/поверх текущего) |
|---|---|
| `tpl:start` | `📋 Шаблон «Спина и бицепс» применён — 4 упражнения. Вес и подходы из плана подскажу по каждому упражнению.` |
| `tpl:rep` (Повторить) | `🔁 Повторяем тренировку от 03-11. Фактические веса и подходы подскажу по каждому упражнению.` |

Дальнейший текст экрана тренировки — как сейчас.

### 5.3. Список `/templates` с планами

К сообщению списка добавляется план под каждым шаблоном (нумерация = порядку кнопок, новые
сверху):

```
📋 Шаблоны · 3 из 20

1. Спина и бицепс — 4 упр.
   Тяга блока 60×3×10 · Подтягивания 4×8 · Тяга штанги 50×3×10 · +1
2. Ноги — 3 упр.
   Присед 80×3×8 · Жим ногами 90×3×10 · +1

Тапни по названию, чтобы начать тренировку.
```

- формат строки плана — тот же, что в MA (§4.3): первые 3 упражнения + `+N`, имя > 16 символов
  клипается, `esc()` для HTML parse_mode;
- inline-клавиатура списка (`▶️ имя | 🗑`) — без изменений;
- пустой список — без изменений.

### 5.4. Текст после сохранения шаблона

```
✅ Шаблон «Спина и бицепс» сохранён (3 из 20).

Начать из него: /templates или кнопка «📋 Шаблоны».
При старте план последнего подхода подставится одним тапом.
```

## 6. «Повторить прошлую» — тот же механизм, фактические веса

Отдельного механизма **нет**: повтор строит временный шаблон (`tplFromWorkout` /
`templateFromWorkout`, план = последний блок каждого упражнения), и после §2.4 этот план
попадает в записи упражнения → работают все подсказки §4/§5. Тап по пилюле в MA = «взять
фактический вес прошлого раза»; кнопка в боте = «записать как в прошлый раз».

**Границы (не трогаем):**

- быстрый ввод «45кг, 4 по 12» (бот) и форма MA — без изменений;
- кнопки прошлых весов/повторов (`sugWeights`/`sugPop`/`sugReps`, пилюля UX-I1 после первого
  блока) — без изменений;
- «Повторить» с экрана конкретной завершённой тренировки (`tpl:rep_<wid>` / `newRepeatFrom`) —
  та же механика, план = факты **этой** тренировки;
- кнопка «🔁 Повторить прошлую» в модалке старта скрыта, если завершённых нет (как сейчас);
  кнопка «🔁 Повторить» в карточке существует только у завершённых тренировок, а они всегда
  имеют упражнения (фильтр при завершении) — «повтор пустой тренировки» недостижим.

**Наблюдение вне скоупа:** тост повтора «📋 Шаблон применён» поправлен попутно (§4.4),
больше расхождений с «повтор»-семантикой не фиксируем.

## 7. Edge cases (сводная таблица)

| Случай | Поведение |
|---|---|
| **Шаблон с планом × активная тренировка** | Бот: `pendingTplId`/`pendingRepWid` применяются после «🗑 Удалить и начать новую» — тот же `startFromTemplate`, план приедет вместе с ним, отдельного состояния нет. MA: модалка старта при активной тренировке не открывается (FAB ведёт в активную) — как сейчас |
| **Упражнение удалено из каталога** | Не влияет: подсказка плана живёт на имени записи (`planW/planS/planR` в `ExerciseEntry`), каталог в вводе не участвует; `findEx` по имени без регистра — как вся существующая логика |
| **План с пустым весом (только повторы)** | MA: пилюля «свой вес × 3 × 10», тап заполняет s и r, вес остаётся «0». Бот: строка «📋 По плану: без веса, 3 по 10», кнопка пишет блок с `w=""` |
| **План с пустыми повторениями** (`r=""`) | MA: пилюля заполняет только вес и подходы («… — вес и подходы»). Бот: строка-подсказка есть, кнопки мгновенной записи нет |
| **«Повторить прошлую», когда прошлая пуста/нет завершённых** | Кнопок нет (существующие условия); в боте `tplRepeat` защищён проверкой `finished` |
| **Шаблон удалён после старта тренировки** | Подсказки работают: план — снимок в записях, а не ссылка на шаблон (усиливает гарантию §4.9) |
| **Перезапуск бота / перезагрузка MA** | Подсказки работают: план в JSON (`pw/ps/pr`), читается как обычные данные |
| **Пользователь удалил первый блок** | Пилюля/кнопка плана возвращаются (записей снова нет) |
| **Старый JSON без `pw/ps/pr`** | `planS=0` → подсказки не появляются; файл читается; при записи ключи плана не пишутся (байт-в-байт) |
| **Дубликаты имён в шаблоне («Жим» / «жим»)** | Каждая запись несёт свой план; подсказки независимы (как вся существующая логика имён) |
| **Диапазон в плане («75-175»)** | Подставляется строкой как есть; e1RM/средние считают существующие парсеры при сохранённом блоке |
| **Несколько вкладок MA** | План часть `G`, синхронизируется существующим механизмом; подсказка перечитывается при каждом открытии модалки |
| **`w:plan` в рассинхроне (editing-сессия)** | Игнор + перерисовка (§5.1) |

## 8. Что НЕ делаем и почему

| Отсечено | Причина |
|---|---|
| **Автозаполнение полей ввода значениями плана** (поля сразу «60 / 3 / 10») | Поля неотличимы от введённых руками — юзер может сохранить неподходящий блок не глядя (фантомные данные → грязная статистика, ложные объёмы). Тап по пилюле = осознанный выбор «сегодня беру план», а конвенция «0 = без веса» и дефолты формы не ломаются |
| **Копирование фактических блоков прошлой тренировки в новую** (готовые записи при «Повторить») | Тот же фантом-риск, но хуже: «выполненная» тренировка без единого тапа, объёмы и тонаж в статистике, которую юзер не делал. Подсказки дают ту же скорость с честностью |
| **Несколько блоков w/s/r в упражнении шаблона** | Это уже программа тренировки, а не подсказка; UI сохранения и превью усложняется вдвое; семантика «план = последний блок» согласована с превью и бэклогом. Схема допускает будущее расширение без ломки |
| **Мгновенная запись блока по пилюле в MA** | Форма MA построена вокруг правки перед сохранением; мгновенный confirm — нативный паттерн бота (§5.1). Единообразие механики между средами навязывать не нужно |
| **План-подсказка для 2-го и дальнейших блоков упражнения** | План описывает один блок; дальше релевантнее «↺ Предыдущий подход» (UX-I1) и sug-кнопки бота. Две пилюли стеком — шум; правило «пока нет записей» к тому же исключает их одновременный показ |
| **План в редактировании записи** | Редактируется факт; подмена блока планом одним тапом опасна и не нужна |
| **Чип «по плану» на каждом подходе** | Избыточно: план применим к первому блоку (см. выше); чипы в форме — ещё один компонент без выигрыша |
| **Чек-лист «план vs факт» как в Hevy** | Смена парадигмы ввода; отсечено ещё в §4.10 старой спеки — не пересматривается |
| **Хранение `tplId` в тренировке вместо снимка плана** | Ломает гарантию «удаление шаблона не трогает тренировку» (§4.9) и не работает для повтора; снимок в `ExerciseEntry` проще и переживёт всё |

## 10. Критерии приёмки

1. Старт из шаблона с планом → у каждого упражнения первая запись показывает пилюлю плана;
   тап заполняет вес/подходы/повторы; сохранение даёт блок «60 кг, 3 подхода по 10».
2. После первого блока пилюля исчезает, появляется «↺ Предыдущий подход» (как раньше).
3. «Повторить прошлую» → пилюля показывает **фактический** последний блок каждого упражнения.
4. Бот: на вес-шаге строка «📋 По плану…» и первый ряд кнопки; тап записывает блок целиком
   одним сообщением «✅ Записано…»; таймер отдыха запускается как обычно.
5. Быстрый ввод «45кг, 4 по 12» и кнопки прошлых весов работают без изменений.
6. В редактировании записи план-подсказки отсутствуют (обе среды).
7. План без веса → «свой вес…» / «без веса, 3 по 10» — блоки сохраняются корректно.
8. Удаление первого блока возвращает подсказку плана.
9. Шаблон удалён после старта → подсказки продолжают работать.
10. Старый `data/*.json` без `pw/ps/pr` читается; round-trip файлов без плана — без новых
    ключей; файлы с планом переживают round-trip без потерь.
11. Карточки шаблонов (MA и бот) показывают компактный план: 3 упражнения + «+N».
