## 1. Цель и пользовательская проблема

**Продуктовая проблема**: у GymHelper нет работающего способа «похвастаться
тренировкой». v1 ([UX-I14]) предполагала client-side canvas в Mini App с отправкой
через `navigator.share` — механика провалилась на webview Telegram (сохранение
картинки ненадёжно, UX-B15). Дистрибуция остаётся главным гэпом проекта.

**Пользовательская проблема**: после сильной тренировки есть чем гордиться —
рекорд, объём, — но поделиться нечем: скриншот приложения выглядит как таблица,
текстом «пожал 100×5» — сухо и без контекста.

**Решение v2**: рендер на сервере (чистая Java 2D, доказано POC внутри Docker) +
доставка прямо в чат Telegram методом `sendPhoto` — ноль webview-механики.
Пользователь тапает «🖼 Постер» в боте и получает готовую картинку 1080×1920 с
caption; пересылает её друзьям в два тапа. Каждый пользователь = канал привлечения.

**Тон картинки**: плакат итога, «хочу так же» — только факты тренировки, никаких
«скачай/бесплатно». Продукт в текстах — от третьего лица. Подпись бренда — одна
строка в футере.

**Приватность (решение владельца 21.11): имя пользователя на постере НЕ
показывается** — ни имя, ни @username, ни фото. Постер — это тренировка, а не
человек. Полный чек-лист исключений — §5.4.

## 2. Сценарии использования

### Сценарий 1 — «Побил рекорд» (главный виральный)

1. Пользователь завершает тренировку в боте: «🎉 Тренировка завершена!» +
   клавиатура (§7.1).
2. Тап **«🖼 Постер тренировки»** → в чат прилетает PNG-постер: дата, 4 числа,
   янтарная карточка «РЕКОРД! Жим лёжа — 100 кг × 5», список упражнений, футер.
3. Пересылка постера в любой чат/канал — Telegram делает это нативно
   (forward в два тапа), caption едет вместе с картинкой.
4. Получатель спрашивает «что это?» → открывает @-профиль бота из футера/caption
   → онбординг ~60 секунд.

### Сценарий 2 — «Обычная тренировка»

Без рекорда карточка «РЕКОРД!» не рисуется, список упражнений встаёт выше —
постер собирается из любого завершённого дня. Делиться можно любой тренировкой
из истории (кнопка на экране просмотра завершённой тренировки, §7.2).

### Сценарий 3 — «Калистеника / турники» (без весов)

Объём кг = 0 → карточка статистики показывает сумму повторений («387 ·
повторений»), строки списка без «кг» («Подтягивания · 4×8»). Рекорд объёма
повторений — той же карточкой «РЕКОРД!» («Подтягивания — 38 повторений»).
Макет состояния — в HTML-макете, постер (б).

### Сценарий 4 — «Старый день из истории»

Тренировка записана 18.11, постер делается 21.11 → шапка постера показывает
**день тренировки** («18 ноября 2026, среда»), не «сегодня» (урок UX-B14).

## 5. Маппинг GymData → блоки (формулы = SharePage/Records)

Постер рендерит **завершённую** тренировку (`w.finished == true`). Упражнения с
пустым `sets` исключаются (как `finishWorkout`: `removeIf(e -> e.sets.isEmpty())`).

### 5.1. Дата-шапка

`w.date` (ISO-строка) → «21 ноября 2026, суббота» — формат `russianDate` из POC
(родительный падеж месяца, день недели полностью, год всегда). Парсинг
`LocalDate.parse`; нераспарсимая дата → показать строку как есть (фиксируется
контрактом GymContractTest, [UX-T46]). **Дата берётся строго из `w.date`**, никогда
`LocalDate.now()` — урок UX-B14 (тренировка не под своим днём).

### 5.2. Статистика 2×2

| Карточка | Формула (источник) | Значение | Подпись |
|---|---|---|---|
| Объём | `SharePage.volumeOf`: Σ `Records.avgWeight(s.weight) × max(s.sets,0) × Records.repsAvg(s.reps)` по всем блокам; **округление до целого** | объём > 0: `fmtNum` + « кг»; объём = 0 (безвесовая): `fmtNum(totalReps)` без «кг» | «объём тренировки» / «повторений» (§6.5) |
| Упражнения | число непустых `w.exercises` | число | «упражнение / упражнения / упражнений» (склонение `exWord`) |
| Подходы | `SharePage.setsTotal`: Σ `max(s.sets,0)` | число | «подход / подхода / подходов» (`SharePage.setsWord`) |
| Длительность | `SharePage.durationMin`: `endedAt − startedAt`, округление до минут; null — таймстемпов нет | «N ч M мин» (компакт, §10.1); h=0 → «M мин»; m=0, h>0 → «N ч»; null или 0 → «—» | «длительность» |

`fmtNum` — группировка тысяч пробелом («5340» → «5 340», код `SharePage.fmtNum`).

### 5.3. Карточка «РЕКОРД!» (условная)

Показывается максимум одна. Приоритет — **весовой рекорд**; весового нет →
рекорд объёма повторений; и его нет → карточка не рисуется.

**Весовой рекорд** (правила `SharePage.isRealWeightRecord`):
1. Найти подход с максимальным `Records.avgWeight(s.weight)` по всем блокам
   тренировки (упражнение = `maxEx`).
2. Рекорд засчитывается, только если этот вес **строго** больше максимального
   веса того же упражнения во ВСЕХ прошлых тренировках (индекс < текущей).
   Первое выполнение упражнения (базы нет) — **не рекорд**. Равенство — не рекорд.
3. Строка карточки: «Жим лёжа — 100 кг × 5» = `{упражнение} — {вес} × {повторы}`
   лучшего подхода (§5.5). Вес — `avgWeight` подхода **без округления**: целое —
   без дробной части («125 кг» — диапазон «75-175»), дробное — с десятичной
   **запятой** и срезанными хвостовыми нулями («82,5 кг», «82,25 кг» —
   `CardRender.weightAvgText`, та же база сравнения рекорда; §6.8).
   Повторы — текст подхода как введён («5», «8-10», «5+1»);
   нечисловой текст («макс») → 10 (`repsAvg`).
4. Расчётный 1ПМ по Эпли на постере **не показывается** (решение владельца
   19.11, унаследовано v1→v2): «100 кг — который реально жал».

**Рекорд объёма повторений** (безвесовое упражнение, аналог `Records.congratulation`):
1. Для каждого безвесового упражнения тренировки: `vol = Σ max(s.sets,0) × repsAvg(s.reps)`
   по всем его блокам в этой тренировке.
2. Рекорд, если `vol` **строго** больше максимального суммарного объёма этого
   упражнения во всех прошлых тренировках и база непуста (первое выполнение —
   не рекорд).
3. Строка: «Подтягивания — 38 повторений» (`repeatWord`: повторение/повторения/
   повторений).

Подпись карточки в обоих случаях: «личный результат по этому упражнению» (POC).

### 5.4. Что НЕ попадает на постер (унаследовано из v1 §3 + решение владельца)

- **имя / @username / фото пользователя** — решение владельца 21.11, без исключений;
- кастомное название тренировки (может содержать личное: «Тренировка с Машей»);
- время начала/конца (часы) — паттерн распорядка дня; на постере только длительность;
- вес тела, пол, возраст, дата рождения, ккал, питание — ПДн и шум;
- прогресс vs прошлая тренировка, серия/стрик — не запрошены владельцем, POC без них;
- призывы к действию — тон продукта: факт + подпись бренда в футере.

### 5.5. Строки упражнений

Каждая строка = **лучший подход** упражнения:

1. **Лучший подход** (правило задачи; отличие от `SharePage.bestSetIdx` — там при
   равенстве берётся первый):
   - с весами: макс `avgWeight`; при равенстве — макс `repsAvg`; при равенстве — первый;
   - без весов: макс `max(s.sets,0) × repsAvg(s.reps)`; при равенстве — первый.
2. Формат строки = `SharePage.setLine` (паритет с приложением и /w/<id>):
   - с весом: «120 кг × 3×8» (`weightText` — запятая вместо точки, строка веса как
     введена, диапазоны «75-175 кг × 3×8» показываются как есть);
   - без веса: «4×8»; тайм-упражнения: «3×60 сек» (sets×reps, где reps — «60 сек»).
3. Усечение длинного имени — §6.3.

## 6. Edge-кейсы (с примерами рендера)

### 6.1. Нет рекорда

Карточка «РЕКОРД!» не рисуется. Блок «УПРАЖНЕНИЯ» и строки сдвигаются вверх
(таблица §4.1): заголовок на baseline 800, строки с y=830. Пример — постер (б)
HTML-макета.

### 6.2. 0 / 1 упражнение

- **0 упражнений** (все пустые): постер **не рендерится** — делиться нечем.
  Кнопка «🖼 Постер» на такой тренировке не показывается; защита на callback —
  ответ «У этой тренировки нет записанных упражнений» (§7.4).
- **1 упражнение**: постер собирается, список из 1 строки. Пример:
  шапка «20 ноября 2026, пятница» · «2 480 кг / объём тренировки» · «1 упражнение» ·
  «12 подходов» · «48 мин» → строка «Приседания · 120 кг × 4×8».

### 6.3. Длинное название упражнения

Каноническое правило — **усечение по фактической ширине** (`FontMetrics.stringWidth`),
не по числу символов: имя + «…» должно влезать в доступную ширину строки
(936 − 72 паддинги − ширина значения − 24 зазор). Ориентир для типичных значений
(«120 кг × 3×8», 38px): имя не длиннее **~24 символов** при шрифте 42px. Значение
справа приоритетно — оно не двигается и не сжимается, усекается только имя.

Пример: «Подъём гантелей через стороны лёжа» + значение «12 кг × 3×12» →
рендер: «Подъём гантелей через ст…»  ·  «12 кг × 3×12».

Названия «своих» упражнений — те же правила (это обычные строки `ExerciseEntry.name`).

### 6.4. Больше упражнений, чем строк (лимит §4.1)

Показываются первые N строк (N = 4 при рекорде / 6 без — порядок пользователя),
под списком строка **«+ K ещё»** (K = всего упражнений − показано; `fmtNum` не
нужен, K < 100 нереалистично, но правило общее). Пример: 7 упражнений без рекорда →
6 строк + «+ 1 ещё». Пример в постере (б) HTML-макета.

### 6.5. Тренировка без весов (калистеника/кардио)

- объём = 0 → карточка объёма показывает `fmtNum(totalReps)` и подпись
  **«повторений»** (без «кг») — герой-слот v1 §8.1 edge 8, адаптированный в сетку 2×2;
- строки списка без «кг»: «4×8», «3×60 сек»;
- рекорд — по объёму повторений (§5.3). Пример: «Подтягивания — 38 повторений».
- Ккал на постере нет (нет в сетке 2×2 POC) — MET-расчёты остаются в приложении.

Замечание о честности формулы: тайм-упражнения («60 сек» → repsAvg 60) входят в
сумму повторений как есть — **та же формула**, что у карточки приложения и
SharePage.totalReps; расхождение «приложение vs постер» исключено.

### 6.6. День тренировки ≠ сегодня

Дата шапки и caption — всегда из `w.date` (§5.1, урок UX-B14). Пример: тренировка
18.11 (среда), постер делается 21.11 → шапка «18 ноября 2026, среда», caption
«Постер тренировки за 18.11 — …».

### 6.7. Пустая длительность

`startedAt`/`endedAt` отсутствуют (старые тренировки до таймеров) или разность
округлилась в 0 → значение карточки **«—»**, подпись «длительность» не меняется.
Сетка 2×2 не перестраивается. Пример: «— / длительность».

### 6.8. Дробные и диапазонные веса

- дробный вес: строка веса как введена с запятой — «82,5 кг × 5×5» (`weightText`);
- диапазон «75-175»: в строке списка как есть — «75-175 кг × 3×8»; в карточке
  рекорда — среднее «125 кг × 5» (avg — та же база сравнения рекорда);
- объём всегда округляется до целых кг («5 340 кг»).

### 6.9. Смешанная тренировка (веса + калистеника)

Объём кг > 0 → карточка объёма показывает кг (обычный режим). Весовой рекорд
имеет приоритет над объёмным (§5.3): если в тренировке рекорд и в жиме, и в
подтягиваниях — показывается один (весовой). Без весового — объёмный.

### 6.10. Незавершённая тренировка

Постер рендерится только для `w.finished == true`. Активная тренировка кнопки
не имеет; callback-защита — §7.4.

## 7. Доставка: Mini App → POST /api/card → sendPhoto (по факту реализации)

> **REV. 21.11, ревью [UX-S16]: §§7.1–7.4 — SUPERSEDED, не реализовано, вне
> периметра [UX-T46/T47]** (кнопки бота `poster_<id>` и multipart-доставка из
> спеки-проекта заменены delivery через Mini App; флоу задан задачей lead'а).
> Актуальная механика — §7.0; caption (бывш. §7.3.4) и тексты ошибок
> (бывш. §7.4) реализованы и остаются верными.

### 7.0. Механика по факту реализации ([UX-T46], ревью 21.11)

Триггер — Mini App, шит «Поделиться» → пункт «Картинка» ([UX-T47]):

1. `POST /api/card {initData, wid}` — initData-авторизация (как /api/share);
   защиты: 404 «Тренировка не найдена», 400 «Постер можно сделать для завершённой
   тренировки», 400 «У этой тренировки нет записанных упражнений».
2. **Антиспам: 3 успешных запроса в час на чат** (окно скользящее); отказ
   Telegram (502), переполнение каталога (503) и серверная ошибка рендера (500)
   слот антиспама откатывают (ревью [UX-S16]); 4-й успешный — 429 «Слишком
   часто: постер можно собирать не чаще 3 раз в час».
3. Рендер PNG 1080×1920 `CardRender.render` (§4–6) на лету, кэша нет;
   `-Djava.awt.headless=true` (Dockerfile ENTRYPOINT + setProperty в Main),
   шрифты — bundled DejaVu из jar.
4. PNG сохраняется в `data/cards/<token>.png`: токен 22 символа base62 (как
   shareId, не угадывается), запись CREATE_NEW (атомарно), **TTL 1 ч** — чистка
   при старте сервера и лениво при каждой записи + TTL-гвард при выдаче; кап
   каталога 1000 файлов → 503 «Слишком много картинок, попробуйте позже».
5. `GET /card/<token>.png` — публичная отдача (без initData): Content-Type
   image/png, noindex, short-cache 1ч; истёкший по mtime файл отдаёт 404.
6. `TelegramApi.sendPhotoByUrl(chatId, url, caption)` — JSON-POST sendPhoto с
   `photo=<https-url>`: Telegram скачивает картинку сам, multipart НЕ нужен.
   `cardUrlBase` — GYM_WEBAPP_URL (https обязателен).
7. Ответ Mini App `{ok:true}` → тост «🖼 Постер отправлен в чат с ботом —
   перешлите друзьям 💪»; ошибки — человекочитаемые на русском в `error`
   (502 «Telegram не принял картинку. Попробуйте ещё раз», 500 «Не получилось
   собрать постер 😔 Попробуйте ещё раз»), сеть — «Нет связи: не удалось
   приготовить постер».
8. Воронка: клиентские `cardClick` (тап пункта) / `cardOk` / `cardErr` через
   /api/track; серверные `cardSend` / `cardSendOk` / `cardSendErr` в /stats.

### 7.1–7.4. [SUPERSEDED] Кнопки бота `poster_<id>` и caption — не реализовано

| Раздел | Статус |
|---|---|
| §7.1 клавиатура «Тренировка завершена» с «🖼 Постер тренировки» | SUPERSEDED — не реализовано (кнопок бота нет) |
| §7.2 экран просмотра с «🖼 Постер» | SUPERSEDED — не реализовано |
| §7.3 callback-поведение, chat action upload_photo, multipart sendPhoto | SUPERSEDED — заменён §7.0 (шаги 3, 6) |
| §7.3.4 caption «Постер тренировки за 21.11 — перешли друзьям 💪» | **РЕАЛИЗОВАНО** в `/api/card` (`WebServer.cardCaption`): день из `w.date`, dd.MM, не текущий год — dd.MM.yyyy |
| §7.4 ошибки бота (не найдена/не завершена/0 упражнений/ошибка рендера) | РЕАЛИЗОВАНО в `/api/card` (тексты — без финальных точек, см. §7.0 шаги 1, 7) |

### 7.1. [SUPERSEDED] Сообщение «🎉 Тренировка завершена!» (`finishWorkout`)

Текст сообщения не меняется. Клавиатура (`finishedKb`) — новый ряд ПОСЛЕ
«💾 Сохранить как шаблон»:

| Ряд | Кнопки |
|---|---|
| 1 | «💾 Сохранить как шаблон» → `tpl:new_<id>` |
| 2 | **«🖼 Постер тренировки» → `poster_<id>`** (новое) |
| 3+ | mainKb (без изменений) |

### 7.2. Экран просмотра завершённой тренировки (`renderWorkoutScreen`, `w.finished`)

Новый full-width ряд после «🔁 Повторить | 💾 В шаблоны»:

| Ряд | Кнопки |
|---|---|
| 1 | «✏️ Редактировать» · «🥤 Питание» |
| 2 | «⏱ Время» · «🏷 Название» |
| 3 | «📈 Прогресс» · «🔥 Ккал» |
| 4 | «🔁 Повторить» · «💾 В шаблоны» |
| 5 | **«🖼 Постер» → `poster_<id>`** (новое) |
| 6 | «🗑 Удалить» |
| 7 | «↩️ К истории» · «🏠 Меню» |

У активной (незавершённой) тренировки и в списке истории кнопки нет (§6.10).

### 7.3. Поведение при тапе (callback `poster_<id>`)

1. Найти тренировку по id; проверки §7.4.
2. Отправить chat action **upload_photo** (пользователь видит «отправляет фото…» —
   рендер < 1 сек, но действие даёт тактильную обратную связь).
3. Рендер PNG (§4–5) → `sendPhoto`: multipart/form-data, поля `chat_id`, `photo`
   (attach PNG-байтов), `caption`.
4. **Caption (день тренировки из `w.date`, формат dd.MM; если год не текущий —
   dd.MM.yyyy)**:

   > **Постер тренировки за 21.11 — перешли друзьям 💪**

   Один универсальный caption для всех постеров (с рекордом и без) — без вариантов
   и без канцелярита; эмодзи 💪 в тоне существующих текстов бота.
5. Исходное сообщение (экран тренировки) не редактируется, старые кнопки живут.

### 7.4. Ошибки и защита

| Случай | Реакция бота |
|---|---|
| Тренировка не найдена / id ≤ 0 | тихий no-op (старая клавиатура могла пережить правки) |
| Тренировка не завершена | `«Постер можно сделать для завершённой тренировки.»` (защита от устаревших клавиатур) |
| 0 упражнений | `«У этой тренировки нет записанных упражнений.»` |
| Ошибка рендера (шрифт/графика) | `«Не получилось собрать постер 😔 Попробуй ещё раз.»` — сообщение об ошибке в чат, без падения процесса |

### 7.5. Отправка как photo, не document — актуально, по факту `photo=<url>`

`sendPhoto` (сжатие Telegram) — не `sendDocument`: превью картинки видно прямо в
ленте чата — это суть виральности. Риск лёгкого размытия текста при пережатии
минимален при 1080px (опыт v1 §4: «Telegram пережимает без артефактов текста»).
По факту реализации ([UX-T46]): `photo` — не multipart-файл, а публичный
https-URL `/card/<token>.png` (Telegram скачивает сам).

## 8. Числовая консистентность (критерий честности)

Каждое число постера считается формулой `SharePage`/`Records` (§5) — теми же, что
карточка приложения и страница /w/<id>. Расхождение «постер vs приложение vs
страница шеринга» технически исключено: общий код, а не копии. Кодер выносит
формулы в доступное место (_sharePage_-методы уже пакетно расшарены; при
необходимости — поднятие в общий класс, БЕЗ изменения поведения).

## 9. Что НЕ делаем и почему

| Отсечено | Почему |
|---|---|
| Механика v1: canvas в webview, `navigator.share`, кнопка в Mini App | провалилась (UX-B15: «картинка сохранена», а файла нет); v2 — серверный рендер + sendPhoto, webview-механики ноль |

| Автоотправка постера после завершения тренировки | спам в чат + лишние отправки без запроса; кнопка = явное намерение поделиться |
| Ссылка t.me / пилюля приложения на постере | POC утверждён БЕЗ ссылки (футер — только текст); дистрибуцию несут caption и профиль бота. Вернуть пилюлю v1 — отдельное решение владельца |
| Серия/стрик, ккал, прогресс vs прошлый раз | нет в одобренном POC; добавление = изменение утверждённого визуала |
| Выбор темы/шаблона постера | выбор = трение; один утверждённый дизайн |

| EN-вариант | RU-фокус стратегии |

## 10. Отклонения от POC-референса (полный список)

Визуал (палитра, размеры, композиция, шрифты) — 1:1 из POC. Отклонения — только
адаптация под реальные данные и правила текстов:

1. **Компактный формат длительности**: «1 ч 10 мин» вместо POC-«1 час 10 мин».
   Причина: гарантированная ширина карточки 2×2 на любых данных («10 ч 05 мин»
   полной формой ≈ 430px > 390px доступных; компакт ≈ 280px всегда влезает);
   заодно снимает склонения часов. Шрифт/размер не меняются.
2. **Склонения подписей статистики**: «упражнение/упражнения/упражнений»,
   «подход/подхода/подходов» (POC — статичные «упражнений»/«подходов»); подпись
   слота объёма меняется на «повторений» для безвесовых тренировок (§6.5).
3. **Строка безвесового упражнения — формат `setLine`**: «3×60 сек» вместо
   POC-«60 сек × 3». Причина: числовой паритет с приложением и /w/<id> (правило
   §8) важнее косметики статичного POC-данных.
4. **Дата — из дня тренировки** (`w.date`), POC брал `LocalDate.now()` — урок
   UX-B14; формат строки даты не изменился.
5. **Условность карточки рекорда и сдвиг списка** (§4.1, §6.1): POC рисовал
   рекорд всегда и 4 статичных строки; v2 — правило лимитов 4/6 и «+ K ещё».
6. **Реальные веса/диапазоны/дроби**: запятая-децималь («82,5»), среднее диапазона
   в карточке рекорда («125 кг»), округление объёма до целых (POC — статика).
7. **Пустая длительность «—»** (POC — всегда «1 час 10 мин»).
8. Тексты caption и клавиатур (§7) — новые, вне периметра POC.

## 11. Критерии приёмки (для coder / tester — рев. 21.11, по факту [UX-T46/T47])

- Шит «Поделиться» ([UX-T47]): у завершённой тренировки с подходами — кнопка
  «📤 Поделиться» с бейджем «выбор»; в шите два пункта — «🖼 Картинка»
  (подпись «Постер придёт в чат с ботом — перешлите друзьям») и «Телеграм»;
  у активной тренировки кнопки нет. Кнопок бота `poster_<id>` НЕТ (§7.1–7.2 —
  SUPERSEDED).
- Тап «Картинка» → busy на кнопке «⏳ Готовим постер…» → `POST /api/card` →
  при ok тост «🖼 Постер отправлен в чат с ботом — перешлите друзьям 💪»;
  постер приходит в чат с ботом (`sendPhoto`, `photo=<url>`) с caption
  «Постер тренировки за <дд.мм> — перешлите друзьям 💪» (день — из `w.date`,
  не текущий год — dd.MM.yyyy). Mini App никуда не навигирует (урок UX-B15).
- Ошибки — русские тосты: 429 «Слишком часто…», сеть «Нет связи: не удалось
  приготовить постер», 404 «Тренировка не найдена», 400 «Постер можно сделать
  для завершённой тренировки» / «У этой тренировки нет записанных упражнений»;
  после ошибки кнопка разблокирована, воронка `cardErr`.
- Антиспам: слот лимита 3/час тратит ТОЛЬКО успешная отправка — 3 подряд
  отказов Telegram (502) НЕ приводят к 429 на следующем вызове (контракт
  GymContractTest фиксирует); 4-й успешный вызов в окне — 429.
- PNG отдаётся по `GET /card/<token>.png` (image/png, токен 22 base62,
  не угадывается); истёкший по TTL (1 ч) файл — 404; мусорный/короткий токен
  и traversal — 404.
- Числа постера равны числам карточки приложения и /w/<id> на одних данных
  (§8): объём/повторения, упражнения, подходы, длительность, рекорд, строки
  упражнений.
- Рекорд — реальный вес (не 1ПМ), строго больше базы прошлых тренировок; первое
  выполнение — не рекорд; Эпли на постере отсутствует.
- Имя/@username пользователя на постере отсутствует на любых данных.
- Edge-кейсы §6 — рендер не ломается на: без рекорда; 1 упражнение; 7+ упражнений;
  длинное название; без весов; пустая длительность; дробные/диапазонные веса;
  старая дата.
- Шрифты — только bundled DejaVu (нет зависимости от системных шрифтов хоста);
  рендер работает в Docker-контейнере прод-образа (headless, §7.0 шаг 3).
- Формат GymData не изменился; `GymContractTest` (включая блок [UX-S16])
  зелёный; e2e Mini App дополнены сценариями «Картинки» и зелёные.
- Нагрузка: повторные тапы — каждый рендер заново, утечек памяти нет (PNG не
  кешируется).

## 12. Открытые вопросы к lead'у

1. **Место кнопки** — рекомендация §7 (ряд в сообщении завершения + ряд на экране
   просмотра). Альтернатива: только на экране просмотра (меньше кнопок в
   финальном сообщении). Дефолт — как в §7, возражений не поступало.
2. **sendPhoto vs sendDocument** — рекомендация photo (превью в ленте, §7.5).
   Если владелец захочет «без пережатия» — переключение на документ меняет одну
   строку API-вызова, UX чуть хуже (нет превью). Дефолт — photo.
3. Приоритет реализации внутри кодера: рендер (§4–6) — ядро; кнопки/caption (§7)
   — поверх. Разбивать ли на два Task — решение lead'а при заведении задач.
