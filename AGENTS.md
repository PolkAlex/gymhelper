# AGENTS.md — правила проекта MyHelper (GymHelper)

Telegram-бот дневника тренировок. Backend: чистая **Java 17 без внешних зависимостей** (`src/gym/`).
Frontend: Telegram Mini App — ванильный JS/HTML/CSS (`web/`), без сборки и npm-пакетов.
Тесты: Playwright e2e + контрактный тест на Java. Подробности — `README.md`.
Заметки владельца — `TODO.md` (проверять в начале любой задачи).

## Структура

```
src/gym/*.java             — бот (Main, BotLogic, TelegramApi, Json, GymData, Storage, ...)
src/gym/web/WebServer.java — HTTP-сервер Mini App (порт 8080)

tests/                     — e2e.spec.js (Playwright), GymContractTest.java, check.js, server-test.js

Dockerfile, docker-compose.yml — контейнер для VPS (прод работает в Docker: образ ghcr.io собирает CI на push в main; systemd-юнит gymbot остановлен 08.11.2026 — порт 8080 занят контейнером)
```

**Статусы по типам тикетов** (правила движения):
- **Idea**: Inbox (сырая) → Backlog (проработана/оформлена) → при взятии в работу потомки

### Технические грабли (gh + PowerShell) — НЕ НАСТУПАТЬ

1. **Инлайн-кавычки в длинных командах**: bash-слой съедает `"` внутри PowerShell-строк
   → GraphQL-мутации НЕ собирать инлайном-конкатенацией. Пиши mutation в JSON-файл
   (Write tool, с реальными значениями сразу) и запускай `gh api graphql --input файл`.
2. **PS 5.1 кодировки**: `.ps1`/файлы с кириллицей — только UTF-8 **С BOM** (WriteAllText
   с UTF8Encoding($true)); Set-Content/Get-Content без `-Encoding` перекодируют UTF-8
   в ANSI (mojibake). Продуктовые файлы (web/, src/) править только Write/Edit tool,
   после правки — Read-проверка кириллицы.
3. **Плейсхолдеры-замены**: не гоняй цепочки Replace поверх изменённых файлов — сначала
   получи все значения (выведи/прочитай), затем ОДИН Write файла с готовым содержимым,
   перед запуском — Read-проверка.
4. **`$pid` и прочие автоматические переменные** — readonly, не использовать как имена.
5. **`--jq` надёжнее инлайна** для извлечения значений из gh api вывода; лимитированные
   поля: `gh api ... --jq '.data.r.iNN.id'` — работает стабильно.
6. **gh project item-delete** требует: `gh project item-delete 1 --owner PolkAlex --id <ITEM_ID>`.

### Коды тикетов в заголовках

GitHub не поддерживает Jira-нумерацию (номера issue сквозные и неизменяемы), поэтому семья
обозначается кодом в заголовке: `[MON-E1] Монетизация: ...`. Формат: `[ABC-XN] Название`,
где `ABC` — код направления (таблица выше), `X` — буква типа тикета (`I`=Idea, `E`=Epic,
`S`=Story, `T`=Task, `B`=Bug), `N` — порядковый номер тикета **этого типа** внутри
направления. Примеры: `[DSN-I1]` — первая Idea направления Дизайн, `[MON-E1]` — первый
Epic направления Монетизация, `[MON-T3]` — третий Task. Код и номер ставит lead при
создании тикета; при смене направления заголовок обновляется. Новому направлению
присваивается новый 3-буквенный код.

Idea — постоянный контейнер: тикет навсегда остаётся Тип=Idea и не «вызревает». При взятии
в работу под ней заводятся потомки (Epic/Story/Task) как sub-issues. Связь потомка с
родителем — поле Parent issue (нативный GitHub), на доске виден Sub-issues progress.
По конвейеру едут только потомки; Idea-тикет живёт в Backlog, пока все её потомки не
дойдут до Done, после чего закрывается.

### Процесс работы (договорённости)

1. Когда владелец говорит «идея»: lead продумывает идею; при необходимости задаёт владельцу
   уточняющие вопросы и/или привлекает агента design для проработки (design тоже может
   задавать вопросы владельцу). По итогам обсуждения заводится issue + item на доске
   (Тип=Idea, статус Backlog). Код по идее не пишется до взятия в работу.
2. Когда идею берут в работу: Idea-тикет остаётся собой (Тип=Idea). Lead уточняет детали
   и заводит под неё потомков (Epic/Story/Task) как sub-issues; потомки идут в Todo и далее
   по конвейеру.
3. Тикет с меткой `need_design` идёт через In Design (даже Bug — бывают баги по дизайну);
   остальные — сразу In Dev.
4. Статусы на доске двигает lead в момент передачи работы следующему агенту.
5. Блокер ревью/тестов возвращает задачу в In Dev.
6. Релиз = Milestone. Релиз проводим, когда ВСЕ тикеты milestone в статусе Ready To Deploy.
7. Деплой на прод делает владелец вручную; после его подтверждения lead переводит тикеты
   в Done и закрывает issues (`gh issue close N --comment "что сделано"`).
   ⚠️ ЖЕЛЕЗНОЕ ПРАВИЛО: без явной отмашки владельца («тест пройден / едем») на прод НЕ
   едем — ни lead, ни агентам, ни скриптами. Нарушение — критический инцидент.
   Автоматического деплоя в проекте нет и появляться не должно.
8. Владелец может лично тестировать тикет на этапе In Test: lead передаёт ему инструкцию
   по проверке; тикет ждёт его отмашки («тест пройден») перед переходом в Ready To Deploy.
9. Счётчик багов владельца: lead считает баги, которые владелец находит в работе агентов
   и приносит в чат. При достижении 3 багов владелец проводит полную перепроверку
   недавней работы, после чего счётчик сбрасывается. Текущее значение: **3/3** (обновляет
   lead). История: 1/3 (UX-B5, утро 07.11) → 3 бага из заметок с тренировки (UX-B6/B7/B8,
   вечер 07.11) → перепроверка проведена владельцем (список из 18 пунктов) → сброс →
   1/3 (дубль «Удалить/Отменить», 08.11) → UX-B10/B12 (fullscreen-перекрытие + «Свое…»
   некликабельно, 09.11) = 3/3 → перепроверка владельцем 09.11 («на проде всё ок») → сброс →
   1/3 (тренировка не под своим днём в календаре, 20.11) → UX-B15/B16 из проверки релизов

10. Статусы родителей синхронно с детьми: когда ВСЕ дети (Task'ы Story / Story'и Epic)
   в одном статусе — родитель переводится lead'ом в тот же статус; если хоть один ребёнок
   в предыдущем статусе — родитель остаётся в своём текущем. Lead проверяет это при
   каждом движении тикета.
11. Вместимость: дефолт — один эпик или два мелких тикета за релиз/спринт. Явное решение
    владельца задаёт вместимость иначе (пример: 4 эпика в Спринте 1, 06.11.2026 — это и
    есть вместимость, НЕ «пропуск»). Урок Релизов 1.6+1.7 (два эпика параллельно дали
    много багов по обоим) — учитывать риски при превышении дефолта, но лимитирует
    только владелец.
12. **Todo = только то, что взято в текущий спринт.** Всё остальное живёт в Backlog
   (двигать в Todo без включения в спринт нельзя). В конце спринта незавершённое
   возвращается в Backlog.
13. **Тайминги перед стартом**: перед каждой итерацией/задачей lead сообщает владельцу
   оценку времени (сколько занимает работа агентов и когда понадобится владелец) —
   владелец решает, когда давать старт (может быть не за компьютером).
    **Дополнено 08.11.2026 (инцидент: lead сам начал кодить по фидбеку)**: по умолчанию
    lead ТОЛЬКО оформляет тикеты на доске (Backlog) и даёт оценку — код/дизайн/тесты НЕ
    запускаются без явной команды владельца на конкретный тикет («делай», «бери в
    работу»). «Решай задачи» = оформить + приоритеты, не исполнять. Оценка времени —
    ПОЭТАПНО (кодер ~X, ревью ~Y, тесты ~Z), чтобы владелец видел тайминги.
    **Дополнено 09.11.2026 (третий инцидент: lead выкатил календарь на прод, хотя в том же
    сообщении владельца был прямой запрет «не выкатывай, сначала макеты посмотрю» —
    lead прочитал сообщение частично и взял только «делай и деплой»)**: сообщения
    владельца читать ЦЕЛИКОМ; прямые точечные запреты («не выкатывай до аппрува»,
    «сначала макеты») имеют ПРИОРИТЕТ над общими мандатами («деплой сразу») — общий
    мандат не отменяет точечный запрет на конкретную работу. Макет-ревью владельца —
    жёсткий гейт: без явного «ок, делай» код не пишется и не выкатывается.
    **Дополнено 09.11.2026 (четвёртый инцидент: при ночном мандате «10 часов,
    занимайся» lead остановился после первого релиза и ждал выбора меню)**: ночной/
    пакетный мандат = конвейер продолжается непрерывно по мандату и приоритетам до
    исчерпания задач или конца окна; пауза-вопрос владельцу — ТОЛЬКО при реальном
    блокере (доступ/токен/решение, которое никто кроме владельца не примет).
    **Дополнено 11.11.2026 (пятый инцидент: фраза владельца «Поправишь макеты,
    посмотрю. Это исправим и можно выкатывать релиз» была прочитана как отмашка на
    немедленный деплой — EXR с НЕвычитанными текстами уехал на прод до просмотра
    владельцем)**: отмашкой на деплой считается ТОЛЬКО безусловное указание на
    выкатку прода, не обременённое предварительными действиями, требующими
    просмотра владельцем. Если в сообщении с «выкатывай» есть «посмотрю /
    посмотрите / внесу правки / после одобрения» — это отложенная выкатка: сначала
    перечисленные шаги (включая просмотр владельцем), деплой — только после явного
    «посмотрел / ок / выкатывай» в ответ на результат. Правило чтения сообщения
    ЦЕЛИКОМ (см. инцидент 09.11, третье дополнение) применяется и здесь.
14. **Спринт проставляется на все тикеты семьи** — включая Epic и Idea-контейнер,
    а не только исполнительные Story/Task (GitHub не наследует итерацию от детей).
15. **Спринт закрывается строго по дате** (правило владельца, 06.11.2026): длится ровно
    14 дней и НЕ закрывается раньше — даже если все его тикеты уже Done; досрочное
    закрытие или продление — только явное решение владельца. «Все тикеты Done» = спринт
    выполнен по содержанию, но окно спринта продолжает действовать: тикеты, взятые
    в работу до даты закрытия, получают текущий спринт (см. п.14 и правило
    обязательного поля «Спринт»). Релизы (Milestone, п.6) — отдельная механика,
    к закрытию спринта не привязаны.
16. **Терминология** (правило владельца, 07.11.2026): фраза «спринт закрыт» — ТОЛЬКО когда
    истекли 14 дней (п.15) или владелец явно закрыл/продлил спринт. Завершённая работа
    по тикету формулируется как «эпик/фича/тикет реализован(а)» или «в Ready To Deploy» —
    никогда как «спринт закрыт».
17. **Метрики качества** (правило владельца, 07.11.2026): при КАЖДОМ переходе тикета по
    статусам lead добавляет строку в `docs/metrics-log.md` (дата, тикет, из → в).
    Определения метрик (Throughput, Velocity, возвраты, Cycle Time In Dev→RtD по SP,
    first-pass CR, escaped defects) и порядок сводок (спринт/месяц/квартал/год) —
    `docs/metrics.md`. GitHub не хранит историю статусов item'ов доски — журнал
    в metrics-log.md единственный источник данных. Дашборд — Grafana Cloud (Infinity
    datasource читает JSON из secret-gist): после изменения журнала
    `node tools/metrics-to-json.mjs` + `gh gist edit` (инструкции — docs/metrics.md,
    раздел «Дашборд»).
18. **Тесты до и после каждого релиза** (правило владельца, 08.11.2026 — цель: меньше
    багов, находимых владельцем): перед деплоем tester прогоняет ПОЛНЫЙ цикл (статика,
    gradle build + контракт, e2e ВСЕХ устройств) и ДОПОЛНЯЕТ e2e-сценарии под свежие
    правки релиза (не покрытый сценарий — новый тест); после релиза каждый баг/фидбек
    владельца фиксируется регресс-тестом в тот же или ближайший батч, чтобы дефект
    не возвращался. Красные тесты = деплой запрещён.
19. **Мониторинг комментариев GitHub** (правило владельца, 08.11.2026): владелец может
    оставлять комментарии/упоминания в issue и PR — это сигнал к реакции. Lead при
    КАЖДОМ взятии задачи (и в начале сессии) проверяет новые комментарии во ВСЕХ
    открытых issue/PR (`gh issue list` + просмотр комментариев) и не пропускает
    фидбек владельца; ответ на комментарий — комментарием в тот же issue/PR.
20. **Метка `inbox` — идеи с телефона** (правило владельца, 09.11.2026): владелец
    создаёт issue из GitHub Mobile с меткой `inbox` — это заявка на работу. Lead при
    КАЖДОЙ сессии проверяет `gh issue list --label inbox`, оформляет тикеты
    (приоритеты, связи) и берёт в работу по приоритету БЕЗ отдельного подтверждения
    владельца (метка = мандат). Техничку и низкоприоритетное — по обычным правилам.
21. **Ссылки на тикеты в чате** (правило владельца, 20.11.2026): упоминая тикет или
    эпик (в любом сообщении владельцу, в отчётах, в планах), указывать помимо номера
    также его название и ссылку на issue. Формат: `[EXR-I3] «Свои» упражнения …`
    (https://github.com/PolkAlex/gymhelper/issues/165).

### Гигиена доски и тикетов (свод правил, 19.11.2026)

Введено после чистки доски 19.11 (рассинхроны: спринты у тикетов «в работе», борд↔issue,
пустые поля, Done-родители с живыми детьми). Автопроверка — `node tools/board-audit.mjs`.

**Обязательные поля item'а на доске** (заполняются в момент добавления тикета на доску;
пустое поле — ошибка lead'а, аудитор скажет [B]/[W]):

| Поле | Когда обязательно | Значение |
|---|---|---|
| Статус | всегда | Inbox (сырая идея) / Backlog (оформленная, не в работе) / конвейер / Done |
| Тип | всегда | Idea/Epic/Story/Task/Bug — совпадает с буквой кода заголовка ([UX-I16] ⇒ Idea) |
| Направление | всем членам семьи (одна семья = одно направление) | одиночные [TECH]/[DOC]/[APP]-тики могут без него |
| Приоритет | при оформлении тикета | число 1–100 |
| Спринт | при взятии в работу — ВСЕЙ семье, включая Idea-контейнер и Epic (п.14); тикет в Todo..Ready To Deploy без текущего спринта не живёт | текущая итерация |
| Story Points | только эпикам | 1–2/3/5/8; предлагает lead, утверждает владелец |

**Движение и синхронизация:**
1. Порядок конвейера и правила движения — скилл `board`: Todo → (In Design — только для
   `need_design`) → In Dev → Code Review → In Test → Ready To Deploy → Done; ревью до тестов;
   блокер возвращает в In Dev.
2. **Борд и issue — одно состояние:** Done на борде ⇒ issue закрыт тем же действием (с
   комментом «что сделано»); закрытый issue ⇒ Done на борде. Борд не обгоняет issue и не отстаёт.
3. **Родители = состояние детей** (п.10): запрещён родитель Done при незавершённых детях;
   Idea живёт в Backlog, пока потомки не Done, затем Idea → Done + issue закрывается.
4. **Sub-issues:** у ребёнка ровно один родитель; перенос = `removeSubIssue` + `addSubIssue`
   (remove асинхронный — add делать после проверки родителя). Чужой ребёнок в семье — ошибка
   оформления (пример 19.11: ANA-T5 в ANA-S2).
5. **Спринт-гигиена:** старт нового спринта — незавершённое возвращается в Backlog (п.12);
   итерации у Backlog-тикетов не обновляются «про запас»; устаревшая итерация у Backlog-тика —
   история, не трогается (решение владельца 19.11).
6. Каждое движение статуса → строка в `docs/metrics-log.md` + gist (п.17).

**Аудит (как следить за порядком):**
- `node tools/board-audit.mjs` — проверяет: пустые Статус/Тип; код заголовка vs Тип;
  Направление у семей; Спринт у конвейера и у родителей семей; борд↔issue; семьи
  (Done-родители, «все дети Done»); In Design без `need_design`; приоритеты; SP эпиков.
  Blocker'ы = нарушения, чинятся немедленно; warnings — по ситуации.
- Прогон обязателен: в начале каждой сессии (шаг триажа) и после каждой партии правок доски.
- Что аудиту не поддаётся (держит в голове lead): вместимость спринта (п.11), приоритеты
  по решениям владельца, синхрон с реестром метрик.

## Конвенции

- Java 17, **никаких внешних зависимостей в коде** (Gradle — только инструмент сборки,
  никаких Maven-зависимостей в build.gradle)
- `web/` — ванильный JS/CSS/HTML: без фреймворков, сборщиков и новых npm-пакетов
- Формат данных `data/*.json` (класс `GymData`) — **обратная совместимость обязательна**:
  старые файлы без новых полей должны читаться (эталон — `GymContractTest`)
- Cache-bust статики: при ОТКАТЕ релиза из main бампать `?v=` версий **ВЫШЕ отозванных**,
  а не возвращать старые номера — иначе телефоны, поймавшие отозванный билд в immutable-кэш,
  не обновятся никогда (коллизия v66, инцидент 26.11; см. п.9 истории багов)
- Все тексты интерфейса — на русском
- Стиль кода — как в соседних файлах; минимальные диффы, рефакторинг без просьбы не делать
- Пол пользователя хранится как `м`/`ж`

## Безопасность

- **НИКОГДА** не читать, не печатать в чат и не коммитить: `token.txt`, `deploy_key`, `deploy_key.pub`
- Не коммитить: `data/`, `out/`, `testout/`, `node_modules/`, `test-results/`
