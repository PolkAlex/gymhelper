## 1. Цель и пользовательская проблема

Приложение хорошо фиксирует **прошлое** (история, статистика, e1RM), но не отвечает на
вопрос **«куда я иду и как быстро»**:

- «хочу пожать 100 кг — сколько уже осталось?» — есть e1RM 96 кг, но негде зафиксировать
  намерение и следить за разрывом;
- «я вообще достаточно тренируюсь?» — счётчик «в этом месяце» есть, а нормы/обещания
  самому себе — нет;
- мотивация падает, когда прогресс не виден глазами: число подходов растёт, а sense of
  progress — нет.

**Сущность «цель»** замыкает петлю: данные, которые УЖЕ собираются (e1RM, завершённые
тренировки), превращаются в измеримый прогресс к выбранной пользователем точке. Это самый
дешёвый способ добавить мотивацию — вся «новая» информация выводится из существующей.

Цель — **явное намерение с дедлайном и авто-прогрессом**. Никаких планов
тренировок, программ, коуч-механик — только «точка Б», текущее положение и остаток.

## 2. Типы целей — предложения lead'а (ядро)

Черновик владельца называет пример «пожать 100 кг» и периоды неделя/месяц/квартал.
Ниже — 4 типа с оценкой ценности и стоимости расчёта из СУЩЕСТВУЮЩИХ данных.

### 2.1 (а) Силовая: упражнение + целевой вес

- **Формула**: «Жим лёжа — e1RM 100 кг» (упражнение + число + метрика).
- **Прогресс**: текущий e1RM упражнения (уже считается на лету: `Records.e1rm`,
  `e1rmOf`; показан в Статистике и в боте «1ПМ ≈») vs цель. % = cur/target.
- **Ценность**: ★★★ — это ровно пример владельца; самая «залитая кровью» метрика
  продукта (рекорды, блок Эпли уже приучили пользователя к «1ПМ ≈»).
- **Сложность расчёта**: минимальная — метрика готова, нужен только max по истории
  (уже есть в обоих рендерах статистики).
- **Метрика цели**: по умолчанию **e1RM (оценка 1ПМ)**. Альтернатива «вес подхода»
  (лучший рабочий вес) — возможна, но: (1) e1RM уже привычна по UI; (2) «пожать 100»
  пользователь почти всегда имеет в виду как раз 1ПМ. Решение — вопрос 2.
  **Изменено решением 12.11: ДАТЬ ВЫБОР пользователю** — e1RM по Эпли или вес
  лучшего подхода, оба варианта валидны (выбор в мастере).

### 2.2 (б) Частота: N тренировок за период

- **Формула**: «12 тренировок до 30.11» (число + срок).
- **Прогресс**: количество завершённых тренировок с датой в окне [start..end] —
  тот же подсчёт, что в «В этом месяце: N» (есть в боте и в statgrid).
- **Ценность**: ★★★ для привычки/возвращаемости — закрывает «я ленюсь», самый частый
  тип цели в фитнес-приложениях (Hevy/Strong: «workout goal»).
- **Сложность расчёта**: минимальная — счётчик готов.
- Нюанс: прогресс растёт рывками (тренировка = +1); визуал — кольцо, не бар (см. §8.2).

### 2.3 (в) Объём: тоннаж (или калории) за период

- **Формула**: «30 тонн за месяц» / «10 000 ккал за месяц».
- **Прогресс**: тоннаж окна = Σ (avgWeight × подходы × средние повторения) по всем
  записям завершённых тренировок в окне. Полуфабрикат есть (`Records.metricsOf` считает
  объём повторений `vol`), но **умножения на вес нет нигде** — нужна новая агрегация.
  Калории за тренировку считаются (MET), но задним числом зависят от текущего веса
  профиля — историческая сумма будет «плавать» при правках профиля.
- **Ценность**: ★★ — метрика продвинутых пользователей; новичку тоннаж ни о чём не говорит.
- **Сложность расчёта**: средняя (новая агрегация; парсинг весов «50, 80»/«100-260» —
  готовый `avgWeight` переиспользуется).
- **Метрика по умолчанию — тоннаж** (кг×повторения); калории — опция на выбор, вопрос
  не критичен для R1, решается в R4.

### 2.4 (г) Вес тела (связь с Профилем)

- **Формула**: «Вес 80 кг» (+ направление: снизить/набрать).
- **Прогресс**: текущий `profile.weight` vs цель относительно веса на момент создания
  цели: % = (start − cur)/(start − target) для «снизить», (cur − start)/(target − start)
  для «набрать».
- **Ценность**: ★★ — расширяет аудиторию на «похудающих/набирающих», которых в зале много.
- **Слабое место**: данные профиля обновляются вручную и нерегулярно — прогресс может
  неделями стоять на месте не потому, что человек не старается, а потому что не вносил
  вес. Нужна подсказка «обновите вес в Профиле» при застывшем прогрессе.
- **Сложность расчёта**: низкая (одно поле профиля), но UX-хвост (напоминание обновлять
  вес) делает тип нетривиальным в поддержке.

### 2.5 Итог: что берём в MVP

| Тип | Ценность | Сложность | Релиз |
|---|---|---|---|
| (а) Силовая (e1RM) | ★★★ | мин. | **R1 (MVP)** |
| (б) Частота | ★★★ | мин. | **R1 (MVP)** — изменено решением 12.11 (было R3) |
| (в) Объём (тоннаж) | ★★ | сред. | R4 |
| (г) Вес тела | ★★ | низкая+UX-хвост | R4 (вопрос 9 — подтверждено решением 12.11) |

Обоснование MVP = только силовая: пример владельца, нулевая стоимость расчёта, и
именно силовая цель утилизирует главный актив приложения — блок Эпли. Частота —
следующий релиз, потому что ценность сопоставима, а каркас (экран, хранение, мастер)
после R1 позволит добавить тип за один таск.

> **Изменено решением 12.11**: в MVP (R1) берём **силовая + частота СРАЗУ**;
> объём/вес тела — R4 (отдельного релиза R3 больше нет).

## 3. Сроки

- **Неделя / Месяц / Квартал** — календарные периоды: конец текущего ISO-недели
  (воскресенье), текущего месяца, текущего квартала (31.03 / 30.06 / 30.09 / 31.12).
  Согласуется с существующими окнами статистики («рекорды недели», «в этом месяце»).
- **Окно прогресса** = [дата создания цели .. конец периода]. Цель, созданная 13.11
  с сроком «месяц», считается по тренировкам с 13.11 по 30.11 (не с 01.11) — честно
  относительно усилий, потраченных на эту цель.
- **Edge: создание в конце периода.** Если до конца периода осталось < 3 дней, мастер
  дополнительно показывает чипы СЛЕДУЮЩЕГО периода («Следующий месяц · до 31.12») —
  чтобы никто не получил «цель на 1 день».
- **«Без срока»** (навсегда) — только для силовых: цель-ориентир («пожать 100 кг»
  без дедлайна). Бар показывает прогресс, вместо даты — «без срока». Для частоты/объёма
  «без срока» не имеет смысла (окно и есть суть цели) — чип не показывается.
- Срок отображается везде в формате «до 31.12» (без года, год виден в мастере/резюме).

## 4. Прогресс: расчёт из существующих данных

### 4.1 Формулы

| Тип | Текущее значение | % достижения |
|---|---|---|
| Силовая | max e1RM упражнения по ВСЕЙ истории (тот же агрегат, что в «Оценка 1ПМ · Эпли») | round(cur/target × 100) |
| Частота | завершённые тренировки с date в [start..end] | round(cur/target × 100) |
| Объём | тоннаж завершённых тренировок окна | round(cur/target × 100) |
| Вес тела | profile.weight | по формуле §2.4 |

- % закапывается в **100** (перевыполнение не рисуем >100%).
- Силовая цель считается по e1RM за всю историю (не только окно): e1RM — монотонный
  максимум, «откатить» его нельзя, прогресс цели не может падать. Это упрощение
  осознанное: цель силовая — «дорасти до», а не «удерживать».
- Подпись прогресса: «96 из 100 кг · осталось 4 кг», для частоты «8 из 12 · нужно ещё 4».

### 4.2 Момент проверки достижения

- **Мини App (R1)** — в момент записи подхода, та же точка, где живёт «🏆 Рекорд!»
  (`prCheck` в приложении): новый блок поднял e1RM упражнения до ≥ target → тост цели
  (§11), цель переводится в статус «достигнута».
- **Бот (R2)** — та же точка (`BotLogic.confirmEntry`/финиш тренировки): рядом с
  «🏆 Рекорд!» отправляется «🏆 Цель достигнута!» (§6.1).
- **Страховка чек-ином**: если достижение проскочило незамеченным (софт-краевой случай,
  правки задним числом через ✏️ Редактирование), еженедельный чек-ин и ежедневный
  планировщик проверяют активные цели и закрывают их (§6.2).

### 4.3 Edge cases

- **Цель уже достигнута на момент создания** (e1RM 104 при цели 100): мастер показывает
  предупреждение «Текущий e1RM — 104 кг. Цель 100 кг уже достигнута — поставьте выше?»
  и подсказывает чип +10%.
- **Редактирование/удаление тренировок задним числом**: частота/объём пересчитываются
  на следующем рендере; если из-за правки прогресс стал < 100 у УЖЕ «достигнутой» цели —
  НЕ откатываем (достижение зафиксировано честным подсчётом на момент события;
  `doneValue` хранит результат). Для частотных целей с окном в будущем это невозможно
  влево (тренировки не удаляются из будущего) — риск только теоретический.
- **Упражнение переименовано**: цель хранит строку названия; переименование записи
  в истории (существующая механика) разорвёт связь. Решение: при переименовании
  упражнения обновлять поле `ex` активных целей с этим названием (одна строка кода
  в точке переименования; включено в R1-таск T4).
- **Удалённая цель из архива**: удаляется безвозвратно (без confirm — архив
  не влияет на расчёты).

## 5. Предложения целей по истории

Мотив: постановка цели — самый высокий «порог входа» фичи («а какую цель-то ставить?»).
История даёт готовую разумную цель — пользователь принимает её одним тапом.

- **Силовая (R1)**: для упражнения с e1RM ≥ 40 кг, по которому НЕТ активной цели:
  `target = ceil((e1rm × 1.06) / 2.5) × 2.5` (шаг 2,5 кг — стандартный шаг блинов).
  Пример: 132 × 1.06 = 139,9 → **140 кг**. Диапазон роста 5–10% на квартал — реалистичный
  темп для любителя; 2,5-кратное округление вверх даёт «красивые» числа.
- **Срок в подсказке**: конец ТЕКУЩЕГО квартала, если до него ≥ 6 недель; иначе
  конец следующего (13.11 → «до 31.12»; 01.12 → «до 31.03»).
- **Частота (R3)**: если «в этом месяце» ≥ 4 тренировок → «В следующем месяце —
  N+2 тренировок?» (N — текущий темп).
- **Показ**: ОДНА карточка-подсказка (top-1 по наибольшему e1RM среди подходящих):
  - в Статистике — сразу под карточкой «Оценка 1ПМ · Эпли» (подсказка вырастает
    из её данных, соседство осмысленно) — макет, экран 1;
  - на экране «Цели» в пустом состоянии — вместо «нечего показать».
- **Кнопки**: [🎯 Поставить 140 кг] — открывает мастер с предзаполненными шагами
  2–3 (осталось выбрать/подтвердить срок); [Нет, спасибо] — скрывает подсказку
  для этого упражнения, пока e1RM не вырастет (память отклонений — `localStorage`,
  ключ `gymGoalDismiss:<упражнение>:<target>`; не синхронизируется с ботом — приемлемо).
- Если все упражнения с e1RM уже под целью — подсказки нет. Подсказка — НЕ уведомление:
  она существует только внутри приложения, пуши по ней не отправляются.

## 6. Напоминания бота

### 6.1 Канал и типы сообщений (тексты)

Канал — обычное сообщение в чат с ботом (не канал, не e-mail). Три типа:

**1) Еженедельный чек-ин** (по умолчанию воскресенье 19:00, вопрос 5 —
подтверждено решением 12.11; один глобальный тогл достаточен):

```text
🎯 Чек-ин по целям

1. Жим лёжа — e1RM 100 кг
   96 из 100 кг (96%). Осталось 4 кг, до 31.12 — 3 недели.

2. 12 тренировок до 30.11
   8 из 12 (67%). Нужно ещё 4, до 30.11 — 2 недели.

Маленький шаг на этой неделе — и Вы ближе к цели 💪
```

- ОДНО сообщение со сводкой всех активных целей (не по сообщению на цель — антиспам).
- Не отправляется, если активных целей нет.
- «осталось X» и «N недель» — по состоянию на момент отправки.

**2) Поздравление о достижении** (R2, точка финиша тренировки — та же, что у рекордов):

```text
🏆 Цель достигнута!

«Жим лёжа — e1RM 100 кг»: оценка 1ПМ 101 кг.
Цель переехала в архив достижений. Поздравляем! 🎉
```

**3) Финал по сроку — «не успел»** (день истечения срока; проверка ежедневным
планировщиком, отправка с утренним чек-ином дня):

```text
⏳ Срок цели истёк

«Жим лёжа — e1RM 100 кг»: результат 96 кг (96%), до цели не хватило 4 кг.
Цель в архиве — можно повторить её в приложении или поставить новую.
```

- Достигнутая в срок цель не получает сообщение №3 (закрывается №2 при достижении).

### 6.2 Расписание и техническая база

- В `BotLogic` уже есть `ScheduledExecutorService` (restScheduler, таймер отдыха) —
  добавляется один ежедневный тик (раз в сутки, фиксированное время сервера):
  1. раз в неделю (день чек-ина) — отправить чек-ин (если есть активные цели и
     `goalRemind != false`);
  2. ежедневно — проверить активные цели с истёкшим `end`: не достигнуты →
     «не успел» + архив; достигнуты по факту (e1RM ≥ target, если проскочило) →
     поздравление + архив.
- **Ограничение (честно зафиксировать)**: время — серверное (VPS), не пользовательское.
  Для РФ-аудитории это неважно; пользовательская таймзона — заготовка на будущее
  (поле в Профиле), в скоуп не берём.
- Антиспам: чек-ин один в неделю, событий — только по факту достижения/истечения.
  Никаких «Вы почти у цели!» пушей каждый день.
- Недоступный чат (бот заблокирован) — ошибка отправки игнорируется, повторов нет.

### 6.3 Отключение

- Один глобальный тогл (не per-goal — перебор для MVP):
  - Mini App: Настройки → строка «🔔 Напоминания о целях» (setrow + switch, паттерн
    [UX-S4]);
  - Бот: экран «🎯 Цели» → кнопка-переключатель «🔔 Напоминания: вкл/выкл» (§6.4).
- Хранение: `goalRemind` в GymData (§10). Дефолт — включены (null = вкл).

### 6.4 Кнопка «🎯 Цели» в боте (R2, вопрос 8 — подтверждено решением 12.11)

- Главное меню: строка «📋 Шаблоны» расширяется до пары
  `["📋 Шаблоны", "🎯 Цели"]` (клавиатура остаётся компактной, 6 строк).
- Экран:

```text
🎯 Цели

1. Жим лёжа — e1RM 100 кг
```

## 7. Виджет в Mini App: где и почему

**Решение: вкладка «Статистика», карточка «🎯 Цели» сразу ПОСЛЕ «Оценка 1ПМ · Эпли»
(перед «Серия»)** — макет, экран 1. **Подтверждено решением 12.11 (вопрос 3);
иконка 🎯 в topbar — НЕТ.**

| Место | За | Против |
|---|---|---|
| **Статистика, рядом с e1RM** ✅ | прогресс цели — это аналитика «где я»; данные виджета (e1RM) считаются прямо там; пользователь, у которого есть цель, получает «стало → осталось» в одном экране; подсказка цели вырастает из карточки Эпли | виджет ненавязчив: кто целей не ставил, видит только в конце вкладки |
| История | высокая проходимость вкладки | лента карточек тренировок — про прошлое по дням, цель там «чужая»; замусоривание главного экрана |
| Профиль | — | Профиль — данные и настройки (рост/вес/тема/таймер), не аналитика; цель там не находится |
| Отдельная 6-я вкладка | максимальная заметность | ломает паттерн «4 таба + FAB», ради одной фичи — нет |

- Внутри виджета: до 3 активных целей компактными строками (название + % + мини-бар)
  и кнопка «Все цели →» → подэкран «Цели» (§8). Частотная цель в виджете — той же
  строкой с баром (кольцо — только на полном экране: в строке 24px кольцо нечитаемо).
- **Второй вход — иконка 🎯 в topbar** (как календарь [UX-S6]): НЕ предлагаю в MVP —
  в topbar уже пара [ 📅 ][ ⚙ ] на всех вкладках, третья иконка теснит заголовок на
  320px; вход через виджет достаточен, пока цели — одна вкладка глубиной. Вопрос 3.
- Связь с [TRN-I4] (цели подопечного в Тренере): хранение целей per-chat не блокирует
  будущий «подопечный» сценарий, но UI Тренера — отдельная работа, здесь не проектируется.

## 8. Экран «Цели» (подэкран Mini App)

### 8.1 Каркас

Паттерн подэкрана как Настройки/Календарь ([UX-S4]/[UX-S6]): `goalsOpen` (boolean,
в памяти), topbar «← Назад | Цели», «Назад» возвращает на Статистику
(вкладка-источник), нижняя навигация остаётся, тап по табу закрывает подэкран.
Контент сверху вниз:

```
┌────────────────────────────────────────┐
│ ←  Цели                                │
├────────────────────────────────────────┤
│ АКТИВНЫЕ · 2 ИЗ 5                      │  ← секционный лейбл
│ ┌────────────────────────────────────┐ │
│ │ 🏋️ Жим лёжа        [Силовая · e1RM]│ │  ← карточка цели (§8.2)
│ │ Цель: e1RM 100 кг                  │ │
│ │ [████████████████░░░░] 96%         │ │
│ │ 96 из 100 кг · до 31.12 · 4 кг     │ │
│ │            [Отменить цель]         │ │
│ └────────────────────────────────────┘ │
│ ┌────────────────────────────────────┐ │
│ │ 🔢 12 тренировок     [Частота]     │ │
│ │ до 30.11                           │ │
│ │   (кольцо 67%)  8 из 12            │ │
│ │ до 30.11 · нужно ещё 4             │ │
│ │            [Отменить цель]         │ │
│ └────────────────────────────────────┘ │
│ [+ Новая цель]                         │  ← кнопка
│ АРХИВ ДОСТИЖЕНИЙ                       │
│ ✅ Жим лёжа 100 кг · 15.11   [Повторить]│  ← строки архива (§8.3)
│ ✅ 12 тренировок в октябре · 31.10     │
│ ⏳ Вес 80 кг · не успел (82,4 кг)      │
└────────────────────────────────────────┘
```

### 8.2 Карточка активной цели

- Шапка: иконка типа + название (упражнение / «12 тренировок» / «Вес 80 кг») + чип типа
  справа («Силовая · e1RM», «Частота», «Объём», «Вес тела»).
- Прогресс:
  - **бар** — силовая/объём/вес тела (стиль `.rec-bar`: 8px, радиус 999, янтарный
    градиент — готовый класс);
  - **кольцо** — частотная (SVG-кольцо с % в центре: рывковый прогресс «+1 тренировка»
    честнее читается кольцом-счётчиком; в виджете Статистики — всё равно бар, §7).
- Строка метаданных: «96 из 100 кг · до 31.12 · осталось 4 кг» / «без срока».
- Действия: одна кнопка **«Отменить цель»** (sec, приглушённый) → confirm-модалка
  «Отменить цель „Жим лёжа — 100 кг“? Прогресс не сохранится в архиве.» [Отменить цель / Оставить].
  Изменение цели в MVP = отмена + создание новой (изменяемая цель — отдельная работа,
  вопрос 7 — решено 12.11: достаточно).
- Достижение (100%): карточка цели заменяется мгновенным состоянием «🏆 Достигнута»
  + тост (§11), цель уезжает в архив при следующем рендере (или сразу — решение за
  реализацией, поведение одинаковое).

### 8.3 Архив достижений

- Секция «Архив достижений» под активными целями; строки:
  - `✅ Жим лёжа — e1RM 100 кг · 15.11.26` — достигнута (doneValue, если отличается);
  - `⏳ 12 тренировок до 30.11 · не успел (9 из 12)` — не успел (приглушённая строка);
  - отменённые цели НЕ показываются (пользователь сам решил уйти — мусор не храним
    в интерфейсе; в JSON статус 4 остаётся до конца квартала, потом чистить не
    обязательно — размер записи ~100 байт).
- Кнопка «Повторить» на строке архива → мастер с предзаполнением (упражнение/значение/срок
  пересчитываются от текущей даты; «без срока» сохраняется как был).
- Лимит архива не вводим; сортировка — по дате закрытия, свежие сверху. Разворачивание
  «показать все» не нужно до 10+ записей (позже, если понадобится).

### 8.4 Состояния

- **Пусто (нет целей)**: иллюстрация-эмодзи 🎯, «Целей пока нет», подсказка «Поставьте
  первую — например, „пожать 100 кг“. Прогресс посчитается автоматически по Вашей
  истории.», кнопка [🎯 Поставить цель] (prime, wide). Если есть данные для подсказки
  (§5) — карточка-предложение над кнопкой.
- **Загрузка/ошибка**: целей как таковых в сети нет (данные уже в G.*) — особых состояний
  загрузки не нужно; ошибки сохранения показываются существующим механизмом тостов err.
- **Лимит достигнут (5 активных)**: кнопка «+ Новая цель» активна, но мастер на шаге 1
  показывает плашку «Активных целей уже 5 — отмените одну, чтобы поставить новую»
  (шаг 1 тип-карточки disabled).
- **320px**: карточки перестраиваются без горизонтального скролла: чип типа переезжает
  под название, кольцо 56px, мета-строка переносится на 2 строки (макет, экран 8).

## 9. Мастер создания цели (в стиле мастера онбординга)

Полноэкранный подэкран, шаги с индикатором «Шаг N из 4» (как в онбординге), «← Назад»
возвращается на предыдущий шаг, ✕/«Отмена» — выход из мастера.

- **Шаг 1 из 4 · Тип цели** — 4 карточки-опции (frow-паттерн): 🏋️ «Силовая — пожать
  100 кг: упражнение + вес» / 🔢 «Частота — N тренировок за период» / ⚖️ «Объём —
  тоннаж за период» (плашка «Скоро», disabled до R4) / ⚖️ «Вес тела — связь с Профилем»
  (плашка «Скоро», disabled до R4). Неотпущенные типы показываем — так пользователь
  видит roadmap и не считает фичу «недоделанной». (Макет, экран 3.)
- **Шаг 2 из 4 · Упражнение** (только силовая) — поиск + список (переиспользование
  каталога): сверху упражнения с e1RM > 0 (с подписью текущего «e1RM 132 кг»), далее
  весь каталог. Частота/объём/вес тела этот шаг пропускают (мастер сжимается до 3 шагов).
- **Шаг 3 из 4 · Значение** — чипы-подсказки от текущего e1RM: «137,5 · +5%»,
  «140 · +7%», «145 · +10%» + поле «Своё…» (число, шаг 0,5 кг). Для частоты — чипы
  8/10/12/Своё… для объёма — 20/25/30 тонн… (частота — с R1 по решению 12.11;
  объём — R4). (Макет, экран 4.)
- **Шаг 4 из 4 · Срок** — чипы «Неделя · до 20.11», «Месяц · до 30.11», «Квартал ·
  до 31.12», «Без срока» (только силовая; §3). (Макет, экран 5.)
- **Резюме + «Создать цель»** (prime): карточка «Жим лёжа · e1RM 140 кг · до 31.12»
  + строка «Прогресс начнётся с сегодняшнего e1RM 132 кг (94%)». После создания —
  возврат на экран «Цели» с новой карточкой и тостом «🎯 Цель поставлена».

## 10. Хранение (GymData) и совместимость

### 10.1 Модель

```java
public final class Goal {
    public long id;            // общий счётчик data.nextId (сущность как Workout)
    public int type;           // 1 силовая, 2 частота, 3 объём, 4 вес тела
    public String exercise;    // силовая: название; остальные — null
    public double target;      // кг (e1RM/тоннаж/вес) или штук (тренировки)
    public String start;       // ISO-дата создания (начало окна прогресса)
    public String end;         // ISO-дата срока; null = без срока (только силовая)
    public int status;         // 1 активная, 2 достигнута, 3 не успела, 4 отменена
    public String doneDate;    // дата закрытия (достижение/истечение)
    public double doneValue;   // результат на момент закрытия
}
/* GymData: */
public final List<Goal> goals = new ArrayList<>();
public Boolean goalRemind;     // null = напоминания включены (дефолт)
```

JSON-фрагмент файла чата (порядок ключей — в конце карты GymData, как `del`/`templates`):

```json
"goals": [
  {"id": 17, "type": 1, "ex": "Жим лёжа", "target": 100.0,
   "start": "2026-11-13", "end": "2026-12-31", "status": 1,
   "doneDate": "", "doneValue": 0}
],
"goalRemind": false
```

### 10.2 Совместимость старых JSON (обязательное требование)

Полностью по сложившемуся паттерну (`templates`, `del`, `restSec` — эталон
`GymContractTest`):

- **Чтение**: ключа `goals` нет → пустой список (старый файл читается как сейчас);
  битые элементы списка пропускаются (`continue`), как у шаблонов; `goalRemind`
  читается только если это Boolean, иначе null.
- **Запись**: `goals` пишется ТОЛЬКО при непустом списке; `goalRemind` — только когда
  отличен от null. Итог: файл пользователя без целей остаётся **байт-в-байт прежним** —
  контрактный тест и диффы ревью это подтвердят.
- **Обратная совместимость вперёд**: старая версия кода, прочитав новый файл с `goals`,
  просто проигнорирует незнакомый ключ (Json-парсер читает карту целиком) — откат
  версии бесплатный.
- Никаких миграций не нужно: цель — новая сущность, не поле существующих тренировок.

### 10.3 Лимиты

- **Активных целей ≤ 5** (вопрос 4 — подтверждено решением 12.11): мотив — чек-ин
  на 10 целей не читается, виджет — 3 строки максимум; 5 — простор и для [MON-E1]
  (premium = больше целей), и против «списка желаний» (цель работает, когда она одна
  из немногих). **Изменено решением 12.11 (вопрос 10): цели пока БЕСПЛАТНЫЕ**
  («потом будем перерабатывать»); лимит 5 в дизайне остаётся.
- Архив — без лимита (строки мелкие, растут на десятки байт; чистка не планируется).
- Создание целей в боте не даёт bypass лимита (кнопка «✨ Новая цель» ведёт в Mini App).

## 11. Достижение цели: тост и переиспользование механики рекордов

- **Тост** — готовый янтарный градиент PR-тоста `.toast.pr` (механика [UX-T2]):
  «🏆 Цель достигнута! Жим лёжа — e1RM 100 кг». Показ в момент записи подхода,
  поднявшего e1RM до цели.
- **Конфликт тостов** (один подход может одновременно дать PR и закрыть цель):
  показывается ТОЛЬКО тост цели (он важнее; чип 🏆 у записи остаётся как был).
  Очередь тостов не делаем.
- Чип 🎯 у записи подхода (аналог чипа 🏆) — НЕ делаем: экономим место в строке,
  тоста и архивной строки достаточно.
- В архив пишутся `doneDate` + `doneValue` — строка «✅ … · 15.11» строится из них,
  пересчётов при рендере архива нет.
- Бонус-механика «серия достижений»/годовые итоги — не в скоупе (§12).

## 12. Что НЕ делаем и почему

| Не делаем | Почему |

| Соцсоревнование, рейтинг, лидерборды | отдельная идея #56; цели — личная петля мотивации, соцслой меняет продукт и требует модерации |

| Платные цели, деньги за цели | зона [MON-E1] #1; дизайн оставляет крючок (лимит 5 активных), но решение — отдельным тикетом. **Изменено решением 12.11: цели пока бесплатные — не монетизируем («потом будем перерабатывать»)** |
| Цели подопечного | [TRN-I4] #111, направление Тренер; требует модели «тренер→подопечный», вне скоупа GOA |
| Программы тренировок / план по цели | цели отвечают «куда», не «как»; планирование — другой продукт (см. research-competitive) |
| Произвольные напоминания (каждый день, кастомное время, таймзона) | антиспам + серверная таймзона; один еженедельный чек-ин закрывает потребность (§6.2) |

| Чип 🎯 у записи подхода, очередь тостов | место в строке дорогой, тост цели важнее PR-тоста (§11) |
| Иконка 🎯 в topbar на всех вкладках | пара [ 📅 ][ ⚙ ] уже плотная для 320px; вход через виджет достаточен (§7, вопрос 3) |
| Цели на калории одной тренировки, «стреки» | серии уже есть (streak), разовая тренировка — не цель, а факт |

## 13. Вопросы владельцу

1. **Состав MVP по типам**: согласны ли, что в R1 — только силовая (e1RM)? Или сразу
   R1 = силовая + частота (частота почти бесплатна после каркаса)?
2. **Метрика силовой цели**: e1RM (оценка 1ПМ по Эпли, как в Статистике) — или «вес
   подхода», или выбор из двух в мастере? Предлагаю e1RM без выбора (проще и уже
   привычно по UI).
3. **Виджет**: Статистика сразу ПОСЛЕ карточки «Оценка 1ПМ · Эпли» (вариант А) — или
   НАД ней (вариант Б)? И нужен ли второй вход — иконка 🎯 в topbar (как календарь)?
   Предлагаю вариант А и без иконки.
4. **Лимит активных целей**: 3 или 5? Предлагаю 5 (архив без лимита).
5. **Чек-ин**: воскресенье 19:00 по времени сервера — ок? Достаточно ли одного
   глобального тогла «Напоминания о целях» (без настроек на каждую цель)?
6. **«Без срока»** для силовых целей — оставляем? (иначе все цели — с дедлайном;
   цели-ориентиры вроде «пожать 180» живут годами.)
7. **Управление активной целью**: MVP = только «Отменить» (с подтверждением); изменение
   = отмена + новая. Достаточно ли? (Полноценное редактирование — отдельный таск, если нужно.)
8. **Кнопка «🎯 Цели» в главном меню бота**: добавлять в R1 (вместе с приложением) —
   или только в R2 (когда появятся напоминания)? Предлагаю R2.
9. **Вес тела как тип цели**: брать ли в MVP? Прогресс живёт по весу из Профиля —
   свежесть данных зависит от того, как часто Вы вручную обновляете вес. Предлагаю R4
   с подсказкой «обновите вес в Профиле».
10. **Монетизация [MON-E1]**: если цели станут платными — что именно платное (число
    активных > 5? напоминания? типы целей?)? Решение нужно ДО R1: лимит 5 зашит в
    дизайн виджета и чек-ина.

## 14. Декомпозиция на релизы

Крупная фича — по правилам идеи GOA-I1 разворачивается в Epic → Story → Task.
Предложение последовательности:

- **R1 «Силовая цель» (MVP, Mini App)** — Story [GOA-S1]:
  - Task [GOA-T1] Модель Goal + хранение + совместимость: `GymData` (goals, goalRemind),
    сериализация/чтение по §10, расширение `GymContractTest` (старый файл без goals —
    байт-в-байт; новый файл читается).
  - Task [GOA-T2] Экран «Цели» + архив: подэкран, карточки (бар/кольцо), отмена с
    confirm, архив + «Повторить», пустое состояние, 320px.
