## 1. Цель и пользовательская проблема

**Проблема пользователя.** Дневник отлично работает, пока есть привычка. Но привычка
ломается: тренировка осталась незавершённой, неделя прошла без зала, цель тихо зависла.
Бот молчит — вернуть в зал нечему. Единственный проактивный контакт сегодня — ручная
рассылка владельца.

**Проблема продукта.** Retention: по рыночным данным 70–80% пользователей фитнес-приложений
отваливаются за первые 3 месяца. Данные, на которые опирается эта спека (включены по
требованию #406):

| Факт | Источник/следствие для дизайна |
|---|---|
| 70–80% отваливаются за 3 месяца | механика возврата — главный рычаг роста, а не «ещё одна фича» |
| behavior-triggered напоминания работают в 3–4 раза лучше broadcast | триггеры по факту данных (молчание, незавершённая, цель), не календарный спам |
| day-1 ачивка поднимает retention 20.5% → 33.4% | «Первая тренировка» — событие №1 (§10) |
| максимум 2–5 уведомлений в неделю; 53% юзеров считают напоминания раздражающими | антиспам-конституция §2: структурные лимиты, отписка в один тап |
| эмпатия вместо стыда («жизнь бывает busy», не «вы пропали») | тональность §4: без вины и давления |
| сообщения 60–100 символов | все тексты-наджи §4 уложены в коридор |
| уведомления в день тренировки по плану открывают в 3–4 раза чаще, чем в дни отдыха | поле `cadence` (§9) подстраивает пороги и дайджест |

**Суть фичи.** Бот сам, по данным пользователя, пишет ему в чат в четырёх случаях
(незавершённая тренировка / молчание 7–14–21 дней / чек-ин целей / итоги недели) плюс
один раз поздравляет с первой тренировкой. Всё отключается, всё считается, всё в
анти-спам рамках.

## 2. Конституция антиспама (обязательные правила механики)

1. **Не более 1 проактивного сообщения в день** (любого типа). Проверка — по
   `notifyLog` (§12): последняя запись сегодня → тишина.
2. **Структурные лимиты по типам** (считаются по построению, отдельный счётчик не нужен):
   - незавершённая — ≤1 на тренировку (одна активная существует всегда);
   - реактивация — 3 сообщения за жизнь цикла (7/14/21 день), потом стоп навсегда,
     пока не будет новой завершённой тренировки;
   - чек-ин — 1/нед (воскресенье); дайджест — 1/нед (понедельник);
   - «первая тренировка» — 1 за жизнь.
   Итоговый потолок — **≤4/нед в худшем случае** (обычно ≤2) — внутри рыночного коридора 2–5.
3. **Тихие часы: 21:00–10:00 UTC+3 — отправок нет вообще** (даже тихих: баннер ночью
   тоже будит). Окна отправки — §5.
4. **Отписка в один тап под каждым проактивным сообщением** (§4, кнопки `🔕`),
   плюс общий тумблер, плюс `/notify`. Возврат — `/notify` или настройки.
5. **Эмпатия, не стыд.** Запрещены формулировки вины («ты пропал», «ты забросил»),
   обратный отсчёт («осталось 3 дня до провала цели»), сравнения с другими. Тексты §4.
6. **Событийные сообщения ≠ напоминания.** «Первая тренировка» (§10), «🏆 Рекорд!»,
   «🏆 Цель достигнута!» — поздравления в момент действия юзера: общий тумбл НЕ глушит
   их (иначе сломаем существующие поздравления). Мастер-тогл глушит только 4
   проактивных типа.
7. **Тик не пишет файлы без отправки** (правило в псевдокоде §5.4) — ни mtime-шум, ни лишние ревизии.
8. **Агрегаты только.** В `stats.json` и логах — счётчики и типы, без chat_id и
   содержимого (§13; границы — ANA-S2 §3).

## 3. Типы уведомлений — сводная карта

> Дефолты (opt-out на все типы), тональность «ты», тихий пуш для дайджеста/чек-ина —
> решения владельца 25.11, см. §17.

| # | Тип | Триггер | Расписание | Дефолт | Обоснование opt-out (не opt-in) |
|---|---|---|---|---|---|
| 1 | **Незавершённая тренировка** (`unf`) | активная тренировка с `date ≤ сегодня−1`, юзер не трогал данные ≥24 ч | первый тик в окне юзера после срабатывания | **вкл** (null) | данные самого юзера + конкретное действие («допиши»); ≤1 сообщение на тренировку |
| 2 | **Реактивация** (`cb`) | нет завершённых тренировок 7/14/21 дней (пороги §5.3), нет активности ≥3 дней | первый тик в окне юзера | **вкл** (null) | вся ценность фичи — до людей, которые НЕ открывают приложение (opt-in их не увидит никогда); ограничители: 3 сообщения max + стоп, отписка в один тап, эмпатия |
| 3 | **Чек-ин по целям** (`goal`) | есть активные цели, `goalRemind != false` (поле уже существует!) | воскресенье, окно юзера (GOA-S1 §6.2: «19:00» — см. §7) | **вкл** (null) | решение GOA-S1 (12.11): null = включены; UX-S19 наконец отправляет обещанное |
| 4 | **Итоги недели** (`dg`) | ≥1 завершённая тренировка за прошедшую ISO-неделю | понедельник, окно юзера (ANA-S2 §2в: «09:00» — см. §8) | **вкл** (null) | решение ANA-S2 §2в: включена по умолчанию у активных; сводка своих данных в свой чат — легитимно без согласий |
| 5 | **Первая тренировка** (`first`) | завершилась первая тренировка в дневнике (событие, не расписание) | сразу (бот — в сообщении финиша; приложение — ближайший тик, ≤1 ч) | **вкл**, не отключается (событийное, как рекорды) | day-1 ачивка: retention 20.5% → 33.4%; юзер только что был активен, сообщение не «неожиданное» |

Типы 1–4 глушатся мастер-тоглом `notifyMaster`; тогл 5-го типа не заводим (§2.6).

**Приоритет внутри дня** (если готовы несколько): `first` (вне очереди и окон) →
`unf` → `goal` → `dg` → `cb`. Остальные в этот день уже не отправятся (правило 1/день).

## 4. Тексты (ядро, копипаст-готовые)

> Тональность: «ты», эмпатия без стыда, 60–100 символов для наджей. Существующий бот
> весь на «ты» («У тебя есть незавершённая тренировка…», «Заверши первую! 💪») — новые
> сообщения бота наследуют его. Тексты на «Вы» из GOA/ANA спек при реализации
> гармонизируются в «ты» (решение 1 §17). HTML parse_mode, жирный — как во всех
> сообщениях бота; названия упражнений — через существующий `esc()`.

```text
🏋️ Тренировка от 24-11 осталась незавершённой. Жизнь бывает насыщенной — допишешь сегодня?
```

(78 символов; дата — `fmtDate(active.date)`, формат «24-11» как в истории.)

| 1 | ▶️ Продолжить тренировку | callback `wk:resume` | экран активной тренировки (существующий флоу `openWorkout`) |
| 2 | 🔕 Не напоминать | callback `ntf:offunf` | `notifyUnfinished=false` + ответ §4.6 |

## 5. Триггеры, окна, тихие часы и таймзона

### 5.1 Часовой пояс — решение: якорь UTC+3 + «спрошенное окно» (решение 3 §17)

Бот не знает TZ юзера (в `GymData` её нет; `startedAt` пишется серверными часами).
Варианты и выбор:

| Вариант | Оценка | Почему |
|---|---|---|
| **А. Якорь на время сервера + окно «утро/день/вечер» в настройках (выбран — решение 3 §17)** | ✅ | один честный вопрос вместо технического («когда напоминать» понятнее, чем «какой у тебя UTC-офсет»); основная аудитория — RU/СНГ в зоне UTC+3±2, окно шириной 4 ч покрывает сдвиг; ноль математики TZ/DST; ПДн не добавляет |
| Б. Спрошенный UTC-офсет чипами | − | ~30 значений, юзер не знает свой офсет наизусть; UI-перегруз ради точности, которая не нужна окну в 4 ч |
| В. Инференс по времени активности (mtime/сообщения) | − | мало точек у редких юзеров; серверные часы; сбитые часы не чинятся; риск обратный — отправка ночью; невозможно объяснить юзеру, почему «именно сейчас» |
| Г. TZ из Telegram (`initData` не содержит TZ клиента) | − | Bot API не отдаёт TZ юзера — технически недоступно |

**Правила времени (все — по UTC+3, зона якоря без перехода на летнее время):**

- Все часы планировщика считаются от `System.currentTimeMillis() + GYM_NOTIFY_TZ_MIN`
  (env-якорь, **дефолт 180 = UTC+3**) — независимо от TZ контейнера (на VPS UTC).
  Якорь задаёт, что считать «утром» и «вечером»; конкретная зона в спеке и интерфейсе
  не называется — обезличено (решение владельца 25.11).
- **Тихие часы: 21:00–10:00 UTC+3** — отправок нет вообще.
- **Окна отправки**: `notifyWhen` = 1 «Утром» (10–13) · 2 «Днём» (13–17, дефолт, null) ·
  3 «Вечером» (17–21). Окно = «в течение какого часа пришло, неважно»: тик раз в час
  → сообщение попадает в первый час окна (или первый тик после входа в окно).
- Календарные типы: **чек-ин — воскресенье**, **дайджест — понедельник** — в окне юзера
  (день недели по UTC+3; если тик окна понедельника пропущен из-за простоя
  бота — дайджест на этой неделе не приходит, навёрстывания нет, E5 ANA-S2).
- Пояса, далёкие от зоны сервера (например, Дальний Восток) — юзер выберет «утром»
  и получит напоминание в свой вечер: приемлемо для MVP (решение 3 §17).

### 5.2 Триггер «незавершённая тренировка»

- Условия: `data.active() != null` И `LocalDate.parse(active.date) ≤ today−1`
  (висит минимум сутки) И `dataFileMtime(chatId)` старше **24 ч** (юзер не трогал
  ни бота, ни приложение — иначе сообщение прилетит в момент, когда он и так тут)
  И `notifyUnfinished != false` И `notifyLastWid != active.id` (про эту тренировку
  ещё не писали).
- После отправки: `notifyLastWid = active.id` (одна тренировка = одно сообщение,
  вторых «ну может всё-таки?» нет).
- Тренировка завершена/удалена/заменена новой — триггер пересчитывается сам,
  `notifyLastWid` остаётся мусорным до следующего случая (безвредно).

### 5.3 Триггер «реактивация»

- **Молчание** = дней с последней ЗАВЕРШЁННОЙ тренировки (`countFinished`-логика по
  `finished=true`); если завершённых нет — дней с `dataFileMtime` (юзер пришёл,
  посмотрел, ушёл — файл создан и не тронут).
- Пороги: день **7 / 14 / 21** (≥). `notifyStage` хранит, до какого уровня дошли
  (0/1/2/3); уровень L отправляется, когда `stage < L` и молчание ≥ порога(L) и
  `notifyComeback != false` и `dataFileMtime` старше **3 дней** (юзер не активен —
  активным реактивация не нужна).
- **Текст выбирается по факту молчания, не по этапу**: 7–13 дней → «неделя»,
  14–20 → «две недели», ≥21 → «последнее». Так юзер, молчащий с релиза 90 дней,
  получит ОДНО сообщение — сразу «последнее» (корректно и честно), а не «неделя без
  тренировок» про три месяца.
- **Новая завершённая тренировка обнуляет** `notifyStage = 0` (перезапуск цикла
  после возврата — это фича, не баг: следующий отвал получит свежую серию).
- `cadence == 1` (тренируется раз в неделю): 7 дней молчания — его норма, пороги
  сдвигаются на +7 → **14 / 21 / 28** (решение 6 §17). `cadence` ≥2 или null — базовые.
- Нулевая история: текст «первая тренировка — самая важная» (§4.2) на уровне 1.
- **Известная неточность (принять осознанно)**: собственная запись тика (`notifyLog`)
  обновляет mtime — для нулевого юзера лестница уровней растягивается (7-й день →
  уровень 2 через 14 дней после НАШЕГО сообщения, а не от первого захода). Дубликатов
  это не создаёт, только замедляет темп; лечится отдельным полем «дата первого
  захода», которое ради этого не заводим.
- Дружим с незавершённой: у юзера с зависшей тренировкой молчание считается от
  последней ЗАВЕРШЁННОЙ (незавершённая не считается ни тренировкой, ни активностью) —
  «допиши» (unf) и «вернись» (cb) могут идти по своим каналам, разнесённые суточным
  лимитом.

### 5.4 Схема решения тика (порядок проверки, псевдокод для кодера)

```text
для каждого chatId из storage.chatIds():
    data = storage.load(chatId)                      // synchronized, безопасно
    если workouts пусто И mtime свежее (<7д) → skip  // нулевой юзер ещё «на смотрине»

    [first]  firstDone==null И countFinished==1 И дата той тренировки ≤7 дней назад
             (окна и тихие часы НЕ проверяются — событие)      → отправить, firstDone=true
    [unf]    активная есть И date≤вчера И mtime>24ч И lastWid≠id И в окне юзера
             И notifyUnfinished≠false И не отправляли сегодня  → отправить, lastWid=id
    [goal]   воскресенье (UTC+3) И goalRemind≠false И есть активные цели И в окне И не сегодня → чек-ин GOA §6.1
    [dg]     понедельник (UTC+3) И notifyDigest≠false И ≥1 finished за прошлую ISO-неделю
             И в окне И не сегодня                            → дайджест ANA §2в
    [cb]     stage<уровня(молчание) И notifyComeback≠false И mtime>3д И в окне И не сегодня → §4.2

    каждое «отправить»: sendMessageResult → ok ? (notifyLog+дата+тип, stage/wid/firstDone,
    счётчик stats) : (ошибка глотается, файл НЕ пишется — повтор в следующий тик/день)
    при записи: storage.save ТОЛЬКО если что-то отправлено (§2.7)
```

Суточный лимит «не отправляли сегодня» проверяется по `notifyLog` — до выбора типа,
поэтому неуспешная отправка (ошибка Telegram) не съедает лимит дня.

## 6. Планировщик: как встроить в Main без поломки long polling

### 6.1 Архитектура

`Main.java` — чистый цикл long polling (строки 69–81), планировщика в нём нет.
В `BotLogic` уже есть `ScheduledExecutorService` (`rest-timer`, тик 1 с — правки
таймера отдыха) и паттерн `summaryTickSafe` (тик 60 с, сводка владельцу). **Свой
поток обязателен**: часовой обход всех `data/*.json` с HTTP-отправками на общем
`restScheduler` подвешивал бы тик таймера отдыха на секунды.

```java
/* BotLogic, конструктор — рядом с существующим restScheduler: */
this.notifyScheduler = Executors.newSingleThreadScheduledExecutor(r -> {
    Thread t = new Thread(r, "notify-ticker");
    t.setDaemon(true);          // не держит JVM (паттерн rest-timer)
    return t;
});
this.notifyScheduler.scheduleAtFixedRate(this::notifyTickSafe, 70, 3600, TimeUnit.SECONDS);
```

- Период **3600 с (1 ч)**, старт через 70 с (пропустить стартовый шум, разойтись с
  `summaryTick`).
- `notifyTickSafe` = try/catch вокруг всего тика (паттерн `restTickSafe:119`):
  исключение логируется одной строкой `[warn] notify tick: …`, поток живёт.
- Обход: `storage.chatIds()` → для каждого свой try/catch (один битый файл не валит
  обход), `storage.load()` (synchronized — конкурентно с `/api/save` безопасно),
  решение по §5.4, отправка, при успехе — запись.
- Отправка: `api.sendMessageResult(chatId, text)` (null = ok) — ошибки одного чата
  не роняют обход (паттерн `/announce:2060–2088`); пауза 50 мс между отправками
  (только когда есть что слать).
- Тихий пуш: чек-ин и дайджест — через новый `sendMessageSilentKb(chatId, text, kb)`
  (добавить `disable_notification:true` в существующий вариант с клавиатурой);
  unf/cb/first — обычный пуш (§4, решение 5 §17).

### 6.2 Идемпотентность и рестарты

- Вся книга учёта (`notifyLog`, `notifyStage`, `notifyLastWid`, `firstDone`) — в файле
  юзера: рестарт контейнера не даёт дублей (последняя проверка в тике — «отправляли
  сегодня?»). Глобальный `digest-state.json` из ANA-S2 **не нужен** — per-user лог
  заменяет его (у юзеров разные окна отправки, одного глобального «lastWeek»
  недостаточно).
- Бот был выключен в понедельник весь день — дайджест этой недели не приходит
  (навёрстывания нет, E5 ANA-S2); в воскресенье — аналогично чек-ин.
- Один и тот же тик повторно не отправит ничего: все условия проверяются до отправки,
  `notifyLog` пишется только при ok.

### 6.3 Ошибки и недоступные чаты

- Бот заблокирован (`403 Forbidden`): `sendMessageResult` вернёт описание — глотаем,
  **файл не пишем** (лимит дня не съеден), счётчик `notifySent*` не растёт (паттерн
  E7 ANA-S2). Повтор — со следующего eligible-дня. Оптимизация «авто-мьют после N
  подряд 403» — на усмотрение кодера (память процесса), в скоуп не входит (N≈десятки
  чатов — стоимость повторных попыток нулевая).
- `data/` недоступен / файл битый: `storage.load` уже глотает (возвращает пустую
  GymData) — пустой юзер ни на что не триггерит.

### 6.4 Аптайм

- Поток daemon — не держит JVM при остановке бота; исключение в тике не убивает
  планировщик (`notifyTickSafe` глотает). `scheduleAtFixedRate`: если тик зависнет
  (сетевой тайма-аут Telegram — read 40 с), следующий ждёт завершения — деградации
  таймера отдыха нет (он в другом потоке).
- Часы планировщика считаются от `System.currentTimeMillis()` + смещение якоря
  (монотонность не критична: окна широкие, лимит дня по дате).

### 6.5 Гонки с записью из Mini App (важно для кодера)

Тик: `load → решить → отправить → save`. Между load и save (сотни мс — HTTP) юзер
может сохранить тренировку из приложения — слепое `save` затрёт его правку (lost
update). Правило: **перед `save` перечитать файл** (`storage.load`) и применить к
свежей копии ТОЛЬКО книжечные поля (`notifyLog/notifyStage/notifyLastWid/firstDone`),
затем сохранить. Окно гонки сужается до мс.

### 6.6 Логи и ПДн

Тик логирует агрегаты: `[notify] week=2026-W48 unf=1 cb=2 goal=0 dg=1 first=1 err=0`.
Без chat_id, без содержимого (границы ANA-S2 §3.2). Ошибка Telegram — уже без ПДн
(описание API), логируется как счётчик.

## 7. Стыковка с GOA-S1: чек-ин по целям (долг goalRemind)

GOA-S1 §6.2 запроектировал: ежедневный тик → раз в неделю чек-ин, если есть активные
цели и `goalRemind != false`; финалы целей (достижение/истечение) — отдельные события.
GOA-T6 (R2) не реализован: поле `goalRemind` пишется (UI-тогла в приложении до сих
пор нет — `grep goalRemind web/app.js` пуст), но не отправляется ничего.

UX-S19 закрывает долг так:

| Параметр GOA-S1 §6.2 | UX-S19 | Комментарий |
|---|---|---|
| тик раз в сутки, серверное время | тик раз в час, якорь на время сервера | единый планировщик §6, часовая гранулярность для окон |
| воскресенье 19:00 | воскресенье, окно юзера | обобщение: 19:00 = «вечер»; для утреннего юзера чек-ин в его окне (решение 10 §17) |
| тогл: Mini App строка «🔔 Напоминания о целях» + кнопка на экране «Цели» бота | тогл в карточке «🔔 Уведомления» (§11) + строка `/notify` + кнопка `🔕` под чек-ином | одно место для всех напоминаний вместо двух; экран «Цели» бота из GOA-S1 R2 не трогаем (он не реализован) |
| «финалы целей» (достижение/истечение) | **в скоуп UX-S19 НЕ входят** | это событийные сообщения, а не возвратная механика; остаются в GOA-R2, отправятся тем же тиком (код planner'а переиспользуется) |
| `goalRemind` (Boolean, null=вкл) | используется как есть | поле и контракт уже в проде — новых ключей для чек-ина не заводим |

Совместимость: расписание/тогл из GOA-S1 §6.2 заменяются этой спекой; тексты §4.3 —
гармонизация GOA §6.1 в «ты» (решение 1 §17).

## 8. Стыковка с ANA-S2: дайджест недели

Механика ANA-S2 §2в принимается целиком (тексты, расчёты метрик, E-серия, `/digest`,

| Параметр ANA-S2 §2в | UX-S19 | Почему |

- Расчёт метрик (тренировки/время/тоннаж/ккал/рекорды/дельта) — таблица ANA-S2 §2в

- `/digest` сохраняется: ручной просмотр + возврат отправки (тогл пишет `notifyDigest`).

## 9. Онбординг: шаг «Сколько дней в неделю тренируешься?»

Существующий флоу (ONB, ред. 5): приветствие-карусель (слайды 1–3, «Начать»/
«Пропустить», `gymOnbDone`) → туториал 4 шага (новым юзерам) → приложение.

**Новый шаг — между «Начать» и туториалом** (и для существующих юзеров: после
карусели, туториала у них нет — сразу в приложение):

```text
… карусель, слайд 3, «Начать»
        ↓
[новый шаг] «Сколько дней в неделю тренируешься?»
        ↓
новые юзеры → туториал (шаг 1 из 4)
существующие → приложение
```

- Экран в стиле приветствия (`.ob`, макет — экран 3): заголовок, чипы `1 2 3 4 5 6 7`
  и отдельная кнопка **«Пока не знаю»**, подпись «Помогает подстроить напоминания —
  изменить можно в настройках».
- **Тап по чипу = ответ и переход** (один тап, без «Дальше»: настройка безобидна и
  меняется потом). «Пока не знаю» = пропуск и переход.
- Хранение ответа: **`GymData.cadence`** (Integer 1–7; null = «пока не знаю»).
  Отклонение от принципа ONB «флаги в localStorage» осознанное: cadence — не флаг
  онбординга, а настройка, **нужная серверу** (пороги §5.3, строка дайджеста §4.4) —
  как `restSec`. Запись — обычным `save()` (сервер merge'ит по §12.3).
- «Спрошен ли уже» — localStorage `gymCadenceAsk=1` (после ответа/пропуска; не в
  GymData — это именно флаг показа). localStorage недоступен — шаг пропускается
  молча (fail-open, принцип ONB §6).
- Фолбэк (null): пороги 7/14/21 базовые, дайджест без строки «план N/нед» —
  механика полностью работоспособна.
- Существующим юзерам шаг показывается один раз при первом входе после релиза
  (вместе с каруселью) — это самый дешёвый способ заполнить `cadence` у текущей базы.
- Смена потом: Настройки → «🔔 Уведомления» → ряд «Дней в неделю» (§11).

## 10. «Первая тренировка» (day-1 ачивка)

**Условие**: завершилась первая тренировка в дневнике — `countFinished(data)` стала 1.
Retention-обоснование: 20.5% → 33.4% (§1).

- **Бот**: строка в сообщении финиша `BotLogic.finishWorkout:1476` (§4.5) — юзер в
  чате, поздравление мгновенное. Условие в этой точке: до завершения `countFinished==0`.
  После — `firstDone=true` (книга, §12).
- **Mini App**: тост в `finishWorkout` (`web/app.js:4161`), условие: до сохранения
  завершённых было 0 И `G.firstDone` не true (поле придёт из `/api/init` — клиент
  видит книгу).
- **Чат-сообщение при завершении из приложения**: тот же часовой тик — `firstDone==null
  И countFinished==1 И дата первой завершённой ≤7 дней` → отправка (§4.5), `firstDone=true`.
  7-дневный грейс — окно для простоя бота; **легаси-юзеры** (завершили первую задолго
  до релиза) не получают ничего: дата старая → условие ложно, файл не пишется (нулевой
  churn при выкатке).
- Edge: юзер удалил первую и завершил новую — `firstDone==true` → молчим (второго
  «первого раза» нет).
- Не глушится мастер-тоглом (§2.6): событийное, юзер сам только что завершил.

## 11. Управление: карточка в Настройках + /notify

### 11.1 Mini App — карточка «🔔 Уведомления» в Настройках

Место: экран Настройки (`renderSettings`, `web/app.js:3647`), **между «⏱ Таймер
отдыха» и «🧑‍🏫 Персональный тренер»** (макет — экраны 1–2). Компоненты — готовые
`.switch`/`.setrow`/`.chips`, новых иконок НЕТ (урок ONB ред. 3–5 обойдён).

```text
🔔 Уведомления
(мета) Бот подстрахует, если отвлечёшься. Ночью — тишина.
[тумбл] Напоминания                 ← мастер (notifyMaster)
[тумбл] Незавершённая тренировка    (notifyUnfinished)
[тумбл] Возврат в зал               (notifyComeback)

[тумбл] Итоги недели                (notifyDigest)
```

- Мастер off: строки 2–5 и чипы затемняются (`setrow-dim`, чипы `disabled`), состояние
  сохраняется (включение мастера возвращает всё как было); под карточкой остаётся
  рабочей строка «Дней в неделю» (это не напоминание).
- Тап по тумблу → мгновенный `save()` (напоминания живут в данных юзера на сервере:
  правка из приложения применяется сразу, бот увидит её на следующем тике); тост
  «✓ Сохранено» — существующий паттерн.
- «Чек-ин по целям» мета-подсказка: «воскресенье вечером, если есть цели».
- Строки «Уведомления» нет в Профиле — Настройки единственная точка (Профиль — только
  данные, UX-S4 §7).

### 11.2 Бот — /notify (экран §4.7)

Для юзеров без Mini App. Callback-тоглы пишут поля через `storage.save` немедленно.
Плюс кнопки `🔕` под каждым сообщением (§4) — полный путь «увидел → отключил» в один тап.

## 12. Модель данных (GymData) и совместимость

### 12.1 Новые поля (формат — по образцу `goalRemind`/`restSec`: null = дефолт)

```java
/* [UX-S19] механика возврата */
public Integer cadence;           /* дней в неделю 1–7; null = «пока не знаю»/не отвечал */
public Boolean notifyMaster;      /* null = вкл; false = все 4 проактивных типа выкл */
public Boolean notifyUnfinished;  /* null = вкл; false = не писать про незавершённую */
public Boolean notifyComeback;    /* null = вкл; false = без реактивации */
public Boolean notifyDigest;      /* null = вкл; false = без итогов недели */
public Integer notifyWhen;        /* 1 утро, 2 день (дефолт null), 3 вечер */
/* книга учёта — пишет ТОЛЬКО сервер (тик), см. §12.3 */
public Integer notifyStage;       /* реактивация: 0..3 — до какого уровня дошли */
public Long notifyLastWid;        /* id незавершённой, о которой уже написали */
public Boolean firstDone;         /* true = поздравление с первой отправлено */
public final List<NotifyMark> notifyLog = new ArrayList<>(); /* ≤7 последних: {"d":ISO-дата,"t":тип} */
```

`NotifyMark` — новый маленький класс уровня `Goal`: `{ String d; String t; }`,
`t ∈ {unf,cb,goal,dg,first}`.

JSON-фрагмент (порядок — конец карты, рядом с `goalRemind`):

```json
"cadence": 3,
"notifyMaster": true,
"notifyComeback": false,
"notifyWhen": 2,
"notifyStage": 1,
"notifyLastWid": 17,
"firstDone": true,
"notifyLog": [{"d":"2026-11-23","t":"dg"},{"d":"2026-11-25","t":"cb"}]
```

(null-поля `notifyUnfinished`/`notifyDigest` в файле отсутствуют — не настроены
и не отключались; это состояние = «вкл».)

Пишутся только заданные значения (null-поля не пишутся; `notifyLog` — только непустой;
`notifyMaster:true` пишется как true — юзер явно вернул после «выкл», семантика как
у `goalRemind`: null и true = вкл).

### 12.2 Обратная совместимость (эталон — GymContractTest)

- **Чтение**: ключей нет → дефолты (null/пустой список) — старый файл читается как
  сейчас; каждый ключ читается толерантно (`cadence` — Integer 1–7, мусор мимо;
  `notifyWhen` — 1–3; `notifyStage` — 0–3; `notifyLog` — список, битые элементы
  пропускаются, неизвестный `t` игнорируется, трим до 7; `notifyLastWid` — Long ≥ 0;
  Boolean-поля — только Boolean). Мусорное значение не валит чтение файла.
- **Запись**: файл юзера, ни разу не менявшего настройки и не получавшего сообщений,
  остаётся **байт-в-байт прежним** (ни одного нового ключа).
- **Вперёд**: старая версия кода игнорирует незнакомые ключи (Json-парсер читает карту
  целиком) — откат релиза бесплатный.
- Контрактные проверки в `GymContractTest`: legacy-файл без ключей → round-trip без
  новых ключей; файл с полным набором → читается; мусор в каждом поле → дефолт;
  `notifyLog` >7 записей → трим при чтении.

### 12.3 Merge в `/api/save` (WebServer.java:354–370 — расширение блока)

| Поле | Кто прав | Правило (по образцу существующих) |
|---|---|---|
| `notifyMaster`, `notifyUnfinished`, `notifyComeback`, `notifyDigest`, `notifyWhen`, `goalRemind` | клиент (UI их меняет) | как `restSec`/`goalRemind`: null в payload — серверное не затирает; non-null — принимается (старый кэш JS без ключей ничего не ломает) |
| `cadence` | клиент (UI его меняет) | как `warmupFirst`: ЯВНЫЙ ключ применяется как есть, **включая null** — «Пока не знаю» обязано сбрасывать выбор; отсутствие ключа — серверное не затирает. *(Правка ревью PR #417: первоначальная формулировка «null не затирает» противоречила сбросу — код с самого релиза реализует явный ключ, контракт «cadence=null — применяется» в `GymContractTest`)* |
| `notifyLog`, `notifyStage`, `notifyLastWid`, `firstDone` | только сервер (книга) | из payload **не принимаются никогда** — клиентские (стэил) значения игнорируются, серверные сохраняются; иначе гонка «тик отправил → стэил-вкладка сохранила старый stage → дубль сообщения» |

Клиент получает поля через `/api/init` (уже в `data.toJson()`) — для условия тоста
«первая тренировка» (`G.firstDone`) достаточно.

### 12.4 Данные и таймзона

Полей TZ в GymData НЕТ (решение §5.1: `notifyWhen` + env-якорь времени сервера).
`GYM_NOTIFY_TZ_MIN` (дефолт 180 = UTC+3) — конфиг сервера, не юзера.

## 13. Метрики (/stats, Stats.java)

Whitelist `Stats.KEYS` расширяется по процессу ANA-S2 §3.3 (новая строка в таблице
границ + ключи; без тихих инкрементов). Все — агрегаты, без chat_id:

| Ключ | Считает | Точка инкремента |
|---|---|---|
| `notifySentUnf` | отправлено «незавершённая» | тик, только при ok |
| `notifySentRc` | отправлена реактивация (любой уровень) | тик, ok |
| `notifySentGoal` | отправлен чек-ин целей | тик, ok |
| `notifySentFirst` | отправлено поздравление «первая» | тик, ok (строка в бот-финише не считается — это не отдельная отправка) |
| `digestSent` | отправлен дайджест | тик, ok (**имя ANA-S2 сохранено**) |
| `notifyReactedUnf` / `notifyReactedRc` / `notifyReactedGoal` / `notifyReactedDigest` | **реакция**: юзер ЗАВЕРШИЛ тренировку в течение **24 ч** после напоминания этого типа | `BotLogic.finishWorkout` + `WebServer.handleSave` (прирост finished): смотрят `notifyLog` на запись ≤24 ч, тип из записи |
| `notifyOff` | тапы «🔕 Не напоминать» (unf/cb/goal) | callback `ntf:off*` |
| `digestOff` | тапы «🔕 Не присылать итоги» | callback `digest:off` (**имя ANA-S2**) |

- `notifyReactedFirst` НЕ заводим: реакция на поздравление («вторая тренировка за
  24 ч») — метрика нечестная, счётчик-шум.
- `weeks`-агрегация и ротация 26 недель — без изменений (`Stats.add` уже всё умеет).
- Дашборд: панели «react rate по типам» (`notifyReactedX/notifySentX`) и «доля
  отписок» (`notifyOff+digestOff` ко всем отправленным) — конфиг Grafana поверх
  `weeks` (трек (а) ANA-S2), вывозить кодом не нужно; включить в панель при следующем
  обновлении дашборда (по желанию владельца).
- Ежедневная сводка владельцу (`/summary`, `summaryText`) — дополнить строкой
  «🔔 Напоминания: отправлено N · среагировало M» (снимок `Stats` уже там; правка
  одной строки в `summaryText`).

## 15. Что НЕ делаем и почему

| Не делаем | Почему |
|---|---|
| Ежедневные напоминания «занимайся» без триггера | broadcast, а он в 3–4 раза слабее behavior-triggered; коридор 2–5/нед |
| ТЗ-база часовых поясов, автоопределение TZ | нет источника (Bot API не отдаёт); окно юзера + якорь времени сервера покрывают основную аудиторию (§5.1); решение 3 §17 |
| Инференс TZ по активности | флейки у редких юзеров, необъяснимо для юзера, риск обратный (§5.1, вариант В) |
| Отдельный тогл на «первую тренировку», рекорды, поздравления целей | событийные сообщения в момент действия юзера — как существующие «🏆 Рекорд!»; иначе два класса «поздравлений» и ползучий фриз |
| Пуши в Mini App (in-app центры уведомлений) | канал один — чат; in-app не виден без открытия, ради него нужен новый UI целиком |
| Навёрстывание пропущенных чек-инов/дайджестов | шум (E5 ANA-S2); недельный ритм самовосстанавливается |
| Напоминания про серию («сорвёшь стрик») | давление/страх — против тональности §2.5 |
| Пер-цельные напоминания (тогл на каждую цель) | GOA-S1 решил: один глобальный тогл, перебор для MVP |
| Изменение времени каждого типа по отдельности | одно окно юзера для всех — простота важнее точности (решение 3 §17) |
| Автоматический мьют заблокированных чатов, ретраи с бэкоффом | N≈десятки: стоимость повторной попытки нулевая, сложность — нет (§6.3) |
| «Умные» вариации текстов/A-B | нет масштаба для измерений (ANA-S2 §5); 3 финальные строки дайджеста — максимум вариативности |
| Рассылка «новая фича вышла» этой механикой | для этого `/announce` (ручной, владельцем); каналы не смешивать (E8 ANA-S2) |
| Персональные данные в логах тика и счётчиках | граница ANA-S2 §3 (§6.6, §13) |

## 17. Решения владельца (25.11.2026)

> Все 10 открытых вопросов закрыты при утверждении спеки и макета. Нумерация
> соответствует вопросам ревизии 1; ниже — решения и их следствия для реализации.

1. **Тональность — «ты»** (весь бот на «ты», как существующие тексты). Тексты GOA-S1
   §6.1 / ANA-S2 §2в при реализации гармонизируются в «ты» (§4.3/§4.4).
2. **Дефолты opt-out — на все 4 проактивных типа** (null = вкл). Риск закрыт
   ограничителями: реактивация ≤3 сообщений со стопом, отписка в один тап, эмпатия.
3. **Таймзона — якорь UTC+3 + окно юзера** «утро/день/вечер» (§5.1);
   тихие часы 21:00–10:00 UTC+3; env `GYM_NOTIFY_TZ_MIN` — механизм
   якоря (дефолт 180 = UTC+3). **В пользовательских текстах зона называется
   как «UTC+3» — без названия города** (решение владельца 25.11: «время сервера»
   непрозрачно для юзера; правка ревизии 3). При смене `GYM_NOTIFY_TZ_MIN`
   строки «UTC+3» в текстах синхронно обновить. Альтернативы (чипы UTC-офсетов,
   инференс по активности) отклонены.
4. **Тексты §4** — машинная вычитка от ИИ-измов выполнена (ревизия 2; аудит по
   P0→P1→P2 — чисто, правок не потребовалось), финальную вычитку делает владелец
   перед выкаткой; 3 финальные строки дайджеста: «Хорошая неделя. Так держать 💪» /
   «Неделя в работу — каждая тренировка на счету 💪» / «Мощная неделя! 🔥».
5. **Звук пушей**: дайджест и чек-ин — тихие (баннер без звука); незавершённая,
   реактивация, «первая» — обычные со звуком.
6. **Порог для «раз в неделю»**: `cadence=1` → пороги реактивации **14/21/28** дней
   (сдвиг +7, §5.3).
7. **«Первая тренировка» НЕ глушится мастер-тумблером** (событийное сообщение, как
   «🏆 Рекорд!»).
8. **Winback-волна на релизе — разово при выпуске** (всем молчунам ≥21 дня уходит
   одно «последнее напоминание» §4.2); далее — env-гейт по возрасту молчания для
   будущих запусков (механизм в §15 не входит, при необходимости оформится отдельно).
9. **Дайджест — понедельник в окне юзера** (не фиксированные 09:00 из ANA-S2).
10. **Чек-ин целей — воскресенье в окне юзера** (не фиксированные 19:00 из GOA-S1).
