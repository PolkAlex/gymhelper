## 0. Общие изменения модели данных (GymData.java) — общие для фич

Оба новых поля **опциональные**: старые `data/*.json` без них читаются как раньше
(требование обратной совместимости, эталон — `GymContractTest`).

### 0.1. `restSec` — длительность отдыха по умолчанию (фичи #77 и #79)

| Что | Значение |
|---|---|
| Тип в GymData | `public Integer restSec;` (nullable) |
| Диапазон | 30–600 сек; вне диапазона → игнорировать при чтении, clamp при записи |
| Дефолт при отсутствии/null | **90 сек** (обе среды: бот и Mini App) |
| Кто пишет | бот: `/rest N`; Mini App: чипы в Профиле (§1.5) |
| Сериализация | `toJson`: писать только если `restSec != null` (как `profile`); `fromJson`: `Object v = m.get("restSec"); if (v != null) { int n = (int) Json.lng(v); if (n >= 30 && n <= 600) d.restSec = n; }` |

Единое поле = единая настройка для бота и приложения (логично: один человек, один зал).
Mini App НЕ дублирует её в localStorage — читает из загруженного `G` (при офлайн-редактировании
значение уже в памяти с последнего `/api/init`).

### 0.2. `templates` — шаблоны тренировок (фичи #82 и #84)

Точная схема JSON (имена полей — в стиле существующего кода: короткие, нижний регистр;
блок `w/s/r` повторяет форму `SetEntry`):

```json
"templates": [
  {
    "id": 1,
    "name": "Спина и бицепс",
    "createdAt": "2026-11-06T18:30:00",
    "exercises": [
      { "name": "Тяга верхнего блока", "w": "60", "s": 3, "r": "10" },
      { "name": "Подтягивания",        "w": "",   "s": 4, "r": "8"  }
    ]
  }
]
```

| Поле | Тип | Смысл |
|---|---|---|
| `id` | long | уникальный в пределах пользователя; при создании `max(существующих id)+1` (отдельный счётчик не нужен: id используется только в момент старта, переиспользование после удаления безвредно) |
| `name` | String 1–60 | название шаблона |
| `createdAt` | String ISO | дата создания (для сортировки списка «новые сверху») |
| `exercises[].name` | String 1–60 | название упражнения (снимок на момент сохранения) |
| `exercises[].w / s / r` | String / int / String | **план-подсказка** (последний блок по упражнению): показывается в превью списка («4 упр. · 60 кг»); в v1 НЕ автоподставляется в ввод — см. §4 «Отсечено» |

Классы Java (в стиле соседних): `GymData` получает `public final List<Template> templates = new ArrayList<>();`
и новые классы `Template` (`long id; String name; String createdAt; List<TemplateExercise>`) и
`TemplateExercise` (`String name; String w; int s; String r`).

Правила чтения/записи:
- `fromJson`: если ключа нет → пустой список (старые файлы ок). Толерантно к пропускам: `w` нет → `""`, `s < 1` → `1`, `r` нет → `""`.
- `toJson`: писать ключ `templates` только если список непуст (как `del`) — файлы «до фичи» остаются байт-в-байт прежними.
- ⚠️ Критично: Mini App сохраняет через `/api/save` весь `G` целиком — сервер обязан сохранить
  `templates` и `restSec` при round-trip (иначе шаблон, созданный в приложении, молча исчезнет).
  Отсюда именно типизированные поля GymData, а не «прозрачные» map-остатки.
- `GymContractTest` дополнить: legacy-файл без `templates`/`restSec` читается; файл с шаблонами
  переживает round-trip без потерь (имена с кавычками/эмодзи, `w` с диапазоном «75-175»).

Лимиты: **20 шаблонов** на пользователя; имя шаблона 1–60 символов; упражнений в шаблоне 1–20;
имя упражнения 1–60. Дубликаты имён разрешены (различимы по составу в списке).

## 1. [UX-T4] Таймер отдыха в Mini App (#77)

### 1.1. Цель и проблема

Боль №2 из исследования: таймер отдыха есть у **всех без исключения** конкурентов
(Hevy, Strong, JEFIT, GymUp, HeavySet, Liftin, StrongLifts). Между подходами телефон в руке —
таймер удерживает приложение открытым и убирает «смотреть на часы в телефоне» руками.
Сейчас в GymHelper таймера нет вообще.

### 1.2. Точка автозапуска (по коду)

Подходы логируются в `saveEntry()` (`web/app.js:1463`): после валидации подход добавляется
в `e.sets`, вызывается `await save()`, показывается тост «✓ Сохранено», модалка закрывается.

**Правило:** таймер запускается/перезапускается ТОЛЬКО когда:
- `modalCtx.setIdx < 0` (лог **нового** блока, не редактирование);
- тренировка **незавершённая** (`!w.finished`) — редактирование истории таймер не трогает.

Редактирование записи (`setIdx >= 0`), удаление записи/упражнения таймер не перезапускают.

Длительность = `G.restSec || 90`. Подпись на панели — название упражнения (`modalCtx.name`).

### 1.3. Где живёт панель (решение)

**Плавающая стеклянная плашка над нижней навигацией** (не постоянная нижняя панель). Причины:
1. В карточке тренировки низ уже занят `.backbar` (💾 Сохранить / 🚪 Выйти, fixed, bottom ≈ 78px) —
   вторая постоянная панель внизу не влезает.
2. Таймер — контекстный объект, живущий минуты; постоянная полоса «съедала» бы экран 100% времени.
3. Плавающую плашку можно свернуть в пилюлю — ввод следующего подхода никогда не блокируется.

Позиционирование (CSS, fixed, `left/right: 12px; max-width: 536px; margin: 0 auto`):

| Контекст | bottom |
|---|---|
| Обычный (над `.nav`) | `calc(88px + env(safe-area-inset-bottom))` |
| Видна `.backbar` (карточка тренировки/тех-экран) | `calc(140px + env(safe-area-inset-bottom))` (стопкой над backbar) |
| Открыта модалка ввода | панель **остаётся тикать**, но визуально скрыта под шторкой: `z-index: 38` (< модалки 50), backdrop модалки её накрывает |

`z-index` панели 38 — ниже `.backbar` (39), модалок (50), тоста (90).

### 1.4. Состояния панели

| Состояние | Разметка (см. макет, экран 1–3) | Поведение |
|---|---|---|
| **Идёт** | иконка ⏱, крупные цифры `01:12` (tabular-nums, ~24px/800, янтарь), подпись «Отдых · Жим штанги лёжа», тонкий прогресс-бар (fill = остаток/длительность, градиент `--accent-deep → --accent`), кнопки: `⏸ Пауза`, `+30 сек`, `✕` | тикает раз в секунду от `end`-метки |
| **Пауза** | кнопка `▶ Продолжить`, цифры цвета `--muted`, прогресс замирает | остаток заморожен |
| **Истёк** | glow-бордер (`--glow-brd`), текст `✅ Перерыв окончен — время работать 💪`, кнопка `Скрыть`; + тост «⏱ Отдых окончен» + сигнал (§1.6) | авто-скрытие через 30 с, если нет тапа |
| **Свёрнута** | пилюля `⏱ 01:12 ⌃` (та же позиция), тап раскрывает | не мешает прокрутке и вводу |

Кнопки: `⏸/▶` — пауза/продолжить; `+30 сек` — `end += 30 c`, `dur += 30 c` (шкала удлиняется);
`✕` — сброс (ключ удаляется, панель исчезает; без confirm — потеря дешёвая).
Свёрнутость хранится в состоянии таймера (`mini: true`) и переживает перезагрузку.

### 1.5. Настройка длительности по умолчанию (экран Профиль)

Новая карточка в `renderProfileTab()` после карточки темы:

```
⏱ Таймер отдыха
Запускается автоматически после записи подхода.

[60] [90•] [120] [180] [Своё…]     ← чипы .chip, 90 активна
Своё: [ 240 ] сек (30–600)          ← появляется по тапу «Своё…»
Звук по окончании:  [🔊 Вкл] [🔇 Выкл]
```

- выбор чипа / ввод «Своё» → `G.restSec = N` (clamp 30–600) → `save()` → тост «✓ Сохранено»;
  `G.restSec == 90` можно хранить как `null` (дефолт) или числом — кодеру на усмотрение,
  поведение одинаковое.
- «Звук по окончании» → localStorage `gymRestSound` = `'on'|'off'` (дефолт `on`). Локально на
  устройстве, т.к. аудио — свойство устройства, синхронизировать нечего.

### 1.6. Сигнал по окончании

Каскад (первый доступный):
1. `tg.HapticFeedback.notificationOccurred('success')` — внутри Telegram (iOS/Android);
2. `navigator.vibrate([180, 90, 180])` — браузер вне Telegram;
3. WebAudio-beep: 3 коротких синус-сигнала 880/880/1318 Гц по ~0.18 с (последний выше — «финиш»);
   `AudioContext` создаётся лениво и разблокируется на первом пользовательском тапе
   (одноразовый `pointerdown`-листенер) и на тапе «Добавить» — иначе мобильные браузеры блокируют звук.
4. Всё недоступно → тихо (только визуал).

Звук выключен тумблером (§1.5) → только вибрация/хаптика и визуал.

### 1.7. Хранение: переживает перезагрузку

localStorage-ключ **`gymRest`** (единственный, формат JSON):

```json
{
  "end": 1730912400000,   // epoch ms момента окончания (абсолютная метка!)
  "dur": 90,              // полная длительность текущего цикла, сек
  "paused": false,        // true → отсчёт заморожен
  "left": 42,             // остаток в сек — только при paused
  "mini": false,          // панель свёрнута
  "ex": "Жим штанга лёжа" // подпись упражнения
}
```

Ключевые решения:
- остаток **всегда вычисляется** как `end − Date.now()` (не декрементом по таймеру) —
  вкладки, сон устройства и перезагрузка не уводят отсчёт;
- пауза: `left` = остаток, `end` из ключа удаляется; продолжение: `end = now + left·1000`;
- при старте приложения: `paused` → показать `left`; `end > now` → продолжить; `end ≤ now` и
  `now − end < 60 с` → показать состояние «Истёк»; иначе ключ стереть (протух за ночь).

### 1.8. Edge cases (обязательные к реализации)

| Случай | Поведение |
|---|---|
| **Лог подхода другого упражнения во время отсчёта** | таймер перезапускается на полную длительность, подпись меняется на новое упражнение. Правило одно: таймер привязан к последнему залогированному подходу, никакой очереди таймеров |
| **Несколько вкладок** | ключ `gymRest` один; `window.addEventListener('storage', …)` синхронизирует отображение; последняя запись побеждает (last write wins — конфликты маловероятны: пишет только действие пользователя). Звук по истечении может сработать в каждой открытой вкладке — принимаем (редкий сценарий, стоимость фильтрации выше ценности) |
| **Разметка при истечении** | состояние «Истёк» из §1.4 (glow-карточка + тост), авто-скрытие 30 с |
| **Перезагрузка страницы** | восстановление по `end`-метке (§1.7), включая свёрнутость |
| **Модалка ввода открыта в момент истечения** | звук/хаптика срабатывают, тост показывается поверх (z 90), панель обновится под шторкой; ввод не прерывается ничем |
| **Активной тренировки нет** | панель независима от экранов: дорабатывает или сбрасывается по `✕` |
| **Офлайн** | таймер — чисто клиентский, работает без сети; настройка `restSec` берётся из последнего загруженного `G` |

### 1.9. Что НЕ делаем и почему

| Отсечено | Причина |
|---|---|
| Разные длительности по упражнениям (Strong-style) | нет данных «какое упражнение какой отдых хочет»; добавлять настройки в каталог ради этого рано; одно глобальное значение закрывает боль |
| Отдельный таймер для разминки | нет разминки как типа записи в модели данных (set-типы отсечены в исследовании) |
| Синхронизация таймера бот ↔ Mini App | разные среды исполнения, у бота и приложения разные сессии; общий только дефолт `restSec` |
| Push-уведомление об окончании из Mini App | Telegram Mini App не умеет пушить без бота; сигнал в моменте (звук/вибрация) достаточен |
| Ползунок/циферблат на панели | чипы в Профиле + «+30 сек» на панели покрывают подстройку; циферблат — лишний хром |

## 2. [UX-T5] Таймер отдыха в боте (#79)

### 2.1. Цель и проблема

Та же боль №2, но для юзеров, которые ведут дневник в чате, не открывая Mini App.
Бот может пушить — в зале это даже удобнее (вибрация кармана). Главные риски: лимиты
Telegram API на редактирование и спам, если юзер ушёл из чата.

### 2.2. Точка запуска (по коду)

`confirmEntry()` (`BotLogic.java:645`) — после `storage.save` и отправки
`«✅ Записано: …»` с `entryDoneKb()`. Там же запускается/перезапускается отсчёт.

### 2.3. Одно сообщение на сессию

- После **первого** лога подхода бот отправляет сообщение-отсчёт (см. формат ниже).
- Каждый следующий лог подхода **перезапускает это же сообщение** (`editMessageText`),
  а не создаёт новое. У чата не более одного живого таймера.
- Если сообщение удалено юзером («message to edit not found») → сессия помечается мёртвой;
  при следующем логе создаётся новое сообщение.

### 2.4. Форматы сообщений (HTML parse_mode, как везде в боте)

**Отсчёт:**
```
⏱ Отдых: 1:22
▰▰▰▰▰▰▰▰▰▱▱▱▱▱▱▱▱▱
Жим штанги лёжа — следующий подход
```
- прогресс-бар: 18 ячеек, заполнено = `round(18 × остаток/длительность)`;
- строка 3 = `esc(название упражнения) + " — следующий подход"`;
- inline-клавиатура: `[ +30 сек (rest:more) | ⏹ Стоп (rest:stop) ]`.

**Финал (правка того же сообщения):**
```
✅ Отдых окончен — подход сам себя не сделает
```
клавиатура удаляется.

**Финальное уведомление (отдельное сообщение):**
```
⏰ Перерыв окончан — 75 кг × 8 ждут продолжения
```
- отправляется с `disable_notification = true` — **тихий пуш**: баннер есть, звука нет.
  Обоснование: бот не умеет играть звук; громкий пуш на каждый подход раздражает, а юзер в зале
  и так рядом с телефоном. Тихий пуш + вибрация кармана — золотая середина.
- в текст подставляется последний залогированный блок («75 кг × 8»); для подходов без веса —
  «подходы ждут продолжения».

`TelegramApi.sendMessage` дополнить параметром `disableNotification` (сейчас его нет).

**Кнопки:**
- `rest:more` (+30 сек): `end += 30 c`, длительность шкалы += 30; одна правка сразу;
- `rest:stop`: сессия останавливается, сообщение правится в финальный вид (без уведомления-пуша).

### 2.5. Троттлинг правок (схема)

Telegram tolerates ~1 сообщение/сек на чат; правки считаются в тот же бюджет. Схема с запасом:

| Параметр | Значение |
|---|---|
| Тик планировщика | 1 сек (`ScheduledExecutorService`, один поток — чистый JDK, без зависимостей) |
| Обычная фаза (остаток > 15 с) | правка не чаще **1 раза в 5 сек** |
| Финальная фаза (остаток ≤ 15 с) | правка не чаще **1 раза в 1 сек** (потолок Telegram не задевается: одна правка/сек на чат) |
| Защита «message is not modified» | текст сравнивается до правки; не изменился (округление) → пропуск; ошибка 400 → глушится |
| Дефолт 90 с | ≈ 15 правок по 5 с + 15 по 1 с ≈ **30 правок на таймер** — спокойно |

Планировщик работает только с `TelegramApi` и in-memory сессией (никаких `Storage`-операций) —
потокобезопасность с главным циклом long polling тривиальна; поля сессии, мутируемые из
callback-потока (`end`, `stopped`), пометить `volatile`.

### 2.6. Антиспам: юзер ушёл

- Для каждого чата хранится `lastActivity` (обновляется на **любой** update: сообщение, callback).
- Активности нет **5 минут** → сессия **замораживается**: правки прекращаются, сообщение замирает
  с последним значением (финальный пуш не отправляется).
- Юзер вернулся (любой update) → **одна** ресинк-правка: актуальный остаток, либо сразу финальный
  вид, если время истекло. Тикание продолжается.
- Абсолютная `end`-метка (epoch ms) — заморозка не сдвигает время окончания, только прекращает
  отрисовку.

### 2.7. Команда /rest

| Ввод | Ответ |
|---|---|
| `/rest` | «⏱ Длительность отдыха: 90 сек.\nИзменить: /rest 180 (от 30 до 600).\nТаймер запускается автоматически после записи подхода.» + `mainKb()` |
| `/rest 180` | clamp 30–600; сохраняется в `GymData.restSec` (`storage.save`) → ответ «✅ Отдых: 180 сек.»; если таймер идёт — перезапуск на новую длительность (правка сообщения) |
| `/rest 700`, `/rest abc` | «Число от 30 до 600, например: /rest 180» |
| `/restx`, `/restfoo` | НЕ матчить: проверять `text.equals("/rest") || text.startsWith("/rest ")` (аналогично `/templates` — сейчас `/statsx` тоже матчится, для новых команд делаем аккуратно) |

Регистрация в `setMyCommands()`: `rest` — «Таймер отдыха: /rest 120».

### 2.8. Не блокирует ввод; перезапуск при новом подходе

- Мастер ввода (вес → подходы → повторения) работает как раньше; сообщение-отсчёт — отдельное,
  ничего не редактирует в диалоге ввода.
- Лог подхода во время отсчёта → тот же message-edit на полную длительность (§2.3): диалог
  «✅ Записано…» + отсчёт заново. Никаких вопросов «прервать таймер?».
- `wk:finish` / `wk:cancelok` → сессия останавливается, сообщение правится в финальный вид
  (без пуша).

### 2.9. Хранение сессии

Только в памяти: `ConcurrentHashMap<Long, RestSession>` (как `states`). В JSON не пишем:
после рестарта бота сообщение просто замирает, следующий лог создаст новое. Персистентность
таймера не нужна — это секундный объект, а не данные пользователя.

### 2.10. Что НЕ делаем и почему

| Отсечено | Причина |
|---|---|
| Кнопка «Пауза» в боте | «+30» и «Стоп» покрывают 100% сценариев; пауза в чате почти никогда не нужна (ушёл — сообщение само замрёт по §2.6) |
| Правки каждую секунду всё время | 90 правок на таймер против 30 — нагрузка на API и батарея юзера ради плавной цифры; 5-сек шаг и финальная секунда дают живость |
| Проценты/эмодзи-циферблат | текстовый бар из 18 ячеек читается и рендерится мгновенно |
| Пуш «звонком» (со звуком) | см. §2.4: боты не управляют звуком пушеи; громкий пуш на каждый подход — антипаттерн |

## 3. [UX-T2] Live-PR + 1ПМ (#71)

### 3.1. Цель и проблема

Боль №10 (мотивация) и №12 (оценка 1ПМ): у Hevy это live PR notification, у FitNotes — e1RM.
Рекорды у нас есть в статистике, но пользователь не получает **эмоцию в момент ввода** —
самый дешёвый ретеншн-механизм (§7 исследования: «эмоция за 20 строк кода»).

### 3.2. Формула и вычисления

**Эпли:** `e1RM = вес × (1 + повторения / 30)`, округление до целого, отображение со знаком «≈».

Правила разбора блока (одинаковые в боте и Mini App):
- вес блока — строка («70», «75-175»): берём **среднее** (в MA — готовый `avgNum`; в боте —
  парсер чисел по образцу `NUM_PATTERN`: диапазон → среднее, два числа → среднее);
- повторения — строка: по правилам существующего `repsAvg` (MA): «12» → 12, «8-10» → 9,
  «5+1» → 6 (дроп-сет суммируется); в боте — та же логика (там уже есть разбор «5+1»/«8-10» в вводе);
- блок «70 кг, 3 подхода по 8» = **один** кандидат e1RM ≈ 89 кг. **Количество подходов (`s`)
  в e1RM не участвует** — это оценка одного повторения, умножение на `s` ломает метрику;
- `w` пустой (без веса) → e1RM не считается.

### 3.3. Критерий рекорда

**PR силы (e1RM)** — для упражнений с весом:
> e1RM нового блока **строго больше** max e1RM всех блоков этого упражнения из **прошлых
> тренировок** (упражнение сопоставляется по имени без регистра — как `findEx`;
> «прошлые» = индекс тренировки строго меньше текущей в `G.workouts`).

Следствия (осознанные решения):
- блоки **той же** тренировки не входят в базу → в одной тренировке упражнение празднуется
  **максимум 1 раз** (первое превышение). Без этого каждый следующий подход «ставил рекорд» — спам;
- **первый подход упражнения в истории — НЕ рекорд** (база пуста). Иначе «рекордом» был бы
  каждый первый подход нового упражнения, что обесценивает поздравление. Со 2-го лога сравнение
  работает (можно побить базу первой тренировки);
- **равный результат не празднуется** (строгое `>`) — повторение лучшего результата не новость;
- редактирование/удаление записей задним числом PR-поздравления не пересчитывает (они
  «моментные»); блок статистики 1ПМ всегда считается от актуальных данных.

**Объёмный PR** — для упражнений **без веса** (боль №14: «no volume for bodyweight squats»):
- объём упражнения за тренировку = `Σ (sets × повторения)` по всем его блокам;
- рекорд: объём этой тренировки строго больше максимума по прошлым тренировкам;
- формат: «🏆 Рекорд объёма! 38 повторений подтягивания за тренировку».

**Показывать ли два вида PR?** Решение: **в моменте празднуется ровно один вид**:
- упражнение с весом → только e1RM;
- упражнение без веса → только объёмный PR (e1RM невозможен).
Обоснование: два одновременных поздравления девальвируют друг друга и удваивают шум; объёмный
PR для железа часто «побивается» просто количеством подходов — как поздравление он дешёвый,
поэтому для веса он живёт только в статистике (молча). А для веса тела объём — единственная
честная метрика, там он полноценный PR.

### 3.4. Бот: формат поздравления

Поздравление **второй строкой** в существующее сообщение «✅ Записано…» (`confirmEntry`),
НЕ отдельным сообщением — ввод не засоряется:

```
✅ Записано: 75 кг, 3 подхода по 8
🏆 Рекорд! 1ПМ ≈ 95 кг (прошлый ≈ 88 кг)
```

```
✅ Записано: без веса, 4 подхода по 10
🏆 Рекорд объёма! 40 повторений подтягивания за тренировку
```

- «прошлый ≈ X кг» — побитая база (если база не пуста);
- частота: ≤ 1 поздравления на упражнение за тренировку (§3.3);
- то же правило для блоков, залогированных одной строкой «45кг, 4 по 12» и пошагово —
  точка проверки одна (`confirmEntry`).

### 3.5. Mini App: тост «Новый рекорд!»

В `saveEntry()` после успешного `save()`: если новый блок — PR → вместо «✓ Сохранено»
специальный тост (класс `.toast.pr`, новый стиль):

- фон — янтарный градиент CTA (`linear-gradient(135deg, var(--accent-deep), var(--accent))`),
  текст `--on-accent`, иконка 🏆, длительность 3.5 с (обычный тост 2.2 с);
- текст: `🏆 Новый рекорд! 1ПМ ≈ 95 кг` / `🏆 Рекорд объёма! 38 повторений`;
- хаптика: `tg.HapticFeedback.notificationOccurred('success')`;
- вид в макете `docs/mockups/ux-t2-live-pr.html`, экран 1.

Дополнительно (P2, можно вторым коммитом): у подхода-рекордсмена в карточке тренировки —
янтарный чип `🏆 95` (как `.wtag`), вычисляется при рендере карточки (лучший e1RM блока
тренировки > базы прошлых тренировок).

### 3.6. Статистика: блок «Оценка 1ПМ»

**Mini App** (`renderStatsTab()`): новая карточка сразу после карточек «Рекорд недели»
(та же тематика рекордов), до «Серии»:

```
ОЦЕНКА 1ПМ · ЭПЛИ
🏋  Жим штанги лёжа          ≈ 95 кг
    лучший подход: 75 кг × 8
    … (по строке на упражнение, всего 5)
────────────────────────────
e1RM = вес × (1 + повторения ÷ 30) —
оценка, а не цель для разовых попыток
```

- топ-5 упражнений **с весом** по убыванию e1RM (иконка каталога, имя, «≈ N кг» янтарным
  18px/800, подстрока «лучший подход: W кг × R» — блок, на котором достигнут максимум);
- упражнений с весом нет → карточка не показывается вовсе (не пустой заглушкой);
- вид: макет `ux-t2-live-pr.html`, экран 2.

**Бот** (`showStats()`): в списке «🏆 Упражнения» к каждому упражнению с весом добавить строку
`  1ПМ ≈ 95 кг` (после «Максимум: …»). Без веса — строка не добавляется.

### 3.7. Edge cases (сводка)

## 4. [UX-T6/T7] Шаблоны тренировок (#82, #84)

### 4.1. Цель и проблема

Боль №5: главный функциональный разрыв с рынком (Hevy routines, Strong, JEFIT, FitNotes…).
Юзеры ходят по программам и хотят «не думать в зале»: начал из шаблона — список упражнений
уже на месте, дальше обычный ввод. «Повторить прошлую тренировку» — частный случай того же
механизма.

### 4.2. Данные

Схема и лимиты — §0.2. Шаблон = **снимок списка упражнений** на момент сохранения:

### 4.3. Бот: сохранить тренировку как шаблон (#82)

**Момент 1 — сразу после завершения.** `finishWorkout()` сейчас отправляет
`«🎉 Тренировка завершена!\n\n…»` + `mainKb()`. Заменить клавиатуру на `mainKb()` с
добавленным **первым** рядом:

```
[ 💾 Сохранить как шаблон  →  tpl:new_<wid> ]
[ 🏋️ Начать тренировку ]
[ 👀 Посмотреть тренировку ]
[ 📜 История | 📊 Статистика ]
[ 📱 Открыть приложение ]   ← как было
[ ⚙️ Профиль ]
```

**Момент 2 — из истории.** В экране завершённой тренировки (`renderWorkoutScreen`, ветка
`w.finished`) добавить ряд перед «🗑 Удалить»:

```
[ 🔁 Повторить | 💾 В шаблоны ]      ← tpl:rep_<wid> | tpl:new_<wid>
```
(«Повторить» здесь же — см. §4.5.)

**Диалог сохранения:**
```
💾 Сохраним тренировку как шаблон.

Название (до 60 символов), например: Спина и бицепс
[ поле ввода ждёт текст ]
```
inline-клавиатура: `[ 🔤 Авто-имя (tpl:auto_<wid>) | ↩️ Отмена (tpl:canc) ]`,
режим `st.mode = TPL_NAME`. Авто-имя: кастомное название тренировки → первая его строка;
иначе первые 2 упражнения через « · »; иначе «Тренировка DD-MM».

Ответ после сохранения:
```
✅ Шаблон «Спина и бицепс» сохранён (3 из 20).

Начать из него: /templates или кнопка «📋 Шаблоны».
```
+ `mainKb()`.

Ошибки: 21-й шаблон → «Лимит — 20 шаблонов. Удали лишний: /templates»; тренировка без
упражнений с записями → не предлагаем сохранение (кнопка появляется только если есть что
сохранять; finishWorkout и так не завершает пустую).

### 4.4. Список шаблонов (#82)

Команда `/templates` (регистрация в `setMyCommands`: «Шаблоны тренировок») + кнопка
«📋 Шаблоны» (`menu:tpl`) новым рядом в `mainKb()` после «📜 История | 📊 Статистика».

```
📋 Шаблоны · 3 из 20

Тапни по названию, чтобы начать тренировку.
```
inline-клавиатура (по ряду на шаблон, новые сверху):
```
[ ▶️ Спина и бицепс | 🗑 ]     tpl:start_1 | tpl:del_1
[ ▶️ Ноги · тяга | 🗑 ]        tpl:start_2 | tpl:del_2
[ ↩️ Меню ]
```
Пустой список:
```
📋 Шаблонов пока нет.

Заверши тренировку и нажми «💾 Сохранить как шаблон» —
в следующий раз начнёшь с готового списка упражнений.
```
+ `mainKb()`.

Удаление: `tpl:del_<id>` → confirm на том же сообщении:
```
Удалить шаблон «Спина и бицепс»?
```
`[ 🗑 Да, удалить (tpl:delok_<id>) | ↩️ Отмена (tpl:back) ]` → возврат к списку.

### 4.5. «Повторить прошлую тренировку» = тот же механизм (#84)

`tpl:rep_<wid>`: строит **временный** шаблон из завершённой тренировки (в список шаблонов НЕ
пишется): упражнения по порядку, план `w/s/r` = последний блок каждого упражнения. Далее —
тот же код старта, что у `tpl:start`. Шапка: «🔁 Повторяем тренировку от 03-11».
В Mini App — та же логика по кнопке «🔁 Повторить».

### 4.6. Старт из шаблона (#84) — бот

`tpl:start_<id>`:
1. Если есть активная тренировка → стандартный диалог «есть незавершённая»
   (`▶️ Продолжить / 🗑 Удалить и начать новую / 🏠 Меню`) — шаблон применится после решения.
2. Иначе создаётся **незавершённая** тренировка (`id = nextId++`, дата/время — сейчас) с
   упражнениями из шаблона: `name`, `startedAt = now`, `sets` пустые.
3. Экран тренировки (`renderWorkoutScreen`) с шапкой-строкой:
   `📋 Шаблон «Спина и бицепс» применён — 4 упражнения. Записывай как обычно.`
   (шапка добавляется один раз к тексту экрана; при дальнейших рендерах её уже нет).
4. Дальше — обычный ввод. Пустые упражнения (`sets` пуст) отбрасываются при завершении —
   существующая логика обеих сред.

### 4.7. Mini App: выбор шаблона при старте (#84)

`startWorkout()` (кнопка FAB и «Начать тренировку»):
- активная тренировка есть → как сейчас (карточка + пикер);
- нет ни шаблонов, ни завершённых тренировок → **мгновенный старт как сейчас** (новичок
  без лишнего тапа);
- иначе → **модалка «Новая тренировка»** (bottom-sheet, как все модалки):

```
Новая тренировка

[ 🏋️ С пустого списка ]            ← .btn prime wide
[ 🔁 Повторить прошлую · 03-11, 4 упр. ]   ← .btn sec wide (если есть завершённые)

📋 Шаблоны · 2
┌────────────────────────────────┐
│ Спина и бицепс            [🗑] │
│ 4 упр. · тяга блока, подтяг…  │   ← свёрнутая карточка: имя + мета
├────────────────────────────────┤
```

- `🗑` — confirm-модалка «Удалить шаблон «X»?»;
- «Повторить прошлую» — подпись с датой и числом упражнений последней завершённой;

### 4.8. Mini App: сохранить как шаблон (#82)

Кнопка «💾 В шаблоны» в `workoutCard()` для **завершённых** тренировок (ряд действий:

```
В шаблон войдут (4):
```

|---|---|
| «Чек-лист подходов» как в Hevy (план vs факт, отметить выполненное) | смена парадигмы ввода (мастер логирует блоки, а не отмечает план-подходы); отдельный эпик, если спрос подтвердится |
| Автоподстановка плана w/s/r из шаблона в поля ввода | подсказки прошлых весов уже решают это из истории; дубль механики усложняет модалку ввода. Поле в схеме оставлено — превью и будущий префилл |
| Готовые программы (PPL, 5/3/1) «из коробки» | территория StrongLifts/Boostcamp; сначала личные шаблоны, готовые наборы — потом |
| Папки/теги шаблонов | 20 шаблонов обходятся без иерархии |
| Шеринг шаблонов между пользователями | вне модели данных (шаблоны в личном JSON), вопрос приватности; отдельная идея |

## 5. Кросс-фичевые решения (сводка для lead)

| Решение | Альтернатива | Почему так |
|---|---|---|
| Дефолт отдыха — 90 сек, хранится в `GymData.restSec`, общий бот/MA | два независимых localStorage/поля | один человек — одна настройка; боту /rest и MA-профилю не о чем спорить |
| Панель таймера MA — плавающая плашка, сворачиваемая | постоянная нижняя полоса | низ занят `.backbar` в карточке тренировки; контекстность |
| Бот правит отсчёт по схеме «5 с / финальные 15 с по 1 с» | правка каждую секунду | 30 правок вместо 90 на таймер, лимиты Telegram с тройным запасом |
| Пуш по окончании в боте — беззвучный (`disable_notification`) | громкий пуш / только правка | баннер без звука = заметно и не бесит на 20-м подходе |
| PR в моменте — ровно один вид (e1RM для веса, объём для веса тела) | два вида сразу | девальвация и шум; объём для железа бьётся «количеством подходов» |
| Первый подход упражнения — не рекорд | поздравлять первый | иначе каждый новый эксперованный exercises «рекорд» — обесценивание |
| Шаблон = снимок имён упражнений + план w/s/r (без автоподстановки) | чек-лист Hevy-стиля | не ломает обкатанный мастер ввода; план уже полезен в превью |
| Старт из шаблона при активной тренировке | молча перезаписать | активная тренировка — данные юзера, решение за ним (существующий диалог) |
| FAB без шаблонов и истории стартует мгновенно | модалка всегда | новичок не платит лишним тапом; модалка появляется, когда есть выбор |
| Сессии таймера бота — только в памяти | персистентность в JSON | секундный объект; рестарт бота = замирание сообщения, не потеря данных |
